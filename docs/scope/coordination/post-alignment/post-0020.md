# Post-alignment fixes for 0020 (lead workflow wf_fa323a0b-69e, 2026-10-20)

Each item was found by a cross-document reviewer and confirmed by a skeptical second reviewer. Some items repeat from two boundaries; apply once. Lead decisions in the brief override the fix text where they differ.

## 1. [major] Core evaluator returns protocol DTOs: core-to-protocol dependency is forbidden

- Boundary: create-path
- Evidence and reasoning: 0020:274 declares `stackly-core::instance::create::build_form(...) -> CreateForm`, and 0020:179-190 lists `CreateForm` (which embeds the protocol `RuntimeSummary` and `CapabilityStatus` DTOs) under "DTO baru di modul `instance` `stackly-protocol`". No core-side `CreateForm` is defined anywhere. `Evaluation.command: CommandDraft` is a core type built in step 6 (0020:1002), but 0020:431 makes it the parameter of `stackly_protocol::instance::command::equivalent_command(&CommandDraft)`, built in step 8. 0001:87 says "`stackly-core` tidak bergantung pada `stackly-protocol` ... Pemetaan dari domain ke DTO terjadi di `stacklyd`". check_deps.rs:162 denies core -> protocol, and protocol is in LEAVES (check_deps.rs:33), so protocol cannot depend on core either. The CLI round trip also needs the draft type in protocol, because the CLI cannot depend on core. Nothing elsewhere resolves this. Step 6 and step 8 would build incompatible placements of `CommandDraft`, and `build_form` cannot compile as written.
- Fix: In 0020 *Evaluator create*, make `build_form` return a core `CreateFormModel` and `Evaluation.command` a core `CommandSpec`. Define the wire `CommandDraft` in `stackly_protocol::instance::command` next to `equivalent_command` (step 8). Have stacklyd map `CreateFormModel` to `CreateForm` and `CommandSpec` to `CommandDraft` (step 9). Change step 6 to list `CreateFormModel` and `CommandSpec` instead of `CommandDraft`.

## 2. [major] FieldError codes and messages in 0020 break the fixed set in spec 0006

- Boundary: create-path
- Evidence and reasoning: 0006:123 says the FieldError `code` comes from a fixed set and "`message` adalah teks tetap per kode", and 0006:166 applies this to every `ErrorBody.fields`. In code, `FieldError::new(path, FieldCode)` (error.rs:416) takes the message from `code.message()`, and there is no custom-message constructor. 0020:301 explicitly limits the fixed-text rule to `request.invalid_params` ("aturan teks tetap spec 0006 tetap berlaku untuk `request.invalid_params`") and gives interpolated messages such as "Use at least {minLength} characters." (0020:311-316). 0020:319 sets the code for name, display name, endpoint, and secret fields to "kode di baris evaluator", which are catalog error codes and not FieldCodes. 0020:976 says 0006 needs no update. This directly contradicts a foundation wire rule, and the protocol API cannot express it.
- Fix: In 0020 *Field error*, replace the "Pesan" column with "teks tetap `FieldCode` (spec 0006)" and delete the clause that limits the fixed text to `request.invalid_params`. Replace "kode di baris evaluator" with explicit FieldCodes: `invalid_format` for `name` and `displayName`, `unknown_value` for an unknown endpoint name, `out_of_range` for a port, `invalid_value` for `secrets[<i>].input.content`. Bound-specific wording goes only into the preflight row `detail`.

## 3. [major] Synchronous create error adds `fields` to codes that cannot carry fields

- Boundary: create-path
- Evidence and reasoning: 0020:297 (and AC-10, 0020:32) says the synchronous error is the ErrorBody of the first error row "ditambah `fields` berisi semua field issue". Rows are ordered provider, runtime, name, endpoint, settings, data, disk, secret, so a port in use plus a bad setting yields `supervisor.endpoint_in_use` carrying settings fields. 0006:123 requires every code that carries fields to list `omitted` and allow no `items`, and `ErrorBody::with_fields` debug-asserts this (error.rs:177-182). None of the possible first-row codes lists `omitted`: `supervisor.endpoint_in_use`, `endpoint_conflict`, and `endpoint_unavailable` (0010:397-399), `instance.settings_invalid` (0010:424), `instance.name_invalid` (0020:394 and 0010:426, empty details), and `secret.invalid_value` (0011:372). `secret.needs_secret` has `items` (0011:367), so it can never carry fields, yet it can head the error while another secret entry has an `invalid_value` field issue. 0020 proposes no catalog change for these codes. codes.rs on main has no instance or secret area yet, so this is not yet fixed in code.
- Fix: Change 0020:297 to attach `fields` only when the first error code lists `omitted` and has no `items`. In the 0020 *Kode error* table, add `omitted` to `instance.name_invalid`. Add matching update blocks for 0010 (`instance.settings_invalid`, `instance.endpoint_invalid`, `supervisor.endpoint_in_use`, `supervisor.endpoint_conflict`, `supervisor.endpoint_unavailable`) and 0011 (`secret.invalid_value`). State that when `secret.needs_secret` heads the error, `fields` is omitted and AC-2 parity compares `fields` only for the other codes.

State that after step 9 it expects `failed` with full compensation, and that it makes initdb fail through a test hook placed after the content check, or through the fake init path instead of a planted file.

## 5. [minor] Precheck rejection in spec 0007 cannot carry `fields`

- Boundary: create-path
- Evidence and reasoning: 0020 AC-10 (0020:32) and 0020:361 say the precheck rejects "dengan kode baris error pertama dan semua `fields`". The 0007 API (0007:269-270, 310-315) gives `PrecheckOutcome::Reject(OperationError)`, and `OperationError` has only code, retryable, details, and rule (K11 adds items, not fields). On main, `Rejection::parts` (precheck.rs:104) carries no fields. `Rejection::error()` does return `&dyn OperationError`, so stacklyd could downcast to a concrete create error, or keep the Evaluation it passed in. That makes this resolvable, but 0020 never says which, and its 0007 update block adds no fields channel.
- Fix: Add one sentence to 0020 *Operasi `create_instance`* (handler paragraph): the create precheck's error type carries the Evaluation's field issues, and stacklyd recovers them by downcasting `Rejection::error()` (or by keeping the Evaluation it built) and attaches them with `with_fields` when `begin` returns `Rejected`.

## 6. [minor] The `register` step's `ctx.commit` inserts a provider revision that has no compensator

- Boundary: create-path
- Evidence and reasoning: 0007:393 (binding rule): "`ctx.commit` di tengah operasi ... apa pun yang ia sisipkan wajib punya kompensator kustom". 0020:371 commits `InsertProviderRevision?` in the `register` batch through `ctx.commit`, and 0020:127 says provider revisions are removed by compensation "tidak pernah (immutable, dipakai bersama)". `instance_registration` deletes only the instance, its uses, and the cascaded rows. The deliberate exception is sensible, but no document states it, and the 0007 update block in 0020 does not add it. A reviewer applying 0007 would flag it.
- Fix: Add to the 0020 *Usulan update spec lain* block for spec 0007 an exception sentence after the `ctx.commit` rule: "kecuali baris bersama yang immutable dan idempoten (`InsertProviderRevision`), yang sengaja tidak dikompensasi (spec 0020)".

## 7. [minor] Pinned-revision lookup by name and revision has no registry read

- Boundary: create-path
- Evidence and reasoning: 0020:162-163 and AC-15 say "registry punya tepat satu provider revision untuk nama dan revision itu" and give `instance.provider_ambiguous` for more than one digest. The Registry port (0005:402) only has `provider_revision(&ProviderRevisionKey)`, whose key includes `manifest_sha256`, so there is no read by (name, revision). The "jalur spec 0010" that AC-15 cites is disk-based: 0010:380 ("paket pinned ditemukan unik untuk `name` dan `revision`") and 0010:496 (folder `<data>/providers/<ns>/<name>/<revision>/<sha>/`). The 0020 gather IO list (0020:279) names no `read_dir`. A developer resolves it by reading 0010, but the two documents name different sources for the same lookup.
- Fix: In 0020 *Resolusi provider dan revision* and the gather IO bullet, say that gather lists `providers/<ns>/<name>/<revision>/` with `Filesystem::read_dir` (more than one digest folder gives `instance.provider_ambiguous`), then confirms the single candidate with `Registry::provider_revision(key)` and `read_package` with `NameCheck::Skip`.

# Post-alignment fixes for 0010 (lead workflow wf_fa323a0b-69e, 2026-10-20)

Each item was found by a cross-document reviewer and confirmed by a skeptical second reviewer. Some items repeat from two boundaries; apply once. Lead decisions in the brief override the fix text where they differ.

## 1. [minor] 0010 says interrupted creates are compensated before reconciliation; 0007 and 0020 compensate after the daemon is ready

- Boundary: create-path
- Evidence and reasoning: 0010:338: "Untuk create fitur 20 yang dikompensasi penuh, baris instance sudah dihapus kompensasi sebelum rekonsiliasi". 0007:470 gives the slot order as recover, reconciliation, ready, `start()`. 0007:484 has `start()` open the dispatcher that runs automatic compensation, and 0007 AC-10 says "setelah daemon siap dikompensasi". 0020 AC-11 agrees: "setelah daemon siap". Reconciliation therefore always sees the `initializing` row of an interrupted F20 create first and commits `init_failed { interrupted }` before `instance_registration` deletes it. A test written from 0010:338 would assert the wrong order. Behavior still converges, because `DeleteInstanceCreatedBy` reads the current revision and `failed` is deletable.
- Fix: Reword 0010:338 to: "Untuk create fitur 20, kompensasi berjalan setelah daemon siap (spec 0007), jadi rekonsiliasi lebih dulu menerapkan baris `initializing` (`init_failed { interrupted }`) atau membiarkan baris `uninitialized`, lalu `instance_registration` menghapusnya kecuali `instance.lock` masih dipegang."

## 3. [minor] No ordering between the `Stdin::Text` plan variant (0019 step 2) and its executor arm (0010 step 7) on an exhaustive enum

- Boundary: providers-connection
- Evidence and reasoning: Confirmed. The variant comes from 0019 step 2 (0009:82, 0019:534). On main, crates/core/src/provider/plan.rs:274 has only `Null` and `Secret`. 0009:510 and 0010:230 and :646 say F10 step 7 builds the `Stdin::Text` arm. The F10 milestone 2 prerequisites (0010:603, 01-foundation.md:199) do not include 0019 step 2, and 0019 step 2 (:551) needs only feature 9 and says nothing about the executor arm. 0019 step 5 and scope 02:99 assume F10 step 7 already has the arm. Nothing orders the two steps, and no "whichever merges second" rule exists for them the way K7 has one for the launch checks. If F10 step 7 merges first, it cannot build the arm it is assigned. Both are in stackly-core, so the compiler forces whoever adds the variant to add the arm, and 0010:230 describes that arm exactly. Nothing incompatible gets built, so this is minor.
- Fix: Add to the 0010 step 7 bullet (:646): "Arm `Stdin::Text` (`StdinSource::Bytes(SecretValue::new(text))`, kegagalan `init_step_failed`) ditambah oleh yang di merge belakangan di antara langkah ini dan langkah 2 spec 0019 (varian plan nya milik langkah 2 spec 0019)." Mirror the rule in 0019 step 2 and 0009:510.

## 4. [minor] Probe detail: 0019 redacts before truncating, while 0010 and 0023 truncate (format) before the runner redacts

- Boundary: providers-connection
- Evidence and reasoning: Partly confirmed. For `exec`, 0010:293 says the detail "mengikuti format spec 0019", and 0019:338 says explicitly to redact, then cut to 256. 0010 adds that the runner redacts "sebelum menjadi ObservationDetail", which does not contradict that order. So the claimed exec leak comes from reading the ambiguous 0010 sentence on its own. The real drift is in the signatures. 0023:152 and :180 have `Exchange` return `NativeProbeFailure { detail: ObservationDetail }`, already capped at 256 characters with 64-character values, and the runner then redacts it. 0010 says an `ObservationDetail` exists only after redaction. A runner that redacts an already-capped detail can also grow it past 256 characters when a replacement is longer than the secret it replaces. The NATS probe carries no secret in this feature, so the practical impact is low.
- Fix: In 0010 "Hasil runner" (:293), state the order once: "runner menyamarkan teks mentah (baris stderr pertama atau detail native) lewat `Redactor`, lalu memotong 256 karakter, lalu membuat `ObservationDetail`". In 0023 :152 and :180, make `NativeProbeFailure.detail` a `String` that the runner redacts and caps.

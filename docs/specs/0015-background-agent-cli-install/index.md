# 0015. Background agent dan instalasi CLI

**Date**: 2026-10-19 (update 2026-10-21: hasil spike AC-21; update 2026-10-22: file CLI di bundle bernama `stackly-cli`; update 2026-10-22: usulan dari update spec 0013 dan 0068 diterapkan; update 2026-10-22: usulan spec 0016 untuk pengumuman aksi agent, `not_found`, dan akhir penantian daemon diterapkan, dibangun langkah susulan 12a)
**Status**: In Progress

## Summary

Spec ini memutuskan cara `stacklyd` dan `stackly` ikut di dalam `Stackly.app` dan cara daemon berjalan sendiri di latar sebagai LaunchAgent per user yang didaftarkan lewat `SMAppService` (API Apple untuk mendaftarkan helper dan login item), dengan persetujuan pengguna di System Settings. GUI dan CLI sama sama membaca status pendaftaran itu, menampilkannya sebagai enam state yang jujur (termasuk `requires_approval`, `disabled`, dan `not_registered`), dan hanya mengubah pendaftaran saat pengguna menekan tombol atau menjalankan perintah; start, stop, dan restart tidak pernah menjalankan proses lain, karena stop dan restart lewat IPC dan start lewat daftar ulang `SMAppService` (restart memakai daftar ulang yang sama sebagai cadangan kalau launchd tidak menyalakan daemon lagi). CLI dipasang sebagai symlink yang dikelola di `~/.local/bin`, tanpa admin dan tanpa mengubah PATH atau file shell. Semua yang butuh signing identity nyata, pendaftaran `SMAppService` nyata, dan penolakan izin sungguhan di System Settings dikumpulkan di milestone 4 dan tercatat `BLOCKED` sampai identity ada (OQ-012); langkah yang mendaftarkan agent di Mac ini, mengubah Login Items, atau memakai akun macOS kedua hanya berjalan setelah persetujuan kamu, tidak pernah tanpa diawasi. Sisanya dibangun dan diuji tanpa pengawasan dengan fake, CLI, dan fixture GUI.

Spike AC-21 (2026-10-20) membantah empat asumsi, dan update 2026-10-21 menyesuaikan spec ini: bundle yang belum pernah didaftarkan dibaca sebagai `not_registered` (bukan `not_found`), CLI menemukan bundle lewat path canonical nya sendiri sehingga `~/.local/bin/stackly` bekerja, build ad hoc menampilkan `enabled` walau switch Login Items dimatikan (di run spike, macOS mengabaikan switch itu untuk build ad hoc), dan `stackly daemon restart` memakai `relaunch` sebagai cadangan saat launchd tidak menyalakan binary yang sudah diganti. Alasannya ada di [rationale.md](rationale.md), bagian *Update 2026-10-21*. Update 2026-10-22: file CLI di `Contents/MacOS` bernama `stackly-cli`, karena `Stackly` dan `stackly` adalah satu file di APFS yang tidak membedakan huruf besar kecil (format default Mac); perintahnya tetap `stackly` (bagian *Update 2026-10-22 (nama file CLI di bundle)* di rationale).

## Requirements

**User stories**:

- Sebagai pengguna Mac, saya ingin daemon Stackly berjalan di latar sejak login dan tetap jalan saat jendela ditutup, dengan izin yang saya berikan lewat mekanisme macOS sendiri, supaya instance saya tetap diawasi tanpa saya membuka aplikasi.
- Sebagai pengguna yang menolak atau mematikan izin itu, saya ingin GUI dan `stackly daemon status` menyebut keadaannya dengan jujur beserta langkah pemulihannya, dan tidak ada yang mengubah setting itu diam diam, supaya saya tetap memegang keputusan.
- Sebagai pengguna Terminal, saya ingin `stackly daemon install`, `start`, `stop`, dan `restart` dengan `--json` dan exit code yang stabil, plus completion shell dan man page, supaya automation saya bisa mengendalikan daemon tanpa GUI.
- Sebagai pengguna yang memasang CLI dari aplikasi, saya ingin satu tombol yang membuat command `stackly` tersedia tanpa password admin dan tanpa file shell saya diubah, supaya tidak ada yang berubah di luar yang saya setujui.
- Sebagai release owner, saya ingin bundling, signing development, dan registrasi helper terbukti sejak fase ini dengan bukti yang jelas, termasuk apa yang masih `BLOCKED`, supaya masalah packaging tidak baru ketahuan saat rilis (RISK-10).

**Acceptance criteria** (ID lokal spec ini; ID PRD selalu tiga digit, misalnya AC-014):

- **AC-1**: `cargo xtask build-app` (Debug dan `--release`) menghasilkan `Stackly.app` dengan isi persis seperti tabel *Isi bundle*: `Contents/MacOS/Stackly`, `Contents/MacOS/stacklyd`, dan `Contents/MacOS/stackly-cli` (ketiganya mode 0755, arm64), plist LaunchAgent di `Contents/Library/LaunchAgents/com.ojiepermana.stackly.daemon.plist` yang byte nya sama dengan golden file dan lolos `plutil -lint`, man page di `Contents/Resources/man/man1/`, dan catalog dari fitur 17 di `Contents/Resources/catalog/` (bagian catalog, termasuk build yang berhenti saat langkah catalog gagal, dibuktikan milestone 4 spec 0017). Bundle tidak memuat `stackly-fake-server` atau path apa pun dengan segmen `testing` di bawah `Contents/Resources/catalog/`. `CFBundleShortVersionString` app sama dengan versi workspace yang dicetak `stacklyd --version` dan `stackly-cli --version`. Langkah mana pun yang gagal menghentikan build dengan exit bukan 0 sebelum signing, tanpa bundle setengah jadi di path keluaran. Identifier di tabel *Identifier sementara* ada di satu modul Rust dan satu file Swift, dan keduanya lolos fixture `protocols/fixtures/bundle/identifiers.json` (OQ-001, OQ-006, PRD bagian 25).
- **AC-2**: Signing berjalan dari dalam ke luar setelah assembly: setiap Mach-O lain di `Contents/MacOS` dan `Contents/Frameworks` kalau ada, lalu `stacklyd` dengan identifier `com.ojiepermana.stackly.daemon`, `stackly-cli` dengan `com.ojiepermana.stackly.cli`, lalu app, semuanya dengan hardened runtime (`--options runtime`) dan tanpa entitlement. Identity diambil dari `--identity`, lalu `STACKLY_SIGN_IDENTITY`, lalu ad hoc (`-`) sebagai default. Dengan signing ad hoc, `codesign --verify --strict --deep` lulus untuk app, dan xtask mencetak per binary identifier, `ad hoc`, dan designated requirement. AC ini bisa dibuktikan sekarang tanpa identity (RISK-10).
- **AC-3**: `stackly-platform` punya trait `BackgroundAgent` (`status`, `register`, `unregister`, `relaunch`) beserta tipenya, port lewat `Platform::with_background_agent` dengan default `UnsupportedBackgroundAgent`, dan `stackly-testkit` punya `FakeBackgroundAgent` yang dipasang `FakePlatform`. `MacosPlatform::new` dan `MacosPlatform::with_roots` memasang `MacosBackgroundAgent` dan melaporkan capability `background_agent` supported; `UnsupportedPlatform` melaporkannya not supported. `cargo xtask check-deps` gagal kalau `objc2`, `objc2-foundation`, atau `objc2-service-management` menjadi dependency langsung crate selain `stackly-platform-macos`, atau `clap_complete` dan `clap_mangen` selain `stackly-cli` (NFR-010).
- **AC-4**: Satu fungsi murni `classify` di `stackly-platform` dan satu padanannya di `StacklyUI` memetakan hasil probe ke `BackgroundAgentState` (`enabled`, `requires_approval`, `disabled`, `not_registered`, `not_found`, `unavailable`), alasan `unavailable`, dan langkah pemulihan, persis seperti tabel *State background agent*, dan keduanya lolos semua baris `protocols/fixtures/agent/states.json`. `disabled` hanya muncul untuk `requiresApproval` yang punya launch record dan bukan hasil pendaftaran di aksi yang sama. `notFound` menjadi `not_registered` dengan langkah `register`, karena bundle yang belum pernah didaftarkan membaca `notFound`; hanya `notFound` hasil pendaftaran di aksi yang sama yang menjadi `not_found` *(diubah 2026-10-21, spike AC-21 B1)*. `STACKLY_ROOT` yang aktif selalu menghasilkan `unavailable` alasan `root_override` tanpa satu panggilan pun ke OS (REQ-014, PRD bagian 25).
- **AC-5**: `stacklyd` menentukan konteks launch sekali di `main`: `launchd` kalau dan hanya kalau parent PID 1 dan `XPC_SERVICE_NAME` sama dengan `com.ojiepermana.stackly.daemon` atau diawali `dev.stackly.test.agent.`, selain itu `manual`. `DaemonInfo.launch` membawa konteks, label, dan path bundle (null di luar bundle). Hanya daemon berkonteks `launchd` dengan label produksi dan tanpa `STACKLY_ROOT` yang menulis launch record `<data>/background-agent.json` secara atomik setelah lock didapat; tulis yang gagal hanya menjadi satu warning log dan tidak menghentikan start.
- **AC-6**: Method baru `daemon.shutdown { mode }` (ditandai `recovery allowed`) membalas `ShutdownAccepted` lalu menjalankan urutan berhenti spec 0006 dengan reason `requested` (nilai yang sudah ada di `ShutdownReason`) untuk `stop` atau `restart_requested` (nilai baru) untuk `restart`. `stop` keluar 0. `restart` keluar 75 dan hanya diterima daemon berkonteks `launchd`; daemon `manual` menjawab `daemon.restart_unavailable` (kategori `unsupported`) tanpa berhenti. Request kedua selama berhenti mendapat `daemon.shutting_down`. Event `daemon.shutting_down` membawa reason itu. `ProtocolVersion::CURRENT` naik satu minor dan fixture baru lolos di Rust dan Swift (REQ-028, REQ-047).
- **AC-7**: `stackly daemon status` selalu menampilkan blok agent (state, alasan, langkah pemulihan, label, path bundle, waktu launch terakhir dari launch record), juga saat daemon tidak terjangkau, dengan baris teks `Next` dari tabel *Langkah pemulihan CLI* kalau state nya butuh tindakan. Dengan `--json`, `result` adalah `{ info: DaemonInfo | null, health: DaemonHealth | null, client: {...} | null, agent: AgentReport }`; saat daemon tidak jalan, `result` terisi bersama `error` (`ipc.endpoint_missing` atau `ipc.connection_refused`) dan exit tetap 6. Perubahan tipe ini menaikkan `CLI_SCHEMA_VERSION` menjadi 2 di commit yang sama, dengan golden file dan contoh diperbarui (aturan stabilitas spec 0008). Daemon yang berjalan dari copy app lain menambah warning `cli.agent_bundle_mismatch` (REQ-028, REQ-014).
- **AC-8**: `stackly daemon install` hanya memanggil `register` kalau state `not_registered`. State `enabled` tidak memanggil OS dan keluar 0. `requires_approval` dan `disabled` gagal dengan `cli.agent_requires_approval` atau `cli.agent_disabled` (exit 4) tanpa memanggil `register`, sehingga izin tidak pernah dibuka diam diam. Hasil `register` dipetakan lewat tabel *Hasil pendaftaran*: `enabled` menunggu daemon paling lama 30 detik lalu keluar 0 (dengan warning `cli.daemon_not_running` kalau daemon belum menjawab), `requiresApproval` gagal exit 4, dan setiap kode error `SMAppService` yang dikenal mendapat kode dan exit nya sendiri. `STACKLY_ROOT` aktif gagal `cli.agent_root_override` (exit 2). Bundle CLI ditentukan dari path canonical `current_exe` (symlink sudah diselesaikan), sehingga `~/.local/bin/stackly` bekerja persis seperti `Contents/MacOS/stackly-cli` di dalam bundle; CLI yang path canonical nya tidak berada di `Contents/MacOS` sebuah bundle dengan identifier `com.ojiepermana.stackly` gagal `cli.agent_not_bundled` (exit 5) dengan hint `use_bundled_cli` *(diubah 2026-10-21, spike AC-21 B2)*. Setiap kegagalan menulis hint dari tabel *Langkah pemulihan CLI* dan, dengan `--json`, hasil parsial `{ agent, info: null }` bersama `error` (REQ-028, REQ-014).
- **AC-9**: `stackly daemon start` keluar 0 tanpa memanggil OS kalau daemon sudah menjawab handshake. Kalau socket tidak ada atau ditolak dan state `enabled`: bila `lastLaunchedAt` di launch record kurang dari 15 detik yang lalu, CLI lebih dulu menunggu socket paling lama 15 detik tanpa mengubah apa pun; kalau daemon tetap tidak ada, CLI memanggil `relaunch`, menunggu handshake dengan `serverInstanceId` apa pun paling lama 30 detik, lalu keluar 0, atau gagal `cli.daemon_wait_timeout` (exit 8). State lain gagal tanpa mengubah pendaftaran: `not_registered` dengan `cli.agent_not_registered` (exit 6, hint `stackly daemon install`), `requires_approval` dan `disabled` exit 4, `not_found` exit 6, `unavailable` dengan kode alasannya. Error koneksi lain (endpoint tidak dipercaya, major berbeda) dilaporkan apa adanya tanpa daftar ulang. Kegagalan memberi hasil parsial `{ alreadyRunning: false, agent, info: null }` (REQ-028, BR-011).
- **AC-10**: `stackly daemon stop` mengirim `daemon.shutdown { mode: stop }` ke daemon root aktif (konteks apa pun), lalu menunggu EOF di koneksi yang mengirim request itu (daemon menutup koneksi tepat sebelum melepas lock) dan memastikan socket sudah hilang, paling lama 20 detik total, lalu keluar 0; lewat batas itu `cli.daemon_wait_timeout` (exit 8). Jawaban `daemon.shutting_down` dianggap "sudah sedang berhenti" dan penantian yang sama berlanjut. Daemon yang tidak jalan juga keluar 0 dengan `wasRunning: false`. `stackly daemon restart` mengirim `mode: restart` (`daemon.shutting_down` diperlakukan sama), menunggu EOF lalu handshake dengan `serverInstanceId` baru paling lama 30 detik, dan keluar 0. Kalau sampai batas respawn di *Penantian restart* tidak ada handshake baru dan `lastLaunchedAt` di launch record tidak bertambah (launchd tidak menyalakan binary yang sudah diganti), CLI tanpa `STACKLY_ROOT` membaca state agent, memanggil `relaunch` sekali hanya kalau state nya `enabled`, menunggu handshake baru paling lama 30 detik lagi, dan menambah warning `cli.agent_relaunched`; state lain gagal dengan kode state itu tanpa `relaunch` *(diubah 2026-10-21, spike AC-21 B4)*. Daemon `manual` gagal `daemon.restart_unavailable` (exit 5) tanpa berhenti; daemon yang tidak jalan diperlakukan seperti `start`. Daemon lama yang tidak mengenal method itu menghasilkan exit 5 dengan hint update. Ctrl+C selama menunggu keluar 130 lewat `cli.interrupted` dan tidak membatalkan apa pun. Kegagalan memberi hasil parsial dengan `info` null (REQ-028).
- **AC-11**: Pendaftaran tidak pernah berubah tanpa aksi pengguna. Di Rust, `register` hanya dipanggil dari `daemon install` dan `relaunch` hanya dari `daemon start`, `restart` untuk daemon yang tidak jalan, dan `restart` yang tidak melihat daemon baru sampai batas respawn *(diubah 2026-10-21, spike AC-21 B4)*; test dengan `FakeBackgroundAgent` membuktikan `daemon status`, `stop`, `restart` untuk daemon yang jalan selama daemon baru muncul sebelum batas respawn, setiap hint error, dan setiap command lain paling banyak memanggil `status`. Di Swift, `register` hanya dipanggil dari tombol Turn On dan `relaunch` hanya dari Start stacklyd, dan test model membuktikan refresh, aktivasi app, dan polling hanya memanggil `status`; test aturan sumber membatasi `import ServiceManagement` ke satu file (REQ-014, AC-014).
- **AC-12**: `stackly completion <bash|zsh|fish>` mencetak script completion dari definisi clap ke stdout (dengan `--json`, `result` `{ shell, script }`). Perintah tersembunyi `stackly manpage` mencetak semua halaman man dari `clap_mangen` (`--json` memberi `{ pages: [{ file, roff }] }`), dan `build-app` menulis halaman itu ke bundle. Hint lama `start it with stacklyd` di CLI diganti hint dari tabel *Langkah pemulihan CLI*, dan test memastikan teks lama tidak ada lagi di `apps/cli` (REQ-028).
- **AC-13**: Saat presence GUI `unreachable` dengan kode `ipc.endpoint_missing` atau `ipc.connection_refused`, banner jendela, teks `ConnectionHint`, dan seksi Diagnostics *Background Agent* mengikuti tabel *Banner per state* untuk setiap state, termasuk ambang 15 detik sejak `since` sebelum aksi Start stacklyd muncul untuk state `enabled`. Turn On memanggil `register`; hasil `requiresApproval` membuka Login Items sekali. Start stacklyd memanggil `relaunch` dan, kalau daemon belum menjawab dalam 30 detik, menampilkan `AgentActionError.daemonDidNotStart(seconds: 30)` di Last error *(diselaraskan 2026-10-21 dengan bagian GUI; sebelumnya `.timedOut`)*. Open Login Items memanggil `SMAppService.openSystemSettingsLoginItems()`. Status dibaca ulang saat app aktif kembali, setiap 5 detik selama tidak terjangkau dan app aktif, dan setelah setiap aksi. Petunjuk `Start it with stacklyd` (`// provisional: F15`) hilang. Setiap aksi bisa dijalankan dengan keyboard, punya label VoiceOver, dan perubahan state diumumkan lewat `announce(_:)`. Tiga aturan berikut berlaku di presence apa pun, tidak hanya saat `unreachable` dengan kedua kode itu *(ditambah 2026-10-22, usulan spec 0016)*: perubahan state ke `not_found` diumumkan juga saat banner jendela tidak menampilkan baris agent (misalnya Turn On di Diagnostics saat daemon tersambung); setiap kali Last error terisi (Turn On, Start stacklyd, atau penantian daemon yang berakhir dengan `daemonDidNotStart`), teks Last error itu diumumkan sekali; dan penantian daemon setelah Turn On, Start stacklyd, atau state yang menjadi `enabled` berakhir tanpa Last error begitu status yang dibaca menjadi `requires_approval`, `disabled`, `not_registered`, atau `not_found`, jadi aksi baris itu langsung bisa dipakai. Tampilan lolos cek teks besar spec 0012 (preview di lebar sempit 640 pt, karena text style macOS 27 tidak ikut `dynamicTypeSize`) dan kontras spec 0012 (REQ-014, REQ-027, PRD bagian 25).
- **AC-14**: Instalasi CLI hanya membuat symlink `~/.local/bin/stackly` dan symlink man page `~/.local/share/man/man1/stackly*.1` ke file di bundle yang sedang berjalan (untuk CLI: `Contents/MacOS/stackly-cli`), setelah konfirmasi eksplisit, dan hanya membuat folder `~/.local/bin` dan `~/.local/share/man/man1` bila belum ada. Ia tidak pernah menulis file shell (`.zshrc`, `.zprofile`, `.bash_profile`, `config.fish`), `/etc/paths.d`, atau `/usr/local/bin`, dan tidak pernah meminta hak admin. Path yang sudah berisi file atau symlink yang bukan link terkelola dilaporkan `conflict` dan tidak disentuh. Status `installed`, `stale`, `broken`, `conflict`, dan `not_installed` mengikuti aturan *Instalasi CLI*, dibuktikan test Swift di home sementara (PRD bagian 25).
- **AC-15**: Di Mac ini, tanpa signing, test native dengan LaunchAgent sementara di domain `gui/<uid>` (plist nya diturunkan dari golden file produksi dengan `Label` dan `BundleProgram` diganti dan `STACKLY_ROOT` ditambah, dan test memastikan semua key lain sama dengan golden file) membuktikan: `DaemonInfo.launch.context` bernilai `launchd`; `daemon.shutdown restart` memunculkan daemon baru (`serverInstanceId` berbeda) dalam 30 detik; `stop` membuat daemon tetap mati minimal 20 detik (lebih dari `ThrottleInterval`); `SIGKILL` ke daemon memunculkan daemon baru dalam 20 detik; dan agent yang start saat daemon manual memegang lock keluar 3 berulang lalu mengambil alih paling lama 20 detik setelah daemon manual berhenti. Semua agent test dicabut di setiap jalur keluar, termasuk lewat `--cleanup`. Test ini menjalankan job launchd sementara di sesi kamu, jadi ia hanya berjalan di run native yang kamu setujui, seperti spike spec 0003 (REQ-014, REQ-028, PRD bagian 32.2, gate G0).
- **AC-16**: Test native yang sama membuktikan proses instance (fake provider) yang berjalan di session sendiri tetap hidup dengan PID dan waktu start yang sama saat job daemon di `launchctl kickstart -k` dan saat di `launchctl bootout`, lalu diadopsi dengan identitas terverifikasi oleh daemon berikutnya, tanpa `AbandonProcessGroup`. Kalau gagal, fitur kembali ke `/architect` untuk keputusan survival (spec 0010 Follow-up) (REQ-013, AC-013).
- **AC-17**: Dengan build yang ditandatangani identity Apple Development nyata dan dipasang di `~/Applications`, record manual `native` (dijalankan setelah persetujuan kamu) membuktikan alur `SMAppService` sungguhan: `not_registered` terlihat di GUI dan CLI; Turn On atau `stackly daemon install` lalu mengikuti salah satu cabang, dan cabang yang terjadi dicatat. Cabang A: hasilnya `enabled` (biasanya dengan notifikasi Background Items Added), daemon jalan dengan konteks `launchd` dan launch record tertulis; izin dimatikan di System Settings dan Diagnostics serta `stackly daemon status` menampilkan `disabled`. Cabang B: hasilnya `requires_approval` tanpa launch record; izin dibiarkan mati dan state tidak berubah sendiri; izin dinyalakan dan daemon jalan dengan konteks `launchd`; izin dimatikan lagi dan state menjadi `disabled`. Cabang C: status tetap `enabled` setelah izin dimatikan, seperti build ad hoc di spike AC-21; hasil itu dicatat, GUI dan CLI tetap menampilkan `enabled`, dan Keputusan 5 (`disabled` dari launch record) kembali ke `/architect` *(ditambah 2026-10-21, spike AC-21 B3)*. Di setiap cabang, perilaku daemon saat izin dimatikan dicatat (kalau macOS menghentikannya, banner `disabled` tampil dan instance tetap hidup); izin dinyalakan lagi dan instance diadopsi; Start stacklyd dan `stackly daemon start` setelah `stop` menyalakan daemon. Kalau macOS meminta persetujuan lagi setelah `relaunch`, GUI dan CLI menampilkan `requires_approval` dengan langkah pemulihan, dan temuan itu membawa cara start kembali ke `/architect`. Selama Mac ini tanpa identity, record ini `BLOCKED` (reason `no code signing identity on this Mac (OQ-012)`, owner `release owner (OQ-012)`) (REQ-014, AC-014, NFR-015, RISK-10, gate G0).
- **AC-18**: Dengan identity yang sama, record manual `native` (setelah persetujuan kamu; `BLOCKED` dengan reason `no code signing identity on this Mac (OQ-012)` dan owner `release owner (OQ-012)` sampai identity ada) membuktikan item login Keychain yang dibuat saat signing ad hoc tetap bisa dipakai setelah helper ditandatangani: aksi pengguna pertama memunculkan satu dialog per item (Always Allow, atau tulis ulang lewat `stackly secret set`), pemicu latar sebelum itu menghasilkan `access_denied` tanpa dialog, dan setelah itu build ulang dengan identity yang sama tidak memunculkan dialog lagi. Keputusan tetap login Keychain (bukan data protection keychain) tercatat di spec 0011 lewat `/sync` (REQ-016, AC-062, spec 0011 Follow-up).
- **AC-19**: Dengan identity yang sama, record manual `native` (setelah persetujuan kamu) membuktikan bagian NFR-015 milik fitur ini di akun macOS baru yang bukan developer: clean install dari `~/Applications`, approval denied, reinstall di path yang sama, upgrade (bundle diganti saat daemon jalan, lalu `stackly daemon restart` menjalankan versi baru, terlihat dari `DaemonInfo.version`), dan login ulang yang menyalakan daemon lewat `RunAtLoad`. Untuk reinstall dan upgrade, state agent sesudahnya dicatat, dan untuk upgrade juga apakah `restart` butuh `relaunch` (warning `cli.agent_relaunched`) *(ditambah 2026-10-21, spike AC-21 B4)*; kalau macOS meminta persetujuan lagi, GUI dan CLI menampilkan `requires_approval` dengan langkah pemulihan. Record ini punya dua prasyarat yang masing masing tercatat sendiri saat belum ada: identity nyata (`BLOCKED`, owner `release owner (OQ-012)`) dan akun macOS kedua yang dibuat pengguna dengan hak admin (`BLOCKED`, reason `no second macOS user account on this Mac`, owner `user`). Uninstall dengan data tetap milik fitur 62 (NFR-015, REQ-014, PRD bagian 32.2).
- **AC-20**: Dengan identity Apple Development nyata, `cargo xtask build-app --release --identity <identity>` menghasilkan bundle yang `codesign -dv` nya menampilkan `TeamIdentifier` yang sama di app, `stacklyd`, dan `stackly-cli`, designated requirement yang tidak memuat `cdhash`, dan `codesign --verify --strict --deep` lulus. Bukti ini `native` manual dan tercatat `BLOCKED` (reason `no code signing identity on this Mac (OQ-012)`, owner `release owner (OQ-012)`) sampai identity ada (OQ-012, RISK-10, gate G0).
- **AC-21**: Sebelum langkah CLI dan GUI milestone 1 dan 3 dibangun, spike manual ad hoc (setelah persetujuan kamu, karena ia mendaftarkan agent sungguhan di Mac ini) menjawab dan mencatat di rationale dengan record manual `native`: apakah build ad hoc bisa didaftarkan dan status yang dihasilkan; status dari tool di `Contents/MacOS` dan lewat symlink di luar bundle; apakah `unregister` lalu `register` menyalakan job tanpa persetujuan baru; apakah `XPC_SERVICE_NAME` sama dengan label; status setelah izin dimatikan; dan apakah `unregister` menghentikan job yang sedang jalan. Hasil yang membantah asumsi spec ini membawa bagian terkait kembali ke `/architect` sebelum langkah 5 dan 6. Hasil "ad hoc ditolak" adalah hasil yang sah dan dicatat, bukan kegagalan build (REQ-014, RISK-10, gate G0).
- **AC-22**: `cargo xtask build-app --install [<dir>]` (default `~/Applications`) menolak `<dir>/Stackly.app` yang `CFBundleIdentifier` nya bukan `com.ojiepermana.stackly` tanpa menyentuhnya, mengganti bundle Stackly yang ada lewat staging dan rename sehingga `<dir>/Stackly.app` tidak pernah setengah jadi, tidak meninggalkan folder `.Stackly.app.*` setelah berhasil, dan mencetak hint `stackly daemon restart` kalau socket daemon root default ada. Diuji dengan folder tujuan sementara, tanpa mendaftarkan apa pun (PRD bagian 25, NFR-015).

## Decision

**Chosen option**: pilihan yang direkomendasikan di setiap keputusan di [rationale.md](rationale.md): `SMAppService.agent` dengan LaunchAgent di dalam bundle, ketiga binary di `Contents/MacOS`, stop dan restart lewat IPC dengan `KeepAlive` yang hanya menyalakan ulang saat exit gagal, start lewat `relaunch` (daftar ulang `SMAppService`), yang juga menjadi cadangan restart kalau launchd tidak menyalakan binary yang sudah diganti (update 2026-10-21) di belakang port `BackgroundAgent` yang dipanggil CLI (objc2) dan padanan Swift di GUI, `disabled` diturunkan dari launch record, assembly dan signing satu pintu di `cargo xtask build-app`, CLI lewat symlink terkelola di `~/.local/bin`, tetap login Keychain, dan verifikasi tanda tangan peer ditunda ke fitur 60 dan 63.

Pendaftaran helper selalu lewat mekanisme macOS dan hanya berubah saat pengguna bertindak, sedangkan kendali harian daemon lewat IPC yang sudah ada, sehingga tidak ada satu pun bagian Stackly yang menjalankan `launchctl` atau proses lain di produk.

**Implementation skills**: `rust-best-practices` (`apollographql/skills`, `.claude/skills/rust-best-practices/`) · `rust-async-patterns` (`wshobson/agents`, `.claude/skills/rust-async-patterns/`) · `signing-entitlements` (`openai/plugins`, `.claude/skills/signing-entitlements/`) · `swiftui-expert-skill` (`avdlee/swiftui-agent-skill`, `.claude/skills/swiftui-expert-skill/`) · `swift-concurrency` (`avdlee/swift-concurrency-agent-skill`, `.claude/skills/swift-concurrency/`) · `swift-testing-pro` (`twostraws/swift-testing-agent-skill`, `.claude/skills/swift-testing-pro/`)

Kalau isi skill bertentangan dengan spec ini, spec yang menang. `signing-entitlements` dipakai untuk memeriksa hasil `codesign` dan Gatekeeper saat milestone 1 dan 4, bukan untuk memilih entitlement (spec ini tidak memakai entitlement).

### Isi bundle

```text
Stackly.app/Contents/
├── Info.plist                         # dari Xcode; CFBundleShortVersionString = versi workspace
├── MacOS/
│   ├── Stackly                        # app SwiftUI
│   ├── stacklyd                       # daemon, BundleProgram LaunchAgent
│   └── stackly-cli                    # CLI, target symlink ~/.local/bin/stackly
├── Library/LaunchAgents/
│   └── com.ojiepermana.stackly.daemon.plist
└── Resources/
    ├── catalog/                       # fitur 17, tanpa namespace testing/
    └── man/man1/stackly*.1            # dari stackly manpage
```

- Nama file CLI di bundle adalah `stackly-cli`, bukan `stackly`: APFS yang tidak membedakan huruf besar kecil (format default Mac) menganggap `Stackly` dan `stackly` satu file, sehingga CLI akan menimpa executable app. Ketiga nama di `Contents/MacOS` harus berbeda tanpa melihat huruf besar kecil, dan `cargo xtask build-app` menolak mulai kalau tidak *(2026-10-22)*. Perintah yang dilihat pengguna tetap `stackly`: clap memakai nama `stackly` yang ditulis eksplisit (help, usage, pesan error, completion, dan man page), dan symlink terkelola bernama `~/.local/bin/stackly`. Identifier code signing tetap `com.ojiepermana.stackly.cli`.
- `stacklyd` dan `stackly-cli` adalah Mach-O polos tanpa Info.plist sendiri. Info.plist app tidak memakai `LSFileQuarantineEnabled`, dan tidak ada kode yang memanggil API quarantine (fitur 18 bergantung pada ini).
- `AppBundle::enclosing(exe: &Path) -> Option<AppBundle>` (murni, di `stackly-platform::bundle`) menerima path canonical dan mengembalikan bundle hanya kalau bentuknya persis `<X>.app/Contents/MacOS/<file>` (akhiran `.app` dibandingkan tanpa peduli huruf besar). `AppBundle` memberi `root()`, `contents_dir()`, `macos_dir()`, `resources_dir()`, `launch_agents_dir()`, `daemon_executable()`, `cli_executable()`, dan `daemon_plist()`. Fitur 17 menurunkan folder catalog dari `resources_dir().join("catalog")`.
- Bin membaca `std::env::current_exe()` sekali di `main`, membuatnya canonical, lalu memanggil `AppBundle::enclosing`. Library tidak pernah memanggil `current_exe`.

### Plist LaunchAgent

Dirender `xtask` dari konstanta di atas (tidak ditulis tangan), diuji terhadap golden file `xtask/tests/golden/com.ojiepermana.stackly.daemon.plist`, dan dicek `plutil -lint` saat build.

| Key | Nilai | Alasan singkat |
| --- | --- | --- |
| `Label` | `com.ojiepermana.stackly.daemon` | identitas job di launchd |
| `BundleProgram` | `Contents/MacOS/stacklyd` | path relatif bundle, hanya untuk plist yang didaftarkan `SMAppService` |
| `AssociatedBundleIdentifiers` | `[com.ojiepermana.stackly]` | Login Items menampilkan Stackly, bukan nama binary |

### Build, assembly, dan signing

`cargo xtask build-app [--release] [--identity <identity>] [--install [<dir>]]` adalah satu satunya perakit bundle yang lengkap:

0. Hapus folder `target/app/.stage-*` sisa build sebelumnya (hanya di dalam `target/app`).
1. `cargo build --locked --message-format=json -p stacklyd -p stackly-cli` (dengan `--release` untuk `--release`, tanpa `--target`, jadi target host `aarch64-apple-darwin`); path kedua executable diambil dari pesan `compiler-artifact` di output JSON, bukan ditebak.
2. `xcodebuild` seperti sekarang ditambah `CODE_SIGNING_ALLOWED=NO`, `ENABLE_DEBUG_DYLIB=NO` (supaya build Debug tidak menaruh `Stackly.debug.dylib` dan `__preview.dylib` di `Contents/MacOS`), dan `MARKETING_VERSION=<versi workspace>`; hasilnya di `target/xcode/Build/Products/<Config>/Stackly.app` adalah bahan mentah tanpa signature, lalu disalin dengan `ditto` ke staging `target/app/.stage-<pid>/Stackly.app`.
3. Assembly di staging: salin kedua binary (mode 0755), tulis plist, lalu jalankan `stackly manpage --json` dari binary yang baru dibangun dan tulis setiap halaman ke `Contents/Resources/man/man1/`. Langkah assembly adalah daftar berurutan di `xtask/src/build_app/assemble.rs`. Spec ini menyediakan slot langkah catalog di daftar itu (setelah plist, sebelum man page) tanpa isi; milestone 4 langkah 11 spec 0017 mengisinya dengan panggilan `xtask::catalog::build` di dalam proses dengan `--out <bundle>/Contents/Resources/catalog`, beserta test bahwa langkah catalog yang gagal menghentikan build tanpa bundle di path keluaran. Sebelum itu masuk, folder catalog tidak ada dan daemon melaporkan catalog tidak tersedia (spec 0017).
4. Cek isi: `Contents/MacOS` hanya berisi `Stackly`, `stacklyd`, dan `stackly-cli` (ketiga nama berbeda tanpa melihat huruf besar kecil, dicek juga sebelum langkah 1 supaya build gagal cepat); tidak ada `stackly-fake-server`; tidak ada segmen `testing` di bawah `Resources/catalog`; mode dan arsitektur ketiga binary (`lipo -archs` sama dengan `arm64`).
5. Signing dari dalam ke luar: setiap Mach-O di `Contents/Frameworks` kalau ada (package Swift lokal biasanya terhubung statis, jadi folder itu kosong), lalu `codesign --force --sign <identity> --options runtime --timestamp=none --identifier <id> <file>` untuk `stacklyd` lalu `stackly-cli`, lalu `codesign --force --sign <identity> --options runtime --timestamp=none <bundle>`. Tanpa entitlement. Identity dari `--identity`, lalu `STACKLY_SIGN_IDENTITY`, lalu `-`.
6. Verifikasi: `codesign --verify --strict --deep <bundle>`, lalu cetak per binary identifier, Team ID (`ad hoc` kalau tidak ada), dan designated requirement (`codesign -d -r-`).
7. Ganti `target/app/<Config>/Stackly.app` dengan staging lewat rename (bundle lama dipindah ke samping lalu dihapus), sehingga path keluaran tidak pernah berisi bundle setengah jadi. Kegagalan di langkah mana pun menghapus staging dan keluar bukan 0. xtask mencetak path keluaran ini, bukan path produk Xcode.
8. `--install [<dir>]` (default `~/Applications`): tolak kalau `<dir>/Stackly.app` ada dan `CFBundleIdentifier` nya bukan `com.ojiepermana.stackly`; salin dengan `ditto` ke `<dir>/.Stackly.app.staging-<pid>`, pindahkan bundle lama ke `<dir>/.Stackly.app.old-<pid>`, rename staging ke `Stackly.app`, hapus bundle lama. Setelah itu xtask mencetak `run stackly daemon restart to use the new stacklyd` kalau socket daemon root default ada.

Build dari Xcode IDE (Run di Xcode) tetap ditandatangani ad hoc oleh Xcode dan tidak memuat helper, plist, catalog, atau man page. GUI menampilkan state `unavailable` alasan `helper_missing` untuk build itu.

Signing tidak pernah memakai `--deep` (hanya verifikasi yang memakainya), tidak pernah meminta password, dan tidak pernah menulis ke Keychain. Developer ID, timestamp aman, dan notarization milik fitur 60.

### Port `BackgroundAgent` (ditambah ke spec 0004)

```rust
// stackly-platform, modul `agent`
pub trait BackgroundAgent: Send + Sync {
    /// Reads the registration state from the OS. Never prompts and never changes it.
    fn status(&self) -> Result<AgentProbe, BackgroundAgentError>;
    /// Registers the agent; the result may need the user's approval.
    fn register(&self) -> Result<AgentProbe, BackgroundAgentError>;
    /// Unregisters the agent; launchd stops launching it.
    fn unregister(&self) -> Result<AgentProbe, BackgroundAgentError>;
    /// Asks the OS to start the registered job now. On macOS: unregister, then register.
    fn relaunch(&self) -> Result<AgentProbe, BackgroundAgentError>;
}
```

- `AgentProbe` (`#[non_exhaustive]`): `Registration { registration: AgentRegistration, bundle: PathBuf }` (`bundle` adalah root `AppBundle` canonical yang adapter terima dari CLI, bukan `NSBundle.mainBundle`), `NotBundled { executable: PathBuf }`, `HelperMissing { bundle: PathBuf }`. `AgentRegistration`: `Enabled`, `RequiresApproval`, `NotRegistered` (hanya setelah `unregister`), `NotFound` (bundle yang belum pernah didaftarkan, atau OS tidak menemukan service nya), `Unrecognized(i64)` (nilai status OS yang tidak dikenal).
- `BackgroundAgentError` (`#[non_exhaustive]`, thiserror): `NotSupported { capability, os }` dan `Os { op: AgentOp, kind: AgentOsErrorKind, domain: String, code: i64, message: String }`, dengan `AgentOp` `status`, `register`, `unregister`, atau `relaunch`, dan `AgentOsErrorKind` dari tabel *Hasil pendaftaran*.
- `relaunch` adalah satu satunya cara start, dan juga satu satunya cara yang menyalakan binary yang sudah diganti saat terdaftar (spike AC-21 B4: respawn `KeepAlive` gagal dengan last exit 78 sampai daftar ulang). Spike membuktikannya untuk build ad hoc di setiap kasus yang dicoba (job jalan, sudah keluar 0, baru start, lewat symlink, di thread latar, switch Login Items mati), proses baru 0,08 sampai 1,0 detik kemudian tanpa persetujuan baru; build bertanda tangan dibuktikan AC-17. Mekanismenya tetap di adapter, supaya bisa diganti tanpa mengubah CLI atau GUI.
- `Platform::with_background_agent(Arc<dyn BackgroundAgent>)` dan getter `background_agent() -> &dyn BackgroundAgent`, default `UnsupportedBackgroundAgent` yang menjawab `NotSupported { capability: background_agent, os }`.
- `MacosBackgroundAgent` (`stackly-platform-macos::agent`, satu satunya pemakai `objc2-service-management`) *(diubah 2026-10-21, spike AC-21 B2)*: `MacosBackgroundAgent::new(executable: PathBuf)` menerima path executable canonical yang dibaca `main` CLI, dan `MacosBackgroundAgent::unlocated()` (sama dengan `new(PathBuf::new())`) adalah adapter yang tidak tahu executable nya, yang dipasang `MacosPlatform::new` dan `MacosPlatform::with_roots` supaya capability jujur; path kosong tidak pernah cocok dengan `AppBundle::enclosing`, jadi ia menjawab `NotBundled` dengan `executable` kosong untuk setiap method tanpa memanggil OS, dan hanya `stacklyd`, test, dan CLI yang gagal membaca `current_exe` yang memakainya. Setiap method berjalan di dalam `objc2::rc::autoreleasepool` dengan langkah `locate` lebih dulu: `AppBundle::enclosing(executable)`; kalau `None`, `NotBundled { executable }`; kalau `NSBundle::bundleWithPath(root)` tidak ada atau `bundleIdentifier` nya (dibaca dari `Info.plist` bundle itu) bukan `com.ojiepermana.stackly`, `NotBundled { executable }`; kalau plist atau `Contents/MacOS/stacklyd` tidak ada di bundle itu, `HelperMissing { bundle: root }`. Adapter tidak pernah membaca `NSBundle.mainBundle`, karena lewat symlink nilai itu adalah folder symlink tanpa identifier, padahal `SMAppService` sendiri menjawab untuk bundle asli. Setelah `locate`, `SMAppService.agentServiceWithPlistName("com.ojiepermana.stackly.daemon.plist")` lalu `status`, `registerAndReturnError`, `unregisterAndReturnError`, atau keduanya berurutan untuk `relaunch` (error `NotFound` dari langkah `unregister` diabaikan), dan baca `status` lagi sebagai hasil, dengan `Registration.bundle` = root dari `locate`. `NSError` dipetakan lewat tabel *Hasil pendaftaran*. Setiap blok `unsafe` diberi komentar `// SAFETY:`.
- `FakeBackgroundAgent` (testkit): state awal `NotFound` seperti bundle yang belum pernah didaftarkan *(diubah 2026-10-21, spike AC-21 B1; di `main` sekarang `NotRegistered`)*, transisi `unregister` bawaan ke `NotRegistered`, path bundle yang bisa disetel, transisi untuk `register`, `unregister`, dan `relaunch` yang bisa disetel (misalnya `NotFound` menjadi `RequiresApproval`), `fail_next(op, error)`, dan log panggilan berurutan.

**Hasil pendaftaran.** Kode `NSError` di domain `SMAppServiceErrorDomain` dipetakan berdasarkan nama simbol di `ServiceManagement/SMErrors.h` (nilai angkanya diambil dari header SDK saat build dan diuji terhadap konstanta itu, bukan ditulis tangan). Kode di domain lain dan simbol lain menjadi `Other`.

| Hasil | `AgentOsErrorKind` | Perlakuan CLI | Perlakuan GUI |
| --- | --- | --- | --- |
| `kSMErrorAlreadyRegistered` | `AlreadyRegistered` | dianggap berhasil, status dibaca ulang (spike: `register` saat `enabled` berhasil tanpa error dan tanpa menyalakan ulang job, jadi baris ini jarang muncul) | sama |
| `kSMErrorLaunchDeniedByUser` | `LaunchDenied` | state dari `classify` setelah status dibaca ulang (`requires_approval` atau `disabled`), exit 4 | banner state itu |
| `kSMErrorJobMustBeEnabled` | `MustBeEnabled` | sama dengan baris di atas | sama |
| `kSMErrorInvalidSignature` | `InvalidSignature` | `cli.agent_invalid_signature`, exit 4, hint signing nyata | Last error "macOS rejected the signature of this build." |
| `kSMErrorJobNotFound`, `kSMErrorJobPlistNotFound` | `NotFound` | `cli.agent_not_found`, exit 6 | banner `not_found` |
| lainnya | `Other` | `cli.agent_os_error`, exit 7 | Last error dengan domain dan kode |
| berhasil, status sesudahnya `Enabled` | | `install`: tunggu daemon (AC-8); `start` dan cadangan `restart`: tunggu handshake 30 detik | lanjut |
| berhasil, status sesudahnya `RequiresApproval` | | `cli.agent_requires_approval`, exit 4, tanpa menunggu daemon | banner `requires_approval`; Turn On membuka Login Items sekali |
| berhasil, status sesudahnya `NotFound` | | `cli.agent_not_found`, exit 6 | banner `not_found` |
| berhasil, status sesudahnya `NotRegistered` atau `Unrecognized` | | `cli.agent_os_error` dengan `osCode` null, exit 7 | Last error "macOS didn’t keep the registration." |
- Port ini dipanggil `stackly-cli`. `stacklyd` memasangnya lewat `MacosPlatform` hanya supaya capability jujur, dan tidak pernah memanggilnya.

### State background agent

`classify(input: &AgentInput) -> AgentAssessment` (murni, `stackly-platform::agent`), dengan `AgentInput { root_override: bool, probe: ProbeOutcome, launch_record: bool, just_registered: bool }`. `ProbeOutcome` adalah `NotChecked` (hanya saat root override, karena OS tidak dipanggil), `Unsupported`, `Failed { code: Option<i64> }` (error panggilan status dengan kode nya, atau `None` untuk timeout), atau `Probe(AgentProbe)`. `Registration.bundle` selalu bundle canonical CLI itu sendiri, karena adapter menerima path nya dari `main` (lihat *Port `BackgroundAgent`*), jadi CLI tidak mengganti probe apa pun sebelum `classify` *(diubah 2026-10-21, spike AC-21 B2)*. `AgentAssessment { state, reason: Option<UnavailableReason>, recovery: RecoveryStep }`. Baris dievaluasi dari atas, yang pertama cocok menang:

| Kondisi | `state` | `reason` | `recovery` |
| --- | --- | --- | --- |
| `root_override` | `unavailable` | `root_override` | `manual_daemon_for_override` |
| `Unsupported` | `unavailable` | `unsupported_os` | `none` |
| `Failed`, atau `NotChecked` tanpa root override | `unavailable` | `status_failed` | `check_again` |
| `NotBundled` | `unavailable` | `not_bundled` | `use_bundled_cli` |
| `HelperMissing` | `unavailable` | `helper_missing` | `build_with_xtask` |
| `Unrecognized` | `unavailable` | `status_unrecognized` | `check_again` |
| `Enabled` | `enabled` | | `none` |
| `NotRegistered` | `not_registered` | | `register` |
| `NotFound` dan `just_registered` | `not_found` | | `move_or_reinstall_app` |
| `NotFound` dan `!just_registered` | `not_registered` | | `register` |
| `RequiresApproval` dan (`!launch_record` atau `just_registered`) | `requires_approval` | | `approve_in_login_items` |
| `RequiresApproval` dan `launch_record` | `disabled` | | `enable_in_login_items` |

- **`notFound` sebelum pendaftaran** *(2026-10-21, spike AC-21 B1)*: bundle yang belum pernah didaftarkan membaca `notFound` dari setiap path, dan `notRegistered` hanya muncul setelah `unregister`. Karena `HelperMissing` sudah memastikan plist dan `stacklyd` ada sebelum status dibaca, `notFound` di luar aksi pendaftaran berarti "belum didaftarkan untuk identitas bundle ini", dan langkah yang benar adalah `register`. `not_found` hanya dipakai untuk `notFound` yang dibaca tepat setelah `register` atau `relaunch` di aksi yang sama, yang berhasil atau gagal dengan `kSMErrorJobNotFound` atau `kSMErrorJobPlistNotFound` (`AgentOsErrorKind::NotFound`), yaitu saat OS menerima permintaan pendaftaran tetapi tetap tidak menemukan service nya (misalnya app yang dijalankan dari lokasi sementara). Jadi baris `NotFound` di *Hasil pendaftaran* dan state hasil `classify` selalu sama.
- **Build ad hoc dan switch Login Items** *(2026-10-21, spike AC-21 B3)*: di run spike (satu bundle ad hoc di `/private/tmp` dengan identifier test, laporan switch dari kamu dan log OS), macOS mengabaikan switch Login Items (status tetap `enabled`, job tidak dihentikan, dan `relaunch` tetap menyalakannya), sehingga GUI dan CLI akan menampilkan `enabled` walau System Settings menunjukkan mati. Record tambahan ad hoc di milestone 2 mengulanginya dengan bundle di `~/Applications` dan identifier produksi. Itu jawaban jujur dari OS, dan tidak ada kode yang mencoba mendeteksi jenis signature untuk menutupi nya. `requires_approval` dan `disabled` hanya diharapkan untuk build bertanda tangan, dan AC-17 cabang C mencatat kalau build itu juga tidak terpengaruh.
- `classify` tidak tahu apakah daemon terjangkau. Pemanggil yang tahu daemon tidak terjangkau dan mendapat state `enabled` memakai langkah `start` (CLI: hint `stackly daemon start`; GUI: aksi Start stacklyd setelah ambang 15 detik).
- Nilai wire setiap enum ditulis snake_case dan stabil, karena muncul di `--json` CLI. Enum di Swift memakai raw value yang sama.
- `launch_record` berarti file `<data>/background-agent.json` root default ada dan berupa file biasa. Daemon hanya bisa menulisnya setelah launchd menjalankannya, jadi file itu bukti bahwa izin pernah diberikan. `just_registered` true hanya untuk probe yang dibaca di dalam satu aksi pendaftaran setelah `register` atau `relaunch` berhasil, gagal dengan `AlreadyRegistered` (yang dianggap berhasil), atau gagal dengan `AgentOsErrorKind::NotFound`; error lain (misalnya `LaunchDenied`) dibaca ulang dengan `just_registered` false, supaya `classify` tetap bisa memberi `disabled` (CLI `install`, `start`, dan `restart` yang memakai `relaunch`; tombol Turn On dan Start stacklyd di GUI). Di GUI, setiap aksi Turn On atau Start stacklyd menimpa `BackgroundAgentModel.justRegistered` dengan nilai dari hasil nya sendiri (aturan di atas), nilai itu tetap sampai refresh membaca probe yang bukan `requiresApproval` dan bukan `notFound` (lalu menjadi false), dan model baru (app dibuka lagi) selalu mulai dengan false *(diubah 2026-10-21, spike AC-21 B1)*.
- `protocols/fixtures/agent/states.json` *(bentuk ditetapkan 2026-10-21)*: `{ "schema": 1, "rows": [ ... ] }`, setiap baris `{ "name", "rootOverride", "probe", "launchRecord", "justRegistered", "expect": { "state", "reason", "recovery" } }`, dibaca test Rust dan Swift. `probe` adalah `{ "type": "not_checked" | "unsupported" | "failed" | "registration" | "not_bundled" | "helper_missing" }`, ditambah `"code"` (angka atau null) untuk `failed` dan `"registration"` (`enabled`, `requires_approval`, `not_registered`, `not_found`, atau `unrecognized` dengan `"raw"` angka) untuk `registration`; path bundle dan executable tidak ada di fixture, karena `classify` tidak membacanya (test memakai path tetap). `reason` null kecuali `unavailable`; semua nilai snake_case seperti `as_code`. Baris wajib: semua lima nilai `registration` × `launchRecord` × `justRegistered` (20 baris, termasuk keempat baris `not_found` yang dua menjadi `not_registered` dan dua menjadi `not_found`), setiap `type` lain sekali dengan kedua Bool false (`failed` dua kali: dengan kode dan null, total 6 baris), dan `rootOverride` true dengan `not_checked`, `registration` `enabled`, dan `not_bundled` (3 baris).

### Konteks launch dan launch record di daemon

- `LaunchContext::detect(xpc_service_name: Option<&OsStr>, parent_pid: u32) -> LaunchContext` (murni, `stackly-platform::agent`): `Launchd { label }` kalau `parent_pid == 1` dan nilai itu sama dengan `com.ojiepermana.stackly.daemon` atau diawali `dev.stackly.test.agent.`; selain itu `Manual`. `main` membaca `XPC_SERVICE_NAME` sekali dan `std::os::unix::process::parent_id()`.
- `DaemonInfo` mendapat field opsional `launch: DaemonLaunch { context: LaunchContextKind, label: Option<String>, bundlePath: Option<String> }`, dengan `LaunchContextKind` enum terbuka (`launchd`, `manual`, `unrecognized`). Baris log start menambah `launch_context`, `launch_label`, dan `bundle_path`.
- Plumbing di `stacklyd`: `StartConfig` mendapat `xpc_service_name: Option<OsString>`, `parent_pid: u32`, dan `current_exe: Option<PathBuf>` yang dibaca `main`; startup menghitung `LaunchContext` dan `AppBundle` lalu memasukkannya ke `DaemonDeps` (`launch`, `bundle`), yang juga bisa diisi langsung oleh test dalam proses. `DaemonHandle::stop_requested()` menunggu permintaan `daemon.shutdown` dan memberi `ShutdownMode`; startup menunggu itu bersama sinyal, menjalankan urutan berhenti yang sama, lalu keluar 0 untuk `stop` dan 75 (`EXIT_RESTART`) untuk `restart`.
- Launch record: hanya untuk `Launchd` berlabel produksi tanpa `STACKLY_ROOT`, setelah lock didapat (langkah 6 urutan start spec 0006) dan sebelum bind socket, daemon menulis `<data>/background-agent.json` lewat `write_file_atomic` (mode 0600): `{ "schema": 1, "firstLaunchedAt", "lastLaunchedAt", "bundlePath", "version" }`. `firstLaunchedAt` diambil dari file lama kalau terbaca, selain itu sama dengan `lastLaunchedAt`. File lama yang tidak terbaca ditimpa. Kegagalan apa pun dicatat sekali di level `warn` dan start berlanjut. Path nya `DirectoryLayout::agent_launch_record()` (spec 0004). CLI dan GUI hanya memeriksa keberadaannya dan membaca `lastLaunchedAt` (paling banyak 4 KiB).

### Method `daemon.shutdown` dan exit code

| Bagian | Isi |
| --- | --- |
| Params | `ShutdownParams { mode: ShutdownMode }`; `ShutdownMode` enum terbuka `stop`, `restart`, `unrecognized`; `Validate` menolak `unrecognized` dengan `request.invalid_params` |
| Reply | `ShutdownAccepted { serverInstanceId, mode }`, diantrekan sebelum langkah berhenti pertama sehingga ikut dikirim di langkah flush |
| Recovery | `recovery allowed` |
| Saat `starting` | diterima (tidak butuh subsystem) |
| Saat berhenti | request baru mendapat `daemon.shutting_down` seperti spec 0006 |
| `restart` di konteks `manual` | error `daemon.restart_unavailable` (kategori `unsupported`, `details.launchContext`), daemon tetap jalan |
| Efek | urutan berhenti spec 0006 yang sama dengan SIGTERM, dengan reason `requested` (stop) atau `restart_requested` (restart) di event `daemon.shutting_down` dan di log |
| Exit | `stop` 0; `restart` 75 (`EXIT_RESTART`), yang membuat launchd menyalakan daemon lagi lewat `KeepAlive` |

Tabel exit code `stacklyd` menjadi: 0 berhenti normal, 1 gagal start, 2 argumen salah, 3 lock dipegang daemon lain, 75 berhenti untuk restart. Di bawah launchd, exit 1 dan 3 juga dinyalakan ulang setiap `ThrottleInterval`; untuk exit 3 itu berarti agent mengambil alih otomatis setelah daemon manual berhenti. Semua respawn ini gagal kalau binary diganti saat terdaftar (spike AC-21 B4: `spawn failed`, last exit 78) sampai `relaunch`, yang ditangani *Penantian restart* dan `daemon start`.

Instance tidak dihentikan oleh `stop` maupun `restart` (spec 0006 dan 0010); proses nya tetap hidup di session sendiri dan diadopsi daemon berikutnya. Restart terencana yang menghentikan instance terdampak adalah keputusan fitur 30.

### Perintah CLI

Group `daemon` menjadi folder `apps/cli/src/commands/daemon/` (`mod.rs`, `status.rs`, `install.rs`, `start.rs`, `stop.rs`, `restart.rs`, `agent.rs`, `wait.rs`), ditambah `commands/completion.rs` dan `commands/manpage.rs`, mengikuti pola command group spec 0008. Logika keputusan setiap perintah ada di fungsi yang menerima `&dyn BackgroundAgent`, trait kecil `DaemonProbe` (connect plus handshake, kirim `daemon.shutdown`, dan tunggu EOF di koneksi itu), dan trait kecil `LaunchRecordSource` (membaca `lastLaunchedAt` dari launch record, `None` kalau file tidak ada atau tidak terbaca), sehingga diuji dengan `FakeBackgroundAgent`, daemon skrip, launch record skrip, dan jam tokio yang dijeda.

- Pemasangan adapter *(2026-10-21, spike AC-21 B2)*: `main` membaca `std::env::current_exe()` sekali dan membuatnya canonical (`std::fs::canonicalize`); kalau `canonicalize` gagal, path dari `current_exe` dipakai apa adanya (lewat symlink itu berarti `NotBundled`), dan kalau `current_exe` sendiri gagal, path kosong. `env::read(executable: PathBuf)` menerima path itu, dan `Environment` mendapat tiga field: `agent: Arc<dyn BackgroundAgent>` (`MacosBackgroundAgent::new(executable)` di macOS, `UnsupportedBackgroundAgent` di OS lain), `bundle: Option<AppBundle>` (`AppBundle::enclosing` atas path yang sama, sumber `AgentReport.bundlePath`), dan `launch_record: Option<PathBuf>` (`DirectoryLayout::agent_launch_record()` dari root default, yaitu `MacosPlatform::new(None)`, dan `None` saat `STACKLY_ROOT` aktif, karena agent hanya melayani root default). `LaunchRecordSource` live membaca path itu; `None` berarti setiap baca memberi `None`, dan `AgentReport.lastLaunchedAt` null. Modul `platform` di `env.rs` yang sekarang membuang `MacosPlatform` setelah mengambil socket dan uid berubah sesuai itu.
- Panggilan port berjalan lewat `spawn_blocking` dengan batas `AGENT_CALL_TIMEOUT` 10 detik (lewat dari itu `cli.agent_call_timeout`, exit 8). Panggilan OS yang macet tidak bisa dibatalkan, jadi `main` CLI membuat runtime tokio sendiri dan, di setiap jalur keluar, mematikannya dengan `shutdown_timeout(Duration::ZERO)` supaya CLI tidak ikut menunggu thread yang macet. Spike AC-21 menunjukkan semua panggilan `SMAppService` bekerja di thread latar, jadi tidak ada jalur thread utama.
- Penantian daemon (`wait.rs`): satu percobaan connect plus handshake setiap 250 ms sampai batas perintah, tanpa retry `daemon.starting` milik `Session` (spec 0008), supaya irama 250 ms terjaga. `ipc.endpoint_missing`, `ipc.connection_refused`, `ipc.connection_closed`, `ipc.call_timeout` untuk handshake, `daemon.starting`, dan `daemon.shutting_down` berarti "belum naik" dan penantian berlanjut; error lain (endpoint tidak dipercaya, peer ditolak, major berbeda, pelanggaran protokol) menghentikan penantian dan dilaporkan apa adanya *(2026-10-21, cross check)*. Ctrl+C selama menunggu gagal `cli.interrupted` (exit 130) dengan `details.state` `waiting_for_daemon`.
- Ctrl+C selama panggilan `register`, `unregister`, atau `relaunch` sedang berjalan ditunda sampai panggilan itu selesai atau batas 10 detik nya lewat, supaya `relaunch` tidak berhenti di antara `unregister` dan `register`. Kalau `relaunch` lewat batas, `cli.agent_call_timeout` dengan `op` `relaunch` menulis hint `check with stackly daemon status; if it says not registered, run stackly daemon install`, karena pendaftaran bisa tertinggal di `not_registered` *(2026-10-21, cross check)*.
- Jam: "sekarang" untuk membandingkan `lastLaunchedAt` adalah `Clock` dari `stackly-platform` (wall clock, `FakeClock` di test); semua batas tunggu memakai jam monoton tokio (`tokio::time`, dijeda di test). Launch record yang tidak ada, tidak terbaca, lebih dari 4 KiB, atau `lastLaunchedAt` nya bukan RFC 3339 yang valid berarti `None`.
- `STACKLY_ROOT` aktif: `install`, `start`, dan `restart` untuk daemon yang tidak jalan gagal `cli.agent_root_override` (exit 2) sebelum menyentuh OS; `stop`, `restart` untuk daemon yang jalan, dan `status` tetap bekerja lewat IPC ke daemon root itu.
- `stop` dan `restart`: setelah `ShutdownAccepted`, CLI membaca koneksi yang sama sampai EOF (daemon menutup koneksi di langkah 5 urutan berhenti spec 0006, tepat sebelum melepas lock); `stop` lalu memastikan percobaan connect berikutnya mendapat `ipc.endpoint_missing`. Jawaban `daemon.shutting_down` untuk request itu berarti daemon sudah sedang berhenti, dan penantian yang sama berlanjut (tanpa `ShutdownAccepted`, `restart` memakai `serverInstanceId` dari handshake sebagai id lama). `restart` tidak menunggu socket hilang, karena daemon baru bisa sudah bind sebelum CLI melihat celah itu; ia mengikuti tabel *Penantian restart* di bawah.
- `start` untuk state `enabled`: kalau launch record menunjukkan `lastLaunchedAt` kurang dari 15 detik yang lalu (daemon mungkin sedang start atau menunggu `ThrottleInterval`), CLI menunggu socket paling lama 15 detik lebih dulu; baru setelah itu `relaunch`. `relaunch` juga yang menyalakan daemon setelah binary diganti dan daemon lama crash, karena launchd tidak menyalakan ulang binary yang diganti (spike AC-21 B4).
- `restart` untuk daemon yang jalan *(2026-10-21, spike AC-21 B4)*: launchd menyalakan ulang daemon setelah exit 75 kecuali binary nya diganti saat terdaftar (misalnya `cargo xtask build-app --install` atau update app), yang membuat respawn gagal dengan last exit 78 sampai daftar ulang. CLI tidak bisa melihat keadaan job tanpa `launchctl`, jadi ia memakai launch record sebagai tanda respawn, karena daemon baru menulis `lastLaunchedAt` setelah lock didapat dan sebelum bind socket. Urutannya di tabel *Penantian restart*.

**Penantian restart.** `L0` adalah `lastLaunchedAt` (wall clock) yang dibaca sebelum `daemon.shutdown` dikirim, `T_eof` adalah saat EOF terlihat di jam monoton.

| Langkah | Isi |
| --- | --- |
| 1 | baca `L0` lewat `LaunchRecordSource`, lalu kirim `daemon.shutdown { mode: restart }`; `daemon.restart_unavailable` keluar 5 tanpa langkah berikut. Jawaban `daemon.shutting_down` (daemon sudah sedang berhenti, mungkin karena `stop` dari client lain) diperlakukan sama dengan `ShutdownAccepted`, karena yang diminta pengguna adalah daemon yang jalan lagi; id lama diambil dari handshake |
| 2 | tunggu EOF di koneksi itu paling lama `DAEMON_STOP_WAIT` (20 detik), selain itu `cli.daemon_wait_timeout` dengan `details.action` `restart` |
| 3 | saat EOF, hitung sekali `elapsed` = `Clock::now() - L0`, dijepit ke rentang 0 sampai `LAUNCHD_THROTTLE_INTERVAL_SECS` (`L0` di masa depan menjadi 0; tanpa `L0`, 0). Batas respawn `T_respawn` (saat paling lambat launchd seharusnya sudah menyalakan daemon baru) = `T_eof + (LAUNCHD_THROTTLE_INTERVAL_SECS - elapsed) + RESPAWN_GRACE` di jam monoton, jadi selalu antara 5 dan 15 detik setelah EOF dan selalu sebelum `T_eof + DAEMON_START_WAIT` |
| 4 | setiap `DAEMON_POLL_INTERVAL`: handshake dengan `serverInstanceId` berbeda dari id lama berarti selesai, exit 0; `lastLaunchedAt` yang lebih baru dari `L0` (atau muncul saat `L0` kosong) berarti launchd sudah menyalakan daemon baru, dan CLI terus menunggu handshake sampai `T_eof + DAEMON_START_WAIT` tanpa `relaunch` |
| 5 | kalau `T_respawn` lewat tanpa keduanya dan `STACKLY_ROOT` tidak aktif: `status`, `classify` (`just_registered` false). Hanya `enabled` yang lanjut; state lain gagal dengan kode dari daftar kode state di bawah (agent terisi, `info` null). Tepat sebelum `relaunch`, CLI mencoba satu handshake dan membaca launch record sekali lagi, karena respawn bisa terjadi selama `status` berjalan (sampai 10 detik); kalau salah satunya menunjukkan daemon baru, kembali ke langkah 4 tanpa `relaunch` |
| 6 | `relaunch` sekali, lalu `classify` probe hasil nya dengan `just_registered` true. `enabled`: warning `cli.agent_relaunched`, lalu tunggu handshake dengan `serverInstanceId` baru paling lama `DAEMON_START_WAIT` (30 detik) sejak `relaunch`, lewat batas `cli.daemon_wait_timeout`. State lain gagal saat itu juga dengan kode dari daftar kode state, tanpa menunggu dan tanpa warning. Error panggilan nya mengikuti *Hasil pendaftaran* |
| 7 | dengan `STACKLY_ROOT` aktif tidak ada langkah 5 dan 6: CLI menunggu sampai `T_eof + DAEMON_START_WAIT` lalu `cli.daemon_wait_timeout` (agent hanya melayani root default; daemon root override di bawah launchd hanya ada di test native) |

Tebakan `T_respawn` yang terlalu cepat tidak merusak, tetapi tidak gratis: `relaunch` mengirim `SIGTERM` ke daemon yang sedang start (spike: `unregister` menghentikan job yang jalan), daemon itu berhenti lewat jalur sinyal spec 0006, `register` menyalakan yang baru, dan macOS bisa menampilkan notifikasi "Background Items Added" lagi. Instance tetap hidup di session sendiri. Daemon yang gagal menulis launch record (warning saja, AC-5) membuat tanda respawn tidak terlihat, jadi tebakan terlalu cepat hanya terjadi kalau daemon baru juga butuh lebih dari 5 detik sampai handshake. Konstanta `RESPAWN_GRACE` (5 detik) ada di `commands/daemon/wait.rs`; `LAUNCHD_THROTTLE_INTERVAL_SECS` (10 detik) adalah konstanta `stackly-platform::bundle` yang juga dipakai `xtask` untuk menulis `ThrottleInterval` di plist, jadi keduanya tidak pernah berbeda.

### Instalasi CLI

`CommandLineTool` (`StacklyUI/Agent/CommandLineTool.swift`, satu satunya file `StacklyUI` yang memakai `createSymbolicLink`, `createDirectory`, `rename`, atau `removeItem`, dijaga test aturan sumber). Home dari `UserHome.current()` dan bisa disuntik untuk test. `CommandLineTool.bundledTool: URL?` *(ditambah dari spec 0016)* adalah `<bundle>/Contents/MacOS/stackly-cli` kalau file itu ada dan executable, selain itu nil; Install dan Repair butuh nilai ini, Remove tidak. Penggantian link memakai `rename(2)` dari Darwin, karena `FileManager.moveItem` gagal kalau tujuan sudah ada. `<bundle>` di sini selalu `CanonicalPath.resolve(Bundle.main.bundleURL)`, dan status `installed` atau `stale` membandingkan target link dengan path itu setelah target juga di `realpath`, supaya app yang dibuka lewat path dengan symlink tidak dilaporkan `stale` *(2026-10-21)*.

- **Link terkelola**: `~/.local/bin/stackly` menunjuk ke `<bundle>/Contents/MacOS/stackly-cli`, dan `~/.local/share/man/man1/<halaman>` menunjuk ke `<bundle>/Contents/Resources/man/man1/<halaman>` untuk setiap halaman di bundle. Sebuah path adalah link terkelola kalau ia symlink yang target nya berakhiran `.app/Contents/MacOS/stackly-cli` atau `.app/Contents/Resources/man/man1/stackly*.1` *(2026-10-22: nama target `stackly-cli`; belum ada build yang memasang link ke nama lama, jadi tidak ada aturan peralihan)*.
- **Status** (dihitung dari link CLI; halaman man ikut dilaporkan per file): `installed` (link terkelola ke bundle yang sedang berjalan), `stale` (link terkelola ke bundle lain), `broken` (link terkelola yang target nya tidak ada), `conflict` (file, folder, atau symlink lain di path itu), `not_installed`.
- **Install dan Repair**: buat `~/.local/bin` dan `~/.local/share/man/man1` dengan mode 0755 kalau belum ada; folder yang sudah ada (atau symlink ke folder) harus milik user dan tidak bisa ditulis group atau other, selain itu gagal tanpa menulis apa pun. Setiap link ditulis sebagai symlink sementara di folder yang sama lalu di rename, sehingga link lama terganti atomik. Path `conflict` tidak pernah ditimpa dan dilaporkan dengan isi nya. Link man yang tidak lagi punya halaman di bundle (link terkelola yang rusak) dihapus.
- **Remove**: hapus hanya link terkelola; folder tidak dihapus.
- **PATH**: GUI tidak bisa membaca PATH shell pengguna, jadi ia tidak pernah mengklaim `stackly` sudah ada di PATH. Ia selalu menampilkan baris `export` untuk disalin dan path lengkap `<bundle>/Contents/MacOS/stackly-cli` sebagai alternatif. Tidak ada file shell, `/etc/paths`, `/etc/paths.d`, atau `/usr/local/bin` yang disentuh, dan tidak ada permintaan hak admin.

Mockup UI menulis "Install stackly in /usr/local/bin, requires your password once"; perilaku itu tidak dipakai (scope dan spec menang atas mockup), dan fitur 16 menyesuaikan teks langkah Command Line.

### Key invariants

- Tidak ada kode produk (daemon, CLI, GUI, library) yang menjalankan `launchctl`, `open`, `osascript`, `codesign`, atau proses lain untuk mengendalikan agent. `launchctl` hanya dipakai `LaunchAgentFixture` di test dan `runtime spike --cleanup` di xtask.
- Pendaftaran hanya berubah lewat `register`, `unregister`, dan `relaunch`, dan ketiganya hanya dipanggil dari aksi pengguna (`daemon install`, `daemon start`, `daemon restart` untuk daemon yang tidak jalan atau yang tidak dinyalakan ulang launchd sampai batas respawn, Turn On, Start stacklyd). State `requires_approval` dan `disabled` tidak pernah memicu `register` atau `relaunch`.
- Stop yang diminta selalu exit 0, dan restart yang diminta selalu exit 75, jadi `KeepAlive { SuccessfulExit: false }` tidak pernah membatalkan stop.
- Agent selalu melayani root default. Root override selalu daemon manual.
- Launch record hanya ditulis daemon berkonteks `launchd` berlabel produksi, tidak pernah oleh CLI atau GUI.
- Bundle tidak pernah memuat paket `testing/` atau `stackly-fake-server`, `Contents/MacOS` hanya berisi tiga executable, dan binary di bundle selalu ditandatangani sebelum app.
- Instalasi CLI tidak pernah menimpa path yang bukan link terkelola dan tidak pernah menyentuh PATH, file shell, atau path global.
- `classify` Rust dan Swift selalu sama untuk setiap baris fixture.
- Di GUI, jam dan tunggu agent selalu milik `DaemonModel`: `lastCheckedAt` dari `now` nya, dan `startWait`, polling, serta `announceWait` lewat `sleep` nya, tanpa membandingkan `now()` *(2026-10-22)*.
- Adapter Rust tidak pernah membaca `NSBundle.mainBundle` atau `current_exe`; bundle yang ditanyakan ke OS selalu bundle canonical yang diberikan `main` CLI, dan `Registration.bundle` selalu sama dengan bundle di `AgentReport.bundlePath`.
- Tidak ada langkah build atau test tanpa pengawasan yang mendaftarkan agent `SMAppService`, menyalakan atau mematikan Login Items, atau memakai akun macOS lain.

### Security model

- Batasnya tetap satu akun user (BR-012). `daemon.shutdown` bisa dipanggil client mana pun milik user yang sama; itu sama kuatnya dengan sinyal SIGTERM yang sudah bisa dikirim proses user itu, dan tercatat di log dengan pid peer.
- Persetujuan background dikelola macOS. Stackly hanya membaca status, mendaftar saat diminta, dan membuka halaman Login Items; ia tidak pernah mencoba melewati atau menyalakan izin.
- Hardened runtime di ketiga binary tanpa entitlement; App Sandbox tetap mati (spec 0001) dan tidak ada setting yang menurun ke child. Job launchd tanpa environment tambahan, jadi daemon tidak mewarisi variabel shell.
- Binary helper dan CLI berada di dalam bundle yang ditandatangani; selama ad hoc, seal hanya membuktikan "tidak berubah sejak build lokal ini". Pemeriksaan seal saat runtime dan verifikasi tanda tangan peer ditunda ke fitur 60 dan 63.
- Symlink CLI hanya di bawah home pengguna, folder induk wajib milik user tanpa izin tulis group atau other, dan path yang bukan milik Stackly tidak pernah disentuh.
- Panggilan `objc2` adalah permukaan `unsafe` baru di `stackly-platform-macos`, diaudit di fitur 63.

### Configuration required

- `STACKLY_SIGN_IDENTITY` (xtask saja, opsional): nama atau hash SHA-1 identity code signing untuk `build-app`; kosong berarti ad hoc. Tidak ada variabel baru untuk daemon, CLI, atau GUI. `XPC_SERVICE_NAME` diset launchd, bukan pengguna.
- Prasyarat di luar repo untuk milestone 4: identity Apple Development nyata di login Keychain Mac ini (OQ-012). Akun Apple ID gratis dengan Personal Team di Xcode biasanya cukup untuk sertifikat Apple Development lokal; Developer ID dan notarization butuh Apple Developer Program dan milik fitur 60. Keputusan akun ada di release owner.
- Prasyarat untuk AC-19: akun macOS kedua yang bukan developer, dibuat pengguna dengan hak admin.

## Consequences

**Positive**:

- Tidak ada `launchctl`, `open`, atau proses lain di kode produk, jadi aturan "CLI dan GUI tidak menjalankan proses" (spec 0001, 0008, 0013) tetap utuh tanpa pengecualian.
- Persetujuan background sepenuhnya milik macOS, dan Stackly tidak pernah mengubahnya tanpa aksi pengguna, sesuai REQ-014 dan PRD bagian 25.
- Stop dan restart memakai jalur berhenti yang sudah teruji di spec 0006, sehingga perilaku daemon sama di bawah launchd, dari Terminal, dan di test.
- Bundle, plist, dan signing dibuat satu perintah sejak sekarang, jadi masalah packaging muncul di fase ini (RISK-10), dan fitur 60 hanya menambah Developer ID dan notarization.
- Semua logika keputusan (state, hint, perintah) teruji dengan fake dan fixture tanpa signing, dan bagian yang tidak bisa diuji jelas tercatat `BLOCKED`.
- Fakta OS yang paling berisiko diuji spike di awal, sehingga cara start bisa diganti di adapter (`relaunch`) sebelum CLI dan GUI dibangun di atasnya.

**Negative / tradeoffs**:

- Beberapa perilaku OS belum terkonfirmasi sumber resmi. Spike AC-21 membuktikan untuk build ad hoc: pendaftaran ad hoc bisa, `relaunch` menyalakan job tanpa persetujuan baru, `XPC_SERVICE_NAME` sama dengan label, dan `SMAppService` bekerja dari `Contents/MacOS` dan lewat symlink. Yang masih bertumpu pada AC-17 dan AC-19 (build bertanda tangan): status setelah izin dimatikan, apakah `relaunch` meminta persetujuan baru, dan apakah respawn gagal setelah binary diganti. Kalau salah satunya gagal, spec ini kembali ke `/architect` untuk bagian itu.
- Build ad hoc kemungkinan menampilkan `enabled` walau switch Login Items dimatikan, karena di run spike macOS mengabaikan switch itu untuk build ad hoc (B3; satu run, diulang record tambahan milestone 2). Selama development tanpa identity, `disabled` dan `requires_approval` tidak bisa dicoba di Mac ini kecuali lewat fake.
- Setelah bundle diganti saat agent terdaftar, crash daemon tidak dinyalakan ulang launchd (B4), dan `stackly daemon restart` butuh beberapa detik lebih lama (sampai `T_respawn`, biasanya 5 detik setelah EOF) sebelum `relaunch`. Daemon yang mati karena itu hanya terlihat sebagai "stacklyd isn’t running" sampai pengguna menekan Start stacklyd atau menjalankan `stackly daemon start`; sebab nya (last exit 78) baru terlihat di doctor fitur 34.
- `not_found` sekarang hanya muncul tepat setelah pendaftaran. Service yang hilang di luar aksi pendaftaran (misalnya setelah database Background Task Management di reset) tampil sebagai `not_registered` dengan langkah install, yang memang langkah pemulihan yang benar, tetapi tidak menyebut sebab nya.
- `disabled` adalah turunan dari launch record, bukan status OS. Pendaftaran baru setelah pernah diizinkan bisa tampil `disabled`; teks dan langkah pemulihannya netral (Login Items), jadi salah label nya tidak berbahaya, tetapi tetap tidak sepresisi status OS.
- `relaunch` bisa memunculkan notifikasi "Background Items Added" lagi dari macOS, sekarang juga saat `restart` memakai langkah cadangan nya.
- **Konsekuensi untuk spec 0008 (fitur 8 masih dibangun program foundation)**: `CLI_SCHEMA_VERSION` naik ke 2 saat langkah 6 spec ini masuk, jadi golden file setiap perintah yang sudah ada ikut berubah di commit itu, dan teks spec 0008 perlu update di *Usulan update untuk spec lain*. Kalau fitur 8 masih terbuka saat itu, kedua build perlu berurutan supaya golden file tidak bentrok.
- Kegagalan start yang menetap di bawah launchd (misalnya root yang izinnya terlalu terbuka) diulang launchd setiap 10 detik tanpa sebab yang terlihat di GUI sampai doctor fitur 34; yang terlihat hanya "stacklyd isn’t running".
- Saat daemon dihentikan atau izin dimatikan, instance tetap hidup tetapi tidak diawasi (tanpa restart policy dan health) sampai daemon kembali.
- Banner jendela mempertahankan baris agent selama `refreshing` (spec 0013 AC-10). Kalau daemon dinyalakan dari luar app (misalnya `stackly daemon start` di Terminal) saat baris `enabled` sudah lewat 15 detik, baris "stacklyd isn’t running." dengan Start stacklyd tetap tampil selama snapshot berjalan (biasanya sepersekian detik), dan Start di saat itu menjalankan `relaunch` ke daemon yang baru naik. Aksi dari app sendiri dan state yang menjadi `enabled` di luar aksi tidak kena, karena keduanya memakai penantian daemon *(2026-10-22, cross check)*.
- Sejak langkah 12a, aksi yang dalam satu langkah mengubah state dan juga gagal (misalnya hasil pendaftaran `unrecognized`, yang menjadi `unavailable` dan `.registrationNotKept`) memicu dua pengumuman berturut turut, teks per state lalu teks error, dan VoiceOver bisa memotong yang pertama. Kasus nya jarang, dan yang terdengar terakhir adalah teks error yang memuat langkah berikut nya *(2026-10-22)*.
- Satu tepi yang diterima *(2026-10-22, cross check)*: kalau pengumuman transisi masih tertunda dan probe yang menyelesaikan nya membawa state `not_found` sementara kode kegagalan nya sudah bukan kedua kode itu, `agentDidAssess` mencatat `not_found` sebagai state terakhir dan hanya mengumumkan "Can’t connect to stacklyd."; banner tidak menampilkan baris agent di keadaan itu, jadi `not_found` tidak terdengar sampai pengguna membuka Diagnostics. `not_found` hanya muncul tepat setelah pendaftaran, jadi keadaan ini butuh Turn On dan putus koneksi dengan kode lain di jendela waktu yang sama.
- Selama penantian daemon, status yang gagal dibaca (`unavailable`) tidak mengakhiri penantian, jadi tombol Check Again di baris "Stackly couldn’t check its background service." tetap nonaktif sampai handshake atau batas 30 detik *(2026-10-22)*.
- Build dari Xcode IDE tidak memuat helper, jadi alur agent hanya bisa dicoba dari `cargo xtask build-app --install`.
- `~/.local/bin` tidak ada di PATH default macOS, jadi pengguna tetap harus menambahkan satu baris sendiri.
- Klasifikasi state ditulis dua kali (Rust dan Swift); fixture bersama menjaga kesamaannya, tetapi perubahan selalu menyentuh dua tempat.
- Binding `objc2` menambah dependency dan blok `unsafe` di `stackly-platform-macos`.
- Beberapa langkah tidak bisa dijalankan tanpa kehadiran kamu (spike, run native LaunchAgent, milestone 4), jadi build fitur ini tidak bisa selesai sepenuhnya oleh sesi tanpa pengawasan.

**Neutral**:

- Exit code daemon bertambah 75, dan `stacklyd` mendapat satu method dan satu field `DaemonInfo`; protokol naik satu minor.
- `~/Applications/Stackly.app` menjadi lokasi development yang disarankan, supaya path yang dicatat macOS tidak hilang saat `target/` dibersihkan.
- Tidak ada area error baru; semua kode yang dibuat CLI tetap di area `cli`.
- Path keluaran `build-app` pindah dari `target/xcode/Build/Products/<Config>/` ke `target/app/<Config>/`.

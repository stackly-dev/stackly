# 0016. Onboarding

**Date**: 2026-10-20
**Status**: Proposed

## Summary

Spec ini menetapkan onboarding Stackly: lima langkah (Welcome, Background Agent, Storage, Catalog Trust, Command Line) yang tampil di jendela utama saat aplikasi pertama kali dibuka, menggantikan shell sampai pengguna menekan Get Started atau melewatinya dengan Escape. Onboarding hanya membaca: ia tidak pernah mendaftarkan background agent, memasang CLI, atau mengirim mutasi ke daemon kecuali pengguna menekan tombol aksi di dalam langkahnya, dan tombol itu memakai model dan aksi yang sama dengan Diagnostics (spec 0015). Teksnya jujur soal isolasi (instance terpisah per folder, port, dan secret, tetapi berjalan sebagai user kamu tanpa sandbox), tidak menjanjikan fitur yang belum ada di build itu, dan bisa dibuka lagi dari menu Help tanpa mengubah state apa pun. Yang diingat hanya satu preferensi GUI, apakah onboarding sudah selesai, di `UserDefaults` aplikasi, bukan di daemon.

## Requirements

**User stories**:

- Sebagai pengguna yang baru membuka Stackly, saya ingin satu alur singkat yang menjelaskan apa itu Stackly, izin background, lokasi data, trust catalog, dan CLI, tanpa akun cloud, supaya saya tahu apa yang akan terjadi di Mac saya sebelum memakai apa pun.
- Sebagai pengguna yang belum memberi izin background, saya ingin melihat state izin yang sebenarnya beserta langkah pemulihannya, dan bisa lanjut dengan Not Now tanpa ada yang diubah diam diam, supaya keputusan izin tetap di tangan saya.
- Sebagai pengguna yang sudah paham, saya ingin melewati onboarding kapan saja dan membukanya lagi nanti tanpa mengubah daemon, instance, atau CLI, supaya onboarding tidak pernah menjadi penghalang atau sumber efek samping.
- Sebagai pengguna yang peduli keamanan, saya ingin teks yang tidak melebih lebihkan isolasi dan trust, supaya saya tidak mengira provider native disandbox atau tidak bisa membaca file user saya (AC-061).
- Sebagai pengguna keyboard dan VoiceOver, saya ingin semua langkah dan aksi bisa dipakai tanpa mouse dan diumumkan dengan jelas, supaya onboarding sama bergunanya untuk saya.

**Acceptance criteria** (ID lokal spec ini; ID PRD selalu tiga digit, misalnya AC-061):

- **AC-1**: Saat app dibuka dan `OnboardingRecordStore` tidak menyimpan `onboarding.finished` bernilai true, jendela utama menampilkan onboarding di langkah 1 sebagai seluruh isi jendela: tanpa sidebar, toolbar, judul jendela yang terlihat, footer daemon, atau banner daemon. Saat nilainya true, jendela utama menampilkan shell spec 0013 seperti biasa. Nilai itu hanya ditulis true oleh Get Started dan oleh lewati (AC-3), tidak pernah oleh menutup jendela, Quit, atau navigasi antar langkah. Selama satu peluncuran, menutup lalu membuka lagi jendela utama saat onboarding belum selesai menampilkan onboarding di langkah yang sama; peluncuran berikutnya mulai lagi dari langkah 1. Tidak ada bagian onboarding yang menyimpan state ke daemon, registry, atau file di root data (PAGE-01, JOURNEY-01).
- **AC-2**: Onboarding punya tepat lima langkah berurutan dengan label `Welcome`, `Background Agent`, `Storage`, `Catalog Trust`, dan `Command Line`. Footer menampilkan lima titik langkah (titik aktif lebih lebar), teks `Step {n} of 5 · {label}`, tombol Back mulai langkah 2, dan satu tombol utama dengan label: `Get Started` di langkah 5; `Not Now` di langkah 2 selama `BackgroundAgentModel.assessment` bernilai nil atau state nya bukan `enabled`; `Continue` di langkah lain. Continue, Not Now, Back, dan titik langkah hanya memindahkan langkah. Get Started menulis record lalu menampilkan shell. Return menekan tombol utama, dan setiap titik langkah adalah tombol yang pindah langsung ke langkah itu (PAGE-01).
- **AC-3**: Onboarding bisa dilewati dan dibuka lagi tanpa mengubah state daemon. Escape (`onExitCommand`) dan aksi escape VoiceOver di langkah mana pun menutup onboarding dan menulis record yang sama seperti Get Started, tanpa pengumuman "Setup complete." (AC-11). Item menu Help "Welcome to Stackly" membuka jendela utama kalau tertutup dan menampilkan onboarding di langkah 1, atau, kalau onboarding sedang tampil, hanya membawa jendela itu ke depan. Escape tidak diblokir saat aksi langkah sedang berjalan (Turn On, Start stacklyd, atau aksi CLI): aksi itu selesai di modelnya sendiri dan hasilnya terlihat di Diagnostics; konfirmasi yang terbuka menerima Escape lebih dulu sebagai Cancel. Menampilkan, menavigasi, melewati, dan menyelesaikan onboarding tanpa menekan tombol aksi langkah dibuktikan test dengan fake: log `FakeBackgroundAgentController` hanya berisi `status`, home sementara `CommandLineTool` tidak berubah, `MutationPath.perform` tidak pernah dipanggil, dan tidak ada call IPC selain baca yang memang dijalankan `ShellSync`. Setelah onboarding tertutup, shell menampilkan bagian yang tersimpan di `@SceneStorage("shell.section")` tanpa diubah, jadi peluncuran pertama berakhir di Overview (PAGE-01, JOURNEY-01).
- **AC-4**: Langkah Welcome menampilkan ikon app 112 pt, judul "Welcome to Stackly" dengan `.largeTitle.bold()`, subjudul, dan baris fitur dari tabel *Copy* (Isolated instances, Verified runtimes, No account needed), masing masing dengan ikon di tile netral. Baris "Verified runtimes" hanya tampil kalau install runtime lewat daemon (milestone 3 spec 0018) sudah ada di build itu, dan baris "Environments as files" dari mockup tidak tampil sampai fitur 44 menambahkannya; aturan *Fitur yang belum ada* menentukan siapa yang menambahkan baris itu. Tidak ada langkah yang meminta akun, login, atau jaringan, dan folder `Onboarding/` tidak memakai `URLSession` atau literal `http://` dan `https://`, dijaga test aturan sumber (PAGE-01, AC-061).
- **AC-5**: Langkah Background Agent menampilkan satu kartu menurut tabel *Kartu Background Agent* untuk setiap kombinasi `assessment`, presence daemon, kode error koneksi terakhir, `isStarting`, dan ambang `AgentTiming.startGrace` (15 detik sejak `since` dari `ShellPresentation.status` `.unreachable`), termasuk `StatusLabel` daemon dari footer spec 0013 di setiap baris `enabled`. Baris Start stacklyd hanya muncul untuk kode `ipc.endpoint_missing` dan `ipc.connection_refused`, sehingga daemon yang macet, sedang restart, atau tidak kompatibel tidak pernah ditawari `relaunch`. Selama tidak `isStarting`, kartu berganti tepat di detik ke 15 tanpa menunggu polling; selama Turn On, Start stacklyd, atau izin yang baru dinyalakan menunggu daemon (`isStarting`), kartu tidak menawarkan Start stacklyd dan progress tertunda tampil sampai daemon tersambung, `lastError` `.daemonDidNotStart(seconds: 30)` tampil, atau state yang dibaca menjadi `requires_approval`, `disabled`, `not_registered`, atau `not_found`; dalam kasus terakhir penantian berakhir tanpa Last error dan aksi baris state itu langsung aktif, sedangkan state `unavailable` tidak mengakhiri penantian *(diubah 2026-10-22, spec 0015 G2, G7, G9; akhir penantian per state 2026-10-22, langkah 12a spec 0015)*. Aksi kartu hanya memanggil `BackgroundAgentModel.turnOn()`, `openLoginItems()`, `start()`, dan `refresh()`. Muncul nya langkah ini hanya memanggil `refresh()`. Selama `isWorking`, tombol aksi kartu nonaktif dan progress tertunda tampil; `lastError` tampil di bawah kartu dengan teks `AgentActionError` spec 0015. Teks "Without it, the daemon runs only while the app is open." tidak ada di mana pun (REQ-014 lewat spec 0015, PAGE-01, JOURNEY-01).
- **AC-6**: Langkah Storage menampilkan baris Data, Cache, Logs, dan Secrets dengan judul langkah `.title.bold()` dan copy dari tabel *Copy*. Tanpa `STACKLY_ROOT`, nilai Data, Cache, dan Logs diambil dari `DaemonInfo.roots` daemon terakhir yang diketahui kalau ada dan `rootOverride` nya false, selain itu dari `StorageLocations.defaults(home:)` yang mengikuti tabel default macOS spec 0004, dengan awalan home ditulis `~` hanya kalau path sama dengan home atau diawali home ditambah `/`; Secrets "Login Keychain". Dengan `STACKLY_ROOT`, subjudul memakai varian override, ketiga baris itu diganti satu baris catatan override, dan Secrets menjadi "A keychain file inside that folder" (spec 0011 AC-2: root override memakai keychain file di `R/data/keychain/`, bukan login Keychain). Nilai variabel itu tidak pernah tampil (spec 0013) (PAGE-01, AC-061).
- **AC-7**: Langkah Catalog Trust menampilkan satu baris untuk catalog yang dimuat daemon menurut tabel *Baris Catalog Trust*, bersumber dari `CatalogStore.info` (`source`, `trust`, `revision`, `publishedAt`, `outdated`), `CatalogStore.error`, dan `CatalogStore.unsupported` spec 0017, plus catatan trust dari tabel *Copy*. Label "official" hanya muncul saat `info.trust` bernilai `official`; sebelum `CatalogInfo` ada, atau saat catalog gagal atau tidak didukung, label nya "Catalog" dan tidak ada toggle. Saat `info` ada, baris dari `info` yang menang walau refresh berikutnya gagal (spec 0012 AC-8). Tidak ada baris atau toggle community, tidak ada teks "Signed manifests", dan tidak ada teks yang menyebut catalog terbaru, up to date, atau tanggal yang lebih baru dari `publishedAt`. Nilai enum `unrecognized` memakai teks netral spec 0017 (PAGE-01, AC-061).
- **AC-8**: Langkah Command Line menampilkan baris "Install stackly in ~/.local/bin" dengan kontrol menurut tabel *Kontrol Command Line* untuk setiap status `CommandLineTool` (`not_installed`, `installed`, `stale`, `broken`, `conflict`), dengan state dari `CommandLineToolModel` yang sama dengan `CommandLineToolSection` dan dibaca ulang saat app aktif kembali. Status menentukan baris; bundle tanpa `Contents/MacOS/stackly-cli` hanya menonaktifkan Install dan Repair dengan alasannya, sedangkan toggle tetap menunjukkan status sebenarnya dan Remove tetap bisa. Menyalakan toggle, mematikannya, dan Repair masing masing membuka konfirmasi spec 0012 dari `CommandLineToolPrompts`, dan hanya tombol aksi konfirmasi itu yang memanggil `install`, `remove`, atau `repair`; Cancel tidak mengubah apa pun dan toggle kembali ke status sebenarnya. Status `installed` menampilkan baris PATH `export PATH="$HOME/.local/bin:$PATH"` dengan tombol Copy dan path lengkap CLI di bundle (`{path bundle}/Contents/MacOS/stackly-cli`); perintah dan nama link tetap `stackly` *(diubah 2026-10-22, nama file CLI di bundle spec 0015)*. Blok contoh hanya berisi perintah di `OnboardingCopy.commandExamples`. Teks `/usr/local/bin` dan "Requires your password once" tidak ada di mana pun, dan penanda `CommandLineToolSection` menjadi `// provisional: F32` saja (PAGE-01, PRD bagian 25 lewat spec 0015).
- **AC-9**: Semua teks onboarding ada di satu file `OnboardingCopy.swift`, dan test copy memastikan setiap nilai sama persis dengan tabel *Copy*, *Kartu Background Agent*, *Baris Catalog Trust*, dan *Kontrol Command Line*. Test aturan sumber atas folder `Onboarding/` gagal kalau ada frasa "never touching", "sandboxed", "can’t read", "cannot read", "Signed manifests", "only while the app is open", "/usr/local/bin", "password once", "up to date", atau "latest". Langkah `/check verify` membaca ulang semua copy terhadap AC-061 dan mencatat hasilnya (AC-061).
- **AC-10**: Onboarding bisa dipakai penuh dari keyboard: saat Keyboard navigation menyala di System Settings (seperti AC-17 spec 0012), Tab melewati titik langkah, aksi kartu, toggle, tombol Copy, Back, dan tombol utama, dan Space menekannya; Return menekan tombol utama dan Escape melewati dalam setting apa pun. Setiap titik langkah punya label VoiceOver "Step {n} of 5, {label}", trait selected untuk langkah aktif, dan area klik minimal 24 × 24 pt. Saat langkah berganti, fokus VoiceOver pindah ke judul langkah lewat `@AccessibilityFocusState` dan `announce(_:)` mengucapkan "Step {n} of 5, {label}." sekali. Perubahan state agent dan kegagalan aksi agent (teks Last error) diumumkan oleh announcer `DaemonModel` dengan teks tabel *Pengumuman* spec 0015, bukan oleh onboarding, sehingga tidak ada pengumuman ganda; satu satunya pengecualian adalah `not_found` (tone critical): onboarding mengumumkan judul baris banner agent nya ("Stackly can’t find its background service.", teks yang sama dengan `StateBanner` dan `DaemonModel`) sekali saat state agent berubah menjadi `not_found` selagi onboarding tampil, di langkah mana pun, hanya kalau banner jendela yang tersembunyi akan menampilkan baris agent saat itu (seperti banner critical spec 0012, yang biasanya mengumumkan nya); di presence lain announcer `DaemonModel` yang mengumumkan nya, jadi state itu terdengar tepat sekali *(diubah 2026-10-22, spec 0015 G1; dipersempit 2026-10-22, langkah 12a spec 0015)*. Tampilan memakai token, text style, dan permukaan spec 0012 (tanpa glass kustom, ukuran font tetap, atau warna sekunder sistem), terbaca dengan Increase Contrast dan Reduce Transparency, dan tidak terpotong di ukuran jendela minimum 900 × 600 pt (konten digulir kalau perlu) (PAGE-01, NFR-012).
- **AC-11**: Setelah Get Started, `FeedbackCenter.show(.success("Setup complete."))` menampilkan kartu umpan balik di shell dan mengumumkannya sekali (pengumuman datang dari `FeedbackCenter`, bukan panggilan `announce` terpisah). Lewati dengan Escape tidak mengumumkan apa pun selain perpindahan ke shell (PAGE-01).

## Decision

**Chosen option**: opsi yang direkomendasikan di setiap keputusan di [rationale.md](rationale.md): onboarding sebagai isi jendela utama yang menggantikan shell, satu nilai `onboarding.finished` di `UserDefaults` app, lewati lewat Escape tanpa tombol baru, buka lagi lewat menu Help, toggle Command Line yang mencerminkan status nyata dan bekerja langsung lewat konfirmasi, satu baris catalog tanpa community, hanya fitur dan perintah yang ada di build itu, teks isolasi di Welcome dan Catalog Trust, path Storage dari daemon dengan default spec 0004 sebagai cadangan, dan ikon app di Welcome.

Onboarding adalah layar baca yang memakai model milik fitur lain: setiap aksi yang mengubah sesuatu adalah tombol yang sama dengan Diagnostics, sehingga tidak ada jalur efek samping baru.

**Implementation skills**: `swiftui-expert-skill` (`avdlee/swiftui-agent-skill`, `.claude/skills/swiftui-expert-skill/`) · `swift-concurrency` (`avdlee/swift-concurrency-agent-skill`, `.claude/skills/swift-concurrency/`) · `swift-testing-pro` (`twostraws/swift-testing-agent-skill`, `.claude/skills/swift-testing-pro/`)

Kalau isi skill bertentangan dengan spec ini, spec yang menang.

### Model data

Tidak ada schema, tidak ada DTO baru, dan tidak ada perubahan protokol. Satu preferensi GUI:

| Nama | Tempat | Tipe | Arti |
| --- | --- | --- | --- |
| `onboarding.finished` | `UserDefaults.standard` app `com.ojiepermana.stackly` | Bool, tidak ada berarti false | onboarding sudah ditutup lewat Get Started atau Escape |

- `OnboardingRecordStore` (protocol, `@MainActor`): `var isFinished: Bool { get }`, `func markFinished()`. `UserDefaultsOnboardingRecordStore` untuk produksi, `InMemoryOnboardingRecordStore(isFinished: Bool = false)` untuk test, preview, dan runtime fixture spec 0068 (yang mengisinya dari `FixtureScenario.onboardingFinished`). Untuk run manual, argumen launch `-onboarding.finished NO` (domain argumen `UserDefaults`) menampilkan onboarding lagi tanpa menghapus apa pun.
- `OnboardingStep` (enum `Int`, `CaseIterable`): `welcome`, `backgroundAgent`, `storage`, `catalogTrust`, `commandLine`, dengan `label` dari tabel *Copy*.
- `OnboardingModel` (`@MainActor @Observable`, dimiliki `ShellRuntime`): `isPresented: Bool`, `step: OnboardingStep`, `next()`, `back()`, `go(to:)`, `present()`, `finish(_ reason: OnboardingFinish)` dengan `OnboardingFinish` `getStarted` atau `skipped`. Dibuat dengan `isPresented = !store.isFinished` dan `step = .welcome`. Store disuntik lewat `ShellRuntime.init(model:closeNotice:commandLineTool:onboardingStore:)`, `ShellBootstrap.live(rootOverride:clientVersion:now:onboardingStore:)`, dan `ShellBootstrap.assemble(...onboardingStore:)`, semuanya dengan default `UserDefaultsOnboardingRecordStore()`; test memberi `InMemoryOnboardingRecordStore`, dan `ShellBootstrap.fixture` memberi `InMemoryOnboardingRecordStore(isFinished: scenario.onboardingFinished)`. Urutan parameter init itu tetap, mana pun yang masuk lebih dulu: `commandLineTool:` (langkah 12 spec 0015, default nil) sebelum `onboardingStore:` (langkah 2 spec ini) *(2026-10-22)*. `ShellRuntime` memegang `onboarding: OnboardingModel`.
- `OnboardingFooter.primaryLabel(step: OnboardingStep, agentState: BackgroundAgentState?) -> String` (murni): "Get Started" untuk `commandLine`, "Not Now" untuk `backgroundAgent` saat `agentState` nil atau bukan `enabled`, selain itu "Continue". Di milestone 1 view selalu memberi nil; mulai milestone 2 view memberi `DaemonModel.agent?.assessment?.state`, yang tetap nil kalau `DaemonModel.agent` nil (test dan preview tanpa agent).

### State onboarding

```text
hidden ──present() (menu Help)──▶ presented(welcome)
presented(s) ──next / back / go(to:)──▶ presented(s')        (tanpa efek lain)
presented(s) ──finish(getStarted | skipped)──▶ hidden        (store.markFinished())
presented(s) ──jendela ditutup, dibuka lagi──▶ presented(s)  (record tidak berubah)
launch ──store.isFinished false──▶ presented(welcome)
launch ──store.isFinished true──▶ hidden
```

`present()` saat sudah `presented` tidak mengubah langkah. `finish` saat `hidden` tidak melakukan apa pun.

### Tampilan di jendela utama

- `MainWindowRoot(runtime: ShellRuntime, windowWillClose: (NSWindow) -> Void)` (`StacklyUI/Onboarding/`) menggantikan `LiveShell` sebagai isi `Window("Stackly", id: WindowOpener.mainWindowID)` di `StacklyApp` (keputusan K18 foundation): `OnboardingFlow` kalau `runtime.onboarding.isPresented`, selain itu `AppShell`, dengan `StacklyMotion.crossfade` spec 0012 (tetap dipakai saat Reduce Motion, sesuai aturan motion spec itu). `MainWindowRoot` mengambil alih wiring `LiveShell` (presentation, diagnostics, `sidebarCounts`, `reconnect()`, dan `refreshDiagnostics()` dari `runtime.model` ke `AppShell`, plus `.environment(runtime.model)`), lalu `LiveShell` dihapus. *Ditambah 2026-10-22 (spec 0015 G3):* `MainWindowRoot` juga memasang `.environment(runtime.commandLineTool)` seperti `LiveShell`, di atas `OnboardingFlow` dan `AppShell` bersama `.environment(runtime.model)`. Kalau langkah 12 spec 0015 sudah di `main` saat langkah 2 dibangun, langkah 2 memindahkan baris itu dari `LiveShell`; kalau belum, langkah 12 spec 0015 menambahkannya langsung di `MainWindowRoot`.
- *Ditambah 2026-10-22:* `MainWindowRoot` membuat `OnboardingFlow(onboarding: runtime.onboarding)`; hanya `OnboardingModel` yang masuk lewat init. View onboarding membaca kedua model lain dari environment sebagai opsional, seperti seksi Diagnostics spec 0015: `@Environment(DaemonModel.self) private var model: DaemonModel?` (model agent lewat `model?.agent`, roots, override, dan `CatalogStore`) dan `@Environment(CommandLineToolModel.self) private var commandLineTool: CommandLineToolModel?`. Tanpa `DaemonModel.agent` kartu Background Agent tidak tampil (judul dan subjudul langkah tetap) dan label tombol utama memakai `agentState` nil; tanpa `CommandLineToolModel` baris "Install stackly in ~/.local/bin" dan catatan PATH tidak tampil (blok contoh tetap). Runtime `live` dan `fixture` selalu memasang keduanya, jadi hanya preview dan test tanpa model yang melihat varian ini. Kartu Background Agent, baris Command Line, dan baris Catalog Trust masing masing dipecah menjadi view isi yang hanya menerima nilai hasil `make(...)` (misalnya `BackgroundAgentCard(content:)`) dan pembungkus tipis yang membangun nilai itu dari model, supaya snapshot dan preview setiap baris tabel bisa merender view isi dengan nilai buatan test tanpa model atau runtime. *Ditambah 2026-10-21 (spec 0067):* `MainWindowRoot` juga mengambil alih `@State FeedbackCenter` yang dipegang `LiveShell` sejak spec 0067 langkah 7 (atau membuatnya kalau belum ada), dan memasangnya di environment `feedbackCenter` di atas `OnboardingFlow` dan `AppShell`, jadi satu jendela punya satu kartu umpan balik.
- `MainWindowAccessor`, penangkapan `@Environment(\.openWindow)` ke `runtime.windowOpener`, pelaporan `windowWillClose`, dan `.frame(minWidth: 900, minHeight: 600)` pindah dari `AppShell` ke `MainWindowRoot`, supaya notice tutup jendela spec 0013 dan ukuran minimum tetap berlaku selama onboarding (dengan `.windowResizability(.contentMinSize)`). Init `AppShell` kehilangan parameter `windowOpener` dan `windowWillClose`. `AppShell.minimumSize` tetap ada dan `MainWindowRoot` memakainya untuk frame. `ShellLayoutTests` (penjaga layout `35f6bf6`) tetap meng host `AppShell` di `AppShell.minimumSize`; langkah 2 hanya menghapus argumen `windowOpener` dan `windowWillClose` dari panggilan `AppShell(...)` nya. `@SceneStorage("shell.section")` tetap di `AppShell`.
- *Ditambah 2026-10-21 (spec 0069):* `MainWindowRoot` mengambil alih `@State MainWindowKey` dari `AppShell` bersama `MainWindowAccessor`, memasangnya di environment `mainWindowKey`, dan `MainWindowAccessor` memanggil `track(_:)` dengan window nya, di samping laporan `windowWillClose` (spec 0069 *Model dan API*). Kalau `MainWindowKey` belum ada saat langkah 2 dibangun, milestone 2 spec 0069 yang memasangnya langsung di `MainWindowRoot`. `OnboardingFlow` tidak menerbitkan perintah.
- `OnboardingFlow`: latar `StacklyColor.surfaceWindow`, kolom isi 520 pt di tengah dengan jarak antar elemen 14 pt, di dalam `ScrollView` vertikal supaya tidak terpotong di 900 × 600 pt, dan footer di bawah garis pemisah dengan titik, teks langkah, Back, dan tombol utama (`.borderedProminent`, `.keyboardShortcut(.defaultAction)`). ### Kartu Background Agent

Satu kartu `.cardSurface()` dengan ikon status, judul, detail, dan aksi di kanan, dipilih dari baris pertama yang cocok. Fungsi murni `BackgroundAgentStepContent.make(_ input: AgentBanner.Input, footer: StatusAppearance, now: Date, lastError: AgentActionError?, isWorking: Bool) -> BackgroundAgentStepContent` menghasilkan isinya *(diubah 2026-10-22: satu input dengan banner spec 0015)*, dengan masukan:

- `input` = `DaemonModel.agentBannerInput` spec 0015, nilai yang sama dengan banner dan `ConnectionHint`, jadi ketiganya tidak pernah berbeda: `status` (`ShellPresentation.status` spec 0013, `ShellStatus`, yang membawa `.unreachable(lastKnownAt:since:)`, sehingga `since` punya sumber), `failureCode` (`DaemonModel.unreachableCode`, kode kegagalan terakhir selama `unreachable`), `assessment`, `detail` (`BackgroundAgentModel.unavailableDetail`, termasuk `unavailableDetail` yang ditambahkan di sana dari spec ini), dan `isStarting`. `agentBannerInput` nil (tanpa `DaemonModel.agent`) berarti tidak ada kartu (*Tampilan di jendela utama*).
- `footer` = `DaemonModel.presentation.footer` (`ShellPresentation.footer` spec 0013), sumber tone baris "presence lain" dan `StatusLabel` di setiap baris `enabled`.
- `lastError` dan `isWorking` dari `DaemonModel.agent` (`BackgroundAgentModel`, spec 0015).
- `now` = `fixtureNow ?? context.date` dari `TimelineView` di sekitar kartu, dengan `fixtureNow` dari `@Environment(\.fixtureNow)` spec 0068 (nil di luar mode fixture). Jadwal nya dipilih di `body`, di luar closure, lewat predikat spec 0013 `DaemonBanner.ticksEverySecond(input, now: fixtureNow ?? Date.now)`: 1 detik hanya selama baris `enabled` belum 15 detik dan tidak `isStarting`, selain itu tiap menit, sama dengan banner. Jadi baris berganti tepat di detik ke 15 tanpa menunggu polling 5 detik, dan runtime fixture memakai jam tetap `FixtureClock` seperti banner *(diubah 2026-10-22; sebelumnya `TimelineView(.explicit(...))` dengan jam yang tidak disebut)*.

"Tidak terjangkau karena daemon tidak ada" berarti status `.unreachable` dengan `failureCode` `ipc.endpoint_missing` atau `ipc.connection_refused` (aturan yang sama dengan *Banner per state* spec 0015). Baris itu tidak tampil di baris `enabled` tersambung *(2026-10-22)*: spec 0015 hanya mengosongkan `lastError` saat aksi berikut mulai, jadi tanpa aturan ini "stacklyd didn’t start within 30 seconds." tetap tampil di samping daemon yang sudah tersambung. Teks `lastError` diumumkan sekali oleh announcer `DaemonModel` lewat closure `didFail` (langkah 12a spec 0015) saat model mengisi nya, di mana pun aksinya ditekan; kartu dan folder `Onboarding/` tidak pernah memanggil `announce(_:)` untuk `lastError` *(2026-10-22, langkah 12a spec 0015)*.
- Fokus keyboard setelah aksi kartu *(2026-10-22)*: tombol yang ditekan hilang di hampir setiap hasil (Turn On menjadi kartu tanpa aksi atau kartu dengan tombol lain). `OnboardingFlow` memegang `@FocusState` dengan target `cardAction` dan `primary`; saat baris kartu berganti selagi fokus di `cardAction`, fokus tetap di `cardAction` kalau baris baru punya aksi, selain itu pindah ke `primary` (tombol utama footer). Fokus VoiceOver tetap di aturan judul langkah dan tidak dipindah oleh pergantian baris. *(Diperjelas 2026-10-22, langkah 12a spec 0015.)* Karena `.disabled(reason:)` benar benar menonaktifkan tombol, fokus keyboard bisa lepas dari tombol yang ditekan selama `isWorking`, jadi aturan di atas tidak bergantung pada fokus saat baris berganti: setiap tombol aksi kartu memasang `@State focusAfterCardAction = true` di `OnboardingFlow` saat ditekan, dan saat baris kartu berganti atau `isWorking` menjadi false selagi flag itu true, fokus pindah ke `cardAction` kalau baris saat itu punya aksi yang aktif (tidak `isWorking`), selain itu ke `primary`, lalu flag dilepas. Flag juga dilepas saat pengguna memindah fokus sendiri ke target lain. Jadi Turn On yang berakhir `requires_approval` atau gagal dengan `lastError` (baris tetap `not_registered`) mengembalikan fokus ke aksi kartu, sedangkan Turn On yang berhasil memindah fokus ke `primary` saat baris "stacklyd is starting…" tampil, dan akhir penantian sesudah nya tidak menarik fokus lagi.
- Pergantian baris di detik ke 15 tidak diumumkan, sama dengan banner spec 0015.
- `isWorking`: aksi kartu nonaktif lewat `.disabled(reason:)` spec 0012 dengan alasan "Working…", ditambah `DelayedProgress`. *(2026-10-22, spec 0015 G2, G7, G9)* `isWorking` mencakup penantian daemon spec 0015: setelah Turn On atau Start stacklyd dengan hasil `enabled`, dan saat refresh melihat state menjadi `enabled` di luar aksi (izin baru dinyalakan di System Settings, atau `stackly daemon install` di Terminal). Selama penantian itu `isStarting` juga true, jadi baris mengikuti presence tanpa pernah menawarkan Start stacklyd ("stacklyd is starting…" selama `unreachable` dengan kedua kode itu, "Connecting to stacklyd…" selama `connecting`, baris tersambung sesudah handshake), dan progress tetap tampil sampai penantian berakhir: presence bukan `connecting`, `unreachable`, atau `refreshing` (ini arti "sampai daemon tersambung" di AC-5), presence kembali `unreachable` sesudah handshake, `.daemonDidNotStart(seconds: 30)` masuk `lastError` sebelum handshake (sesudah itu baris Start stacklyd tampil kalau sudah lewat 15 detik), atau probe selama penantian memberi state `requires_approval`, `disabled`, `not_registered`, atau `not_found`.
- Akhir penantian per state *(2026-10-22, langkah 12a spec 0015)*: probe yang memberi salah satu dari empat state itu (dari polling, dari `ShellRuntime.didBecomeActive()` saat pengguna kembali dari System Settings, dari transisi presence, atau dari `refresh()` saat langkah 2 muncul) mengakhiri penantian tanpa `lastError`, jadi `isStarting` dan `isWorking` menjadi false dan kartu langsung menampilkan baris state itu dengan aksi aktif: Open System Settings… untuk `requires_approval` dan `disabled`, Turn On untuk `not_registered`, dan tanpa aksi untuk `not_found`. Kalau salah satu dari keempat state itu lalu menjadi `enabled` lagi, penantian baru mulai menurut aturan state yang menjadi `enabled` di luar aksi di atas. Dalam praktik `not_found` tidak muncul selama penantian (sesudah hasil `enabled`, `justRegistered` sudah false, jadi status `notFound` dibaca `not_registered`); spec 0015 memasukkan nya hanya supaya himpunan nya lengkap, jadi tidak ada test kartu untuk akhir penantian lewat `not_found`. State `unavailable` (status gagal dibaca atau tidak dikenal) tidak mengakhiri penantian; selama itu kartu menampilkan baris `unavailable` nya dengan Check Again nonaktif ("Working…") dan progress, sampai penantian berakhir menurut aturan spec 0015: presence bukan `connecting`, `unreachable`, atau `refreshing`, presence kembali `unreachable` sesudah handshake, salah satu dari keempat state di atas, atau batas 30 detik yang hanya berlaku sebelum handshake. State yang berubah dari `unavailable` menjadi `enabled` tidak memulai penantian baru; penantian yang sedang berjalan berlanjut. Kartu tidak menghitung apa pun dari aturan ini sendiri: ia hanya membaca `isStarting`, `isWorking`, dan `assessment` yang sudah diubah model.
- Subjudul langkah: "stacklyd supervises your instances when the window is closed. macOS asks you to allow it in Login Items."
- Langkah ini tidak pernah memanggil `register`, `unregister`, atau `relaunch` sendiri; hanya lewat `turnOn()` dan `start()` milik `BackgroundAgentModel`, sehingga aturan AC-11 spec 0015 tetap berlaku.
- Pengumuman perubahan state agent milik announcer `DaemonModel` (tabel *Pengumuman* spec 0015: `BackgroundAgentModel` melaporkan setiap probe lewat `didAssess` dan tidak memanggil `announce(_:)` sendiri), sekali per perubahan di seluruh app *(diubah 2026-10-22, spec 0015 G1)*. Assessment pertama setelah launch hanya dicatat tanpa teks, jadi masuk ke langkah 2 tidak menambah pengumuman state; refresh saat langkah muncul yang melihat state berbeda dari yang tercatat diumumkan `DaemonModel` sekali dengan teks per state nya. Onboarding sendiri hanya mengumumkan perpindahan langkah, dengan satu pengecualian, `not_found` *(dipersempit 2026-10-22, langkah 12a spec 0015)*:
  - Sejak langkah 12a, announcer `DaemonModel` mengumumkan "Stackly can’t find its background service." sendiri saat state berubah menjadi `not_found` dan banner jendela tidak menampilkan baris agent (`agentBannerInput.flatMap { AgentBanner.content($0, now: now()) }` nil, misalnya presence tersambung), dan diam saat baris agent tampil, karena `StateBanner` yang mengumumkan banner critical saat tampil. Selama onboarding banner jendela tersembunyi (AC-1), jadi hanya kasus kedua yang ditutup onboarding.
  - `OnboardingFlow`, bukan view kartu, mengumumkan `not_found` sekali lewat `announce(_:)` saat `model?.agent?.assessment?.state` berubah menjadi `notFound` dari state lain yang bukan nil, hanya kalau `model?.agentBannerInput.flatMap { AgentBanner.content($0, now: Date.now) }` saat itu tidak nil: presence `unreachable` dengan `ipc.endpoint_missing` atau `ipc.connection_refused`, atau `refreshing` sesudah nya (fungsi itu membuka `.refreshing(after:)`, berbeda dengan baris kartu). - Pengumuman `DaemonModel` tetap berjalan selama onboarding tampil, walau banner tersembunyi *(2026-10-22, diterima)*: transisi presence ke `unreachable` di peluncuran pertama tanpa daemon diumumkan dengan judul banner agent (misalnya "Stackly’s background service is off."), dan perubahan state yang dilihat refresh saat langkah 2 muncul bisa terdengar tepat setelah "Step 2 of 5, Background Agent.". ### Key invariants

- Onboarding tidak pernah mengirim mutasi ke daemon dan tidak punya jalur ke `MutationPath`.
- `register`, `unregister`, dan `relaunch` dari onboarding hanya lewat `BackgroundAgentModel.turnOn()` dan `start()`, yang hanya dipanggil tombol Turn On dan Start stacklyd. Muncul nya langkah Background Agent hanya memicu `refresh()`; Continue, Not Now, Back, titik langkah, Escape, dan Get Started tidak memanggil model agent sama sekali. Penantian daemon yang bisa dimulai refresh itu (state menjadi `enabled` di luar aksi, spec 0015) hanya memanggil `DaemonModel.systemRetry()`, tidak pernah OS.
- File di home hanya berubah lewat tombol aksi konfirmasi `CommandLineToolPrompts`; `requestInstall()`, `requestRepair()`, dan `requestRemove()` hanya membuka prompt.
- Start stacklyd hanya ditawarkan saat daemon tidak ada (`ipc.endpoint_missing` atau `ipc.connection_refused`), tidak pernah untuk daemon yang macet, sedang berhenti, atau tidak kompatibel.
- Satu satunya yang ditulis onboarding sendiri adalah `onboarding.finished`, dan hanya oleh Get Started dan Escape.
- Teks onboarding tidak pernah menyatakan provider disandbox, tidak bisa membaca file user, atau catalog terbaru, dan tidak menyebut fitur atau perintah yang tidak ada di build itu.
- Nilai `STACKLY_ROOT` tidak pernah tampil.
- Onboarding tidak pernah menyentuh jaringan atau meminta akun.

### Security model

- Batasnya tetap satu akun user (BR-012). Onboarding tidak membaca atau menampilkan secret, tidak membuat ID atau path, dan tidak menjalankan proses (aturan sumber spec 0013 tetap berlaku untuk folder `Onboarding/`).
- Persetujuan background tetap milik macOS: onboarding hanya membaca status dan membuka Login Items saat pengguna menekan tombolnya (spec 0015).
- Instalasi CLI hanya lewat `CommandLineTool` dengan konfirmasi, sehingga aturan symlink spec 0015 (hanya link terkelola di home, tanpa admin, tanpa PATH atau file shell) berlaku tanpa pengecualian.
- `onboarding.finished` bukan data sensitif; mengubahnya dari luar hanya membuat onboarding tampil atau tidak.
- Copy yang jujur adalah bagian dari model keamanan: AC-061 meminta pengguna tidak dibuat percaya ada sandbox yang tidak ada (BR-012, BR-020, REQ-032).

### Configuration required

- Tidak ada variabel environment, secret, atau credential baru. Key `UserDefaults` `onboarding.finished` (lihat *Model data*) bisa diset lewat argumen launch untuk run manual.

## Consequences

**Positive**:

- Onboarding tidak punya jalur efek samping sendiri: semua aksi lewat model fitur 15 yang sudah diuji, jadi aturan "izin tidak diubah tanpa sepengetahuan pengguna" tetap satu tempat.
- Melewati dan membuka lagi aman secara konstruksi, karena satu satunya yang ditulis onboarding adalah preferensi GUI.
- Teks isolasi dan trust yang jujur ditulis sekali dan dijaga test, sehingga AC-061 untuk onboarding bisa diperiksa mesin dan manusia.
- Onboarding tetap berguna saat daemon belum berjalan (kasus normal di peluncuran pertama): Storage memakai default spec 0004 dan Catalog Trust menjelaskan bahwa detail muncul setelah stacklyd berjalan.
- Tidak ada perubahan protokol, Rust, atau CLI, jadi fitur ini tidak menahan atau ditahan program foundation selain shell dan model GUI.

**Negative / tradeoffs**:

- Onboarding menggantikan shell di jendela utama, jadi selama tampil banner daemon dan sidebar tidak terlihat; status daemon hanya tampil di langkah Background Agent.
- Tidak ada tombol Skip yang terlihat; melewati sekaligus hanya lewat Escape atau titik langkah terakhir lalu Get Started. Pengguna mouse yang tidak tahu Escape tetap perlu dua klik.
- Record di `UserDefaults` hilang kalau preferensi app dihapus, dan onboarding tampil lagi; tidak ada yang rusak, tetapi itu bisa membingungkan.
- Toggle yang bekerja lewat konfirmasi sedikit tidak biasa: toggle tidak langsung berubah saat diklik, baru setelah konfirmasi.
- Copy berbeda dari mockup di beberapa tempat (isolasi, catalog, CLI, Environments), jadi mockup perlu catatan selisih sampai diperbarui.
- `OnboardingCopy.commandExamples`, `runtimeInstallAvailable`, dan baris Welcome bergantung pada fitur lain menambah atau menyalakan barisnya; kalau fitur itu lupa, onboarding tetap jujur tetapi lebih sedikit isinya.
- Langkah 2 berbagi empat file dengan langkah 16 fitur 13, jadi milestone 1 menunggu langkah itu dan, lewat langkah itu, milestone 2 fitur 10 (K18); onboarding tidak bisa dibangun lebih awal dari shell yang lengkap.
- Path Storage saat daemon belum pernah berjalan dihitung GUI dari aturan spec 0004 tanpa fixture bersama; kalau aturan itu berubah, dua tempat harus diubah.
- *(2026-10-22)* Kartu Background Agent bergantung pada `DaemonModel.agentBannerInput`, `unreachableCode`, dan `DaemonBanner.ticksEverySecond` dari spec 0013 dan 0015, jadi perubahan aturan banner ikut mengubah kartu; itu disengaja (banner dan kartu tidak pernah berbeda), tetapi test kartu perlu dijalankan ulang setiap kali banner berubah.
- *(2026-10-22)* Onboarding punya satu pengumuman state sendiri (`not_found`, dengan judul banner nya), di luar announcer `DaemonModel`. Ia hanya mungkin terjadi karena banner jendela tersembunyi selama onboarding; kalau suatu hari banner ikut tampil di onboarding, pengecualian itu harus dihapus supaya tidak terdengar dua kali.
- *(2026-10-22, langkah 12a spec 0015)* Syarat pengumuman `not_found` dihitung di dua tempat dengan fungsi yang sama tetapi pada saat yang sedikit berbeda: `DaemonModel` saat `didAssess`, onboarding pada render berikut nya (`onChange`). Transisi presence yang jatuh tepat di antara keduanya bisa membuat `not_found` tidak terdengar atau terdengar dua kali. Itu butuh dua kejadian main actor dalam satu siklus render, setelah panggilan OS yang hanya terjadi lewat Turn On atau Start stacklyd, jadi diterima; menutup nya butuh `DaemonModel` menerbitkan keputusan nya sendiri, yang mengubah spec 0015 untuk kasus yang hampir tidak mungkin.
- *(2026-10-22, langkah 12a spec 0015)* Turn On yang hasil `not_found` nya datang setelah jendela utama ditutup (Command W), selagi daemon tidak ada, tidak terdengar: `DaemonModel` diam karena baris agent banner akan tampil, dan baik `OnboardingFlow` maupun `StateBanner` tidak sedang dirender. Membuka jendela lagi juga diam, karena pemicu nya tanpa `initial`. Celah yang sama ada untuk banner critical mana pun di shell yang jendela nya tertutup, jadi diterima; kartu dan banner tetap menampilkan `not_found` saat jendela dibuka.
- *(2026-10-22, langkah 12a spec 0015)* Pengumuman `not_found` dari onboarding bisa terdengar di langkah Welcome, Storage, Catalog Trust, atau Command Line, kalau pengguna pindah langkah selagi Turn On berjalan. Itu disengaja (banner yang digantikan juga tersembunyi di semua langkah), tetapi pengguna mendengar state agent di luar langkah nya, sama dengan pengumuman `DaemonModel` lain selama onboarding.
- *(2026-10-22)* Setelah Turn On berhasil, progress di kartu bisa bertahan sampai 30 detik (sebelum handshake) atau sepanjang snapshot pertama (sesudah nya). Pengguna tetap bisa Continue atau Escape; penantian selesai sendiri di model.

**Neutral**:

- Jendela utama kini punya akar `MainWindowRoot`; `LiveShell` dihapus, dan `AppShell` tidak lagi memegang accessor jendela, `windowOpener`, atau `windowWillClose`.
- Satu key `UserDefaults` baru di domain app.
- Item menu Help ditambah sekarang dan dipindah ke `StacklyCommands` dan `CommandMap` spec 0069 saat fitur 69 dibangun.

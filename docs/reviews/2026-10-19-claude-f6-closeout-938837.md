## Review, claude/f6-closeout-938837 (feature 6, part 1 of 3: contract and codec), 2026-10-19

**Reviewed by**: Sonnet 5.5 (author on Opus 5.5)
**Scope**: 41 files, branch vs main (merge base 859afaf): `crates/protocol` (src, tests, Cargo.toml), `xtask/src/codegen*`, `xtask/src/fuzz.rs`, `fuzz/fuzz_targets/ipc_*.rs`, `protocols/contract-versions.json`, `protocols/fixtures/ipc/index.json`, `typeshare.toml`, and the Swift contract files (`StacklyJSON.swift`, `Wire/`, `ClientErrorCatalog.swift`, `Generated/`).
**Verdict**: Changes requested

### Summary

The contract and codec are well built: a pure frame codec that checks the header before any payload buffer exists, a staged request decoder that recovers the `requestId` in nearly every failure, an error catalog that matches spec 0006 and the spec 0005 wire table entry for entry, open enums that fall back to `Unrecognized` in both languages, and a digest and version record that behave as the spec describes. `cargo test -p stackly-protocol` (90 unit tests plus the integration suites), `cargo clippy -p stackly-protocol --all-targets -D warnings`, `cargo check --target aarch64-pc-windows-msvc -p stackly-protocol`, `cargo xtask codegen --check` (19 files up to date), and the Swift contract suites (28 tests) all pass. The headline problem is that `request.invalid_params` has no bound on `fields`, so a roughly 32 KB `events.subscribe` makes the daemon build an error frame above the 1 MiB limit and drop the connection instead of answering. Behind it are a decode panic at the top of jiff's timestamp range, positional-array acceptance that lets a handshake slip past the major check, and a few gaps in what the digest and the fuzz targets cover.

### Major

#### 🟠 `request.invalid_params` has no bound on `fields`; a ~32 KB request makes the daemon drop the connection, `crates/protocol/src/events.rs:200` [contract]
**Problem**: `SubscribeParams::validate` pushes one `FieldError` for every bad `kinds` entry, even after it has already reported `kinds: too_many`, and neither `ErrorBody::with_fields` (`error.rs:166`) nor `decode_params` (`json.rs:383`) caps the list. I ran `decode_request` on a request whose `kinds` is N copies of `""`: 100 000 entries (300 KB) give a 9.99 MB error frame, and 349 000 entries (the largest request a 1 MiB frame can carry) give 349 001 `FieldError`s and a 35.1 MB frame. Each field costs about 100 bytes of JSON, so about 10 500 bad entries (a ~32 KB request) already push the error above `CONTROL_FRAME_MAX`.
**Why it matters**: On the daemon, `on_frame` (`apps/daemon/src/connection.rs:644-657`) enqueues that frame as is. The `ipc.reply_too_large` substitution exists only for dispatched replies (`connection.rs:756-766`). The writer then calls `FrameWriter::write_frame`, whose `encode_frame` returns `TooLarge` before anything is written, and `write_loop` (`connection.rs:429-446`) breaks and closes the connection. The client gets no error frame at all, contradicting AC-7 ("daemon menjawab dengan error dan koneksi tetap hidup") and the spirit of NFR-004 (bounded output for bounded input). Each such request also allocates tens of MB transiently. The peer is same-uid, so this is not a security boundary issue, but it is an unbounded output on the contract's own decode path, and every spec that adds a `Validate` impl inherits it.
**Suggested fix**: Cap the number of field errors in one central place (for example drop everything past 32 entries inside `decode_params` or `ErrorBody::with_fields`), and make `SubscribeParams::validate` check at most the first `SUBSCRIBE_KINDS_MAX` entries when `kinds` is already `too_many`. Add a test that a 349 000-entry `kinds` still yields an error frame under `CONTROL_FRAME_MAX`, and extend the `request_decode` fuzz harness with the same size assertion (it currently asserts only that the rejection uses a catalog code).

### Minor

#### 🟡 `Timestamp::from_jiff` panics for the last second of jiff's range, so decoding a valid RFC 3339 string can panic, `crates/protocol/src/wire.rs:146` [contract]
**Problem**: `from_jiff` truncates with `jiff::Timestamp::from_millisecond(instant.as_millisecond()).expect(...)`. `from_millisecond` accepts at most 253402207200000 ms (`9999-12-30T22:00:00.000Z`), but `as_millisecond` of `9999-12-30T22:00:00.001Z` through `jiff::Timestamp::MAX` is above that. Verified by a scratch probe: `"9999-12-30T22:00:00.001Z".parse::<Timestamp>()`, `Timestamp::from(jiff::Timestamp::MAX)`, and `decode_server_frame` on an event whose `at` is that string all panic with "an instant truncated to the millisecond stays in jiff's range". The `expect` message names an invariant that is false.
**Why it matters**: A decode path must not panic. Today the only way in is a hostile daemon on the socket the CLI already trusts, so impact is low. It becomes a daemon crash path the moment any spec puts a `Timestamp` in request params (spec 0007 filters, for example), and AGENTS.md allows `expect` only for true invariants.
**Suggested fix**: Truncate with `jiff::Timestamp::new(instant.as_second(), (instant.subsec_nanosecond() / 1_000_000) * 1_000_000)`, which stays in range at both ends, and add boundary tests for `Timestamp::MIN`, `Timestamp::MAX`, and `9999-12-30T22:00:00.001Z`.

#### 🟡 Positional JSON arrays are accepted for every object, and `protocol: [2,0]` passes the handshake with major 2, `crates/protocol/src/json.rs:246`, `apps/daemon/src/connection.rs:497` [contract]
**Problem**: `RawHead`, `RawCall`, and every params struct use serde derives, which also accept a JSON array read positionally. Verified: `["abc", null, {"type":"daemon.get_info"}]` and `{"requestId":"abc","call":["daemon.get_info"]}` both decode as valid requests (AC-7 wants `request.malformed` for a wrong shape). The same leniency opens a hole in the AC-1 major check. The daemon decides the mismatch only from `json::handshake_major`, which cannot read a `protocol` given as an array (it returns `None`), and then falls through to `decode_request`, where `ProtocolVersion` accepts `[2,0]` as `{major: 2, minor: 0}`. I confirmed `handshake_major == None` and `decode_request` returns `Ok` with `protocol.major == 2`. The daemon never re-checks `params.protocol.major` after the decode (`ProtocolVersion::is_compatible_with` is not called anywhere in `apps/daemon`), so `accept()` replies `HandshakeAccepted` to a major 2 client.
**Why it matters**: No honest client sends arrays, so this needs crafted input from a same-uid peer. It is still a gap between the spec's rule and the code, and it is the kind of difference between two parsers that the fuzz harness cannot see.
**Suggested fix**: Reject non-object tops for `RawHead`, `RawCall`, and params (for example a small `deny_seq` wrapper, or a quick check that the first non-space byte of each raw value is `{`), and have the daemon also check `params.protocol.is_compatible_with(CURRENT)` after the decode so the two readers can never disagree. The daemon half is in `apps/daemon` (other reviewer).

#### 🟡 No fuzz target covers the client side `decode_server_frame`, which is how the `Timestamp` panic went unseen, `crates/protocol/src/fuzzing.rs:70`, `xtask/src/fuzz.rs:82` [contract]
**Problem**: Both IPC targets exercise the daemon side (`FrameDecoder`, `decode_request`). Nothing feeds random bytes to `decode_server_frame`, which is where `Timestamp`, `Uuid`, `Sequence`, the open enums, and the event probe are decoded from data the client does not control.
**Why it matters**: The panic above is exactly what such a target finds in seconds. Spec AC-14 asks for two targets, so this is a coverage gap rather than a spec violation, but the review brief for this change named decode soundness explicitly.
**Suggested fix**: Add a `server_frame_decode` harness (no panic, and a `DecodedFrame::Response/Error/Event` result re-encodes and decodes to the same value) as `ipc_server_frame_decode`, seeded from the `ServerFrame` fixtures in `index.json`.

#### 🟡 The digest does not cover wire constants or validation rules, so a lowered limit passes `--check`, `xtask/src/codegen/contract.rs:230`, `crates/protocol/src/limits.rs:11` [contract]
**Problem**: The digest hashes the normalized schemas and the catalog. The schemas carry types only: `Limits` has `maxFrameBytes: uint32` but not 1 048 576, `Timestamp` is `format: date-time` with no hint of the three-digit form, and `Validate` rules (`client.version` 1 to 64 bytes, at most 32 `kinds`, `requestId` and `idempotencyKey` formats) are not schema keywords at all. I confirmed by grep that neither 1048576 nor 65536 appears in `protocols/schemas/`. Spec 0006 says lowering a limit is a major bump and raising one a minor bump, yet changing `CONTROL_FRAME_MAX`, `MAX_JSON_DEPTH`, `REQUEST_ID_MAX`, or tightening a `Validate` rule leaves the digest, and therefore `contract-versions.json` and `contractDrift`, untouched.
**Why it matters**: The check that is supposed to force a version bump on a wire change misses a class of wire changes that the spec itself calls out. This is outside the literal definition in the spec ("semua schema ... dan katalog error"), so it is a spec gap as much as a code gap.
**Suggested fix**: Add one small normalized object to the digest input (`Limits::CURRENT`, `REQUEST_ID_MAX`, `IDEMPOTENCY_KEY_MAX`, `MAX_SAFE_INTEGER`, `SUBSCRIBE_KINDS_MAX`, `CLIENT_VERSION_MAX`, the frame header width), and update spec 0006 to say so. This moves the digest, so it needs a `--amend` of 1.2 while 1.2 is not on main.

#### 🟡 `retryable` is required on `ErrorBody` although the frozen part of the envelope does not include it, `crates/protocol/src/error.rs:105`, `Generated/StacklyProtocol.swift` `ErrorBody.retryable` [contract]
**Problem**: The spec freezes `code`, `category`, `message`, and `details` so that daemons and clients of any major can exchange `protocol.major_mismatch`. The decoders (Rust `retryable: bool`, Swift `retryable: Bool`) also require `retryable`; the schema lists it under `required`. A major 2 daemon that drops or renames `retryable` makes a major 1 client fail the mismatch frame as `ipc.protocol_violation`.
**Why it matters**: The freeze exists to guarantee a clean mismatch message across majors, and this field quietly extends the frozen set by one without saying so. It is latent today.
**Suggested fix**: Mark `retryable` `#[serde(default)]` (false is the safe value), so an old client needs only the four frozen fields; or add `retryable` to the frozen list in spec 0006. Either choice moves the digest, so amend 1.2 while it is not on main.

### Nits

- ⚪ `xtask/src/codegen/contract.rs:55`, normalization keeps array order, so reordering struct fields (`required`) or enum variants (`oneOf`) changes the digest although the wire does not change; sorting `required` (and `oneOf` entries by their `const`) would make the digest answer only wire questions. A doc comment change is correctly ignored (I checked `description` on a `$ref` field, an `Option` field, a `Vec` field, and enum variants under schemars 1.2.3).
- ⚪ `clients/swift/Sources/StacklyClient/Wire/ServerFrameDecoder.swift:48`, Swift reads `sequence` and `revision` as plain `UInt64`, so a frame with `sequence` 2^53 is accepted in Swift and rejected in Rust (`frame-event-sequence-too-large.json` is `langs: ["rust"]`). Harmless against a correct daemon; worth one line in `clients/swift/AGENTS.md` as a known parity gap.
- ⚪ `clients/swift/Sources/StacklyClient/StacklyJSON.swift:40`, `string(from:)` rounds to the nearest millisecond while Rust `Timestamp::from_jiff` truncates; no contract type carries a Swift made `Date` to the daemon today, so it is only a note for later specs.
- ⚪ `clients/swift/Sources/StacklyClient/Connection/ClientErrorCatalog.swift:84`, the doc lists `op` values `read` and `write`, but spec 0006 (and every call site) uses only `stat` and `connect`; `ipc.io_error` is `retryable: true`, which is only true before a byte is sent, so keeping the doc to those two ops avoids a false retry promise.
- ⚪ `crates/protocol/src/message.rs:227`, `every_method_in_the_table_is_the_serde_tag_of_a_call_and_a_reply` skips parameterised variants whenever `content: null` fails to decode, so a swapped table row between two parameterised methods is not caught by this test (the codegen `contract_names` order check does catch it, so the risk is covered elsewhere).
- ⚪ `xtask/src/fuzz.rs:207`, every failure of `cargo fuzz run` is reported with "the crashing input is in fuzz/artifacts/...", including a plain build error.

### Strengths

- `FrameDecoder` keeps the header check before any payload allocation, hands out the frames before a refused header, and its buffer bound is asserted in both a unit test and the fuzz harness; I measured that byte by byte feeding of a 1 MiB frame still takes about 30 ms, so `reserve_exact` is not a performance problem on macOS.
- `decode_request` keeps `content` raw so key order never matters, recovers the `requestId` for `too_deep`, `malformed`, `unknown_method`, and `invalid_params`, never forwards serde's text (the `secret-sentinel` tests prove it), and only echoes a method name that is short printable ASCII.
- `ErrorBody` is only built through the catalog, its message truncation counts characters and cuts on a boundary, and the catalog test list (pattern, duplicates, area, detail keys, items, retryable set) plus the exact registry table test make drift loud. The Swift `ClientErrorCatalog` entries match the Rust catalog in code, category, `retryable`, and `details` keys, and a Swift test compares them with `protocols/error-codes.json`.
- Open enums are handled the same way in both languages (`#[serde(other)]` and the generated `OpenEnums.swift`), unknown event kinds become `SkippedEvent` before the full decode in Rust and Swift alike, and unknown item kinds decode because `kind` and the field keys are plain strings. Fixtures cover each of these, including an error frame with every optional field filled and empty.
- The version record and digest tooling is careful: `--amend` is the only way to change a recorded digest, a recorded version above `CURRENT` fails, nothing is written when the version check fails, `cli` codes are excluded as the spec says, and the history of 1.0 to 1.2 matches the commits that moved the digest.

### Test coverage

Well covered: the frame codec (two frames in one chunk, every two way split, byte by byte, exact max and max plus one, header above the limit), the staged decoder stages and their error codes, the catalog invariants, `ErrorBody` truncation and `items` handling, wire newtype bounds at 2^53 − 1, the version record rules (add, keep, refuse, amend, higher version, missing entry), `swift.rs` parsing of typeshare output, fixture roundtrips in both languages against one shared `index.json`, and seed and regression replay on stable.

Gaps, in order of weight: no test or fuzz assertion bounds the size of an error reply (Major above); no boundary tests for `Timestamp` (Minor above); no test that an array shaped request or handshake is refused (Minor above); no fuzz target for `decode_server_frame`; no test that digest input changes when a limit or validation bound changes; `fuzz_regressions/` is empty (expected, nothing crashed), so the replay of crash inputs is only exercised through seeds. I did not run the 5 minute fuzz campaigns (AC-14 evidence) and I did not review `provider_versions.rs` or the provider fuzz targets in depth (feature 9, outside this part).


## Review, claude/f6-closeout-938837 (part 2 of 3: the stackly-ipc transport), 2026-10-19

**Reviewed by**: Sonnet 5.5 (author on Opus 5.5)
**Scope**: 16 files in `crates/ipc` (3,250 added lines) plus the ipc rules in `xtask/src/check_deps.rs` and the socket scan in `xtask/src/check_deps/source_scan.rs`, branch vs `main` (merge base 859afaf)
**Verdict**: Approve with nits

### Summary

`stackly-ipc` is a careful, well-tested transport. The trust rules are pure and shared with Swift through a fixture, the client never writes before `verify_path` and `verify_peer` pass (and the peer check closes the check-to-connect gap), unreadable credentials fail closed on both sides, the frame reader allocates only after the header is checked and keeps the `max_len + 4 + READ_CHUNK` bound, and bind goes through a `.tmp` name, chmod, then rename so the final path is never visible with another mode. I found no blocker and no major. The real issues are client robustness under cancellation and slow consumption (a cancelled call can truncate a frame on the wire; a full event queue stalls replies), plus a few minor ordering, coverage, and scan gaps. `cargo test -p stackly-ipc` (47 tests, 40 extra runs of the transport suite, no flake), `cargo clippy -p stackly-ipc --all-targets -D warnings`, `cargo fmt --check`, `cargo xtask check-deps`, and the xtask check_deps tests all pass. Nothing in the repo was modified; experiments ran in a scratch copy.

### Blockers

None.

### Major

None.

### Minor

#### 🟡 A call cancelled in the middle of its write poisons the connection, `crates/ipc/src/unix/client.rs:343`

**Problem**: `request` does `self.writer.lock().await.write_frame(&payload).await`, and `write_frame` is `encode_frame` + `write_all` (`connection.rs:238-247`). `write_all` is not cancel safe. The doc on `Pending` (client.rs:192-203), the `call` docs, and the test `a_call_dropped_by_a_timeout_does_not_disturb_later_calls` all present dropping a `Client::call` future (for example by `tokio::time::timeout`) as safe, but the test only cancels while waiting for the reply, never while the frame is half written. If the future is dropped after some bytes of a frame went out, the tokio mutex is released, the next call writes its own header and payload in the middle of the old frame, and the daemon reads a corrupt stream.

**Why it matters**: The trigger needs a full socket buffer (macOS `net.local.stream.sendspace` is 8192 here), so either a request of more than about 16 KiB (allowed up to 1 MiB) or a daemon that stopped reading, which is also the moment a caller's timeout fires. I reproduced it in a scratch copy: a 540 KB `events.subscribe` cancelled after 200 ms against a daemon that was not reading, then a small second call. The daemon saw an incomplete frame that never completed ("idle"), the second call was never answered, and the connection only ended when the daemon gave up (in production, `ipc.frame_stalled` after 30 s, or the client's next call fails with `ipc.connection_closed`). Spec 0008 AC-9 has the Waiter retry `ipc.call_timeout` calls on the same connection, so this is a latent trap for feature 8, not for the one shot `daemon status`. Related: the write itself has no deadline, so while a stalled daemon does not read, every other call queues on the writer mutex and relies on the caller's timeout.

**Suggested fix**: Make a frame write uncancellable by the caller. Either hand each encoded frame to one writer task through a bounded `mpsc` (the task finishes a frame even when the caller is dropped, and the caller only awaits the reply), or `tokio::spawn` the write and await its `JoinHandle`. A cheaper alternative is a "write in progress" flag set before `write_all` and cleared after; if a future is dropped while it is set, close the connection with `Closed::Error` so later calls fail fast instead of hanging. Add a test that cancels a large write and then calls again.

#### 🟡 A full event queue blocks every reply behind it (head of line blocking), `crates/ipc/src/unix/client.rs:438-451`

**Problem**: `deliver` does `sender.send(event).await` on a 1024 slot queue. While the stream owner is not draining, the single reader task is parked there and no later frame, including the response a waiting `call` needs, is processed. This is documented in the `subscribe` docs, but spec 0006 and spec 0008 both say `call` may run while an `EventStream` is alive, which is exactly the shape that deadlocks: one task that holds the stream and `await`s a call before it drains. Reproduced in scratch: subscribe, daemon sends 1100 events then a reply, the consumer calls `events.unsubscribe` without draining; the call timed out after 3 s, and 1100 events were drained afterwards.

**Why it matters**: It needs more than 1024 events queued ahead of the reply, so it is a corner (after an `overflow` gap the daemon's own 64 frame outbound queue plus socket buffers keep the backlog below that). When it does happen the call hangs until the caller's timeout, and a retry in the same loop hangs again.

**Suggested fix**: Pick one. (a) `try_send`; on `Full` drop that subscription's sender and let `EventStream::next` end with an explicit local "overflow" outcome (mirrors the daemon's own slow subscriber rule, which is gap plus resnapshot; a new catalog code would be a [contract] change, a synthetic `events.gap overflow` event would not), or (b) keep the blocking design and state in the `Client::call` docs that the stream must be drained by another task. Add a test for whichever is chosen.

#### 🟡 Coverage gaps on the error branches that matter most, `crates/ipc/tests/transport/`

**Problem**: The suite is strong on the happy path and on the spec's critical scenarios, but these branches have no test: (1) `close_with_error` actually hitting `REJECT_WRITE_TIMEOUT` (`rejected_peers_that_never_read...` sends a tiny frame that fits the socket buffer, so the timeout never fires; fill the peer's buffer first and assert `Io{write, timed_out}` after 1 s on a paused clock); (2) a cancelled write (see the first finding); (3) the full event queue (second finding); (4) `Client` drop ending a live `EventStream` (`Closed::Local`) and `EventStream` drop followed by more events for that id; (5) `Shared::fail` and `deliver` for unknown request ids and unknown subscription ids; (6) `Listener::unlink_if_own` and `bind` error ops (`unlink`, `chmod`).

**Why it matters**: Item 1 is the one spec AC-2 promises ("a client that does not read the rejection frame does not hold the accept loop"); today only the accept loop half is proven, and the bound on the spawned task is not.

**Suggested fix**: Add tests 1, 4 and 5 now; 2 and 3 with their fixes.

#### 🟡 The `ipc.io_error` mapping can mark a possibly executed request retryable, `crates/ipc/src/error.rs:43-47,111-115` [contract]

**Problem**: The catalog entry is "client side: another os error while checking the socket path or connecting", `retryable true`. `IpcError::Io` also carries the ops `read`, `write`, `accept`, `bind`, `chmod`, `rename`, and `unlink`, and `to_error_body` maps all of them to the same retryable code. Today the `Client` never surfaces read or write errors (it maps them to `ipc.connection_closed`, which is correctly not retryable), and the CLI only converts errors from `Client::connect`, so this is not reachable on the wire. But `FramedConnection` is public API and `to_error_body` is a one line call away.

**Why it matters**: A future caller (feature 8 Waiter, tests, a GUI bridge) that reports a mid request `Io{write}` through `to_error_body` tells the user it is safe to retry a request that may have run, which breaks the "retryable only when the request is guaranteed to have had no effect" invariant.

**Suggested fix**: In `to_error_body`, map `Io` with op `read` or `write` to `ipc.connection_closed` (details empty), keep `ipc.io_error` for `stat`, `connect`, and the daemon-only ops, and widen the catalog description for `ipc.io_error` to say the daemon side uses it too (the catalog text is in `crates/protocol/src/codes.rs`).

### Nits

- ⚪ `crates/ipc/src/unix/listener.rs:319-332`, `bind_private` renames the socket to its final path before the fallible steps that do not need the path (`FileIdentity::of(path)`, `set_nonblocking`, `UnixListener::from_std`). If one of them fails, `bind` returns `Err` but a published 0600 socket nobody listens on stays at `path`; in `rebind` the old listener stays live on an unlinked inode and `check_bound` then reports `Replaced` until the next 10 s check rebinds (self healing, so low impact). Do `set_nonblocking` and `from_std` first, record the identity from the temp name before the rename (rename keeps dev and inode, and it avoids stat-ing a path that could have been swapped), and publish last.
- ⚪ `crates/ipc/src/unix/connection.rs:161-177`, the stall timer starts at the arrival time of the chunk that holds the tail of the next frame, so it also counts time the local consumer spent not reading. With a partial tail buffered, a consumer that is away for more than 30 s and then finds the peer's remaining bytes not yet readable on the first poll gets `FrameStalled` immediately (reproduced on a paused clock with a synthetic peer; a more realistic run, 60 times with a daemon blocked mid write and a consumer that slept 40 s, always recovered, because the socket buffer is full of data by then). Starting the timer when the reader begins waiting for the rest of a frame (`frame_started.get_or_insert(now)` right before the read when `buffered() > 0`) measures the peer instead of the local task.
- ⚪ `crates/ipc/src/unix/client.rs:397-402`, after `client.call(Call::EventsUnsubscribe(..))` succeeds, the local sender stays registered, so `EventStream::next()` waits until the connection ends. Likewise a `subscribe` cancelled after the daemon replied leaves a daemon side subscription (one of 8) whose events are then dropped (`answer`, line 113, finds no waiter). A small `EventStream::unsubscribe(self, &Client)` that calls the daemon and closes the local queue would remove the trap.
- ⚪ `crates/ipc/Cargo.toml:15`, `macros` in the normal tokio features is unused by `src/` (`cargo check -p stackly-ipc --lib` passes without it); it is already listed for `[dev-dependencies]`.
- ⚪ `xtask/src/check_deps/source_scan.rs:243-255`, the socket rule compares `ident == "TcpListener"`, which `proc_macro2` evaluates as false for a raw identifier, so `std::net::r#TcpListener::bind(..)` is not reported (confirmed with a scratch test). **Reviewed by**: Claude Sonnet 5.5 (author on Claude Opus 5.5)

**Verdict**: Changes requested

### Summary

The daemon and CLI implement spec 0006 closely. The start order (lock, then log file, then socket, then registry), the handshake phase, the per connection limits, the event bus (subscribe, ring and receiver opened under one lock), recovery gating, the stop order and the CLI exit codes all read correct end to end, and I found no blocker and no [contract] issue. The one Major finding is test coverage: several error and branch paths that decide whether the daemon stays up or exits have no test at any level (periodic prune and the registry fatal path, the socket check failure and `Replaced` branches, the accept error backoff). The Minor findings are robustness gaps around an unread stderr pipe starving the file log, the stop flush windows adding up to three times the spec bound, and a small drain registration race.

Verification I ran (nothing in the repo was modified): `cargo test -p stacklyd --locked` (72 unit, 8 `root_override`, 1 `second_daemon`, 8 `served`, 34 `server`: all pass), `cargo test -p stackly-cli --locked` (9 pass), `cargo clippy -p stacklyd -p stackly-cli -p stackly-testkit --all-targets --locked -- -D warnings` and `cargo fmt --all --check` (clean). I also ran four throwaway experiments against the real binary from the scratchpad (stderr pipe never read; 140 KB of requests pipelined behind a major 2 handshake; a regular file put at the socket path and removed again; a registry folder made unreadable): results are quoted in the findings below.

### Blockers

None.

### Major

#### 🟠 Error and branch paths that decide daemon liveness have no test, `apps/daemon/src/server.rs:645`
**Problem**: Nothing exercises these paths, in process or against the binary:
- `prune_loop` (server.rs:645-666): the periodic prune after `REGISTRY_PRUNE_INTERVAL` (AC-18) and the `Err(Unavailable)` arm that calls `registry_failed` (server.rs:670-674) and makes the daemon stop with exit 1 (step 11 of *Urutan start*). `DaemonConfig::prune_interval` exists for tests but no test sets it.
- The start slot arms `Some(Err(StorageError))` and `None` (server.rs:577-585) and `Unavailable` from the first prune (server.rs:533-536). `startup::serve` selecting on `handle.fatal()` (startup.rs:302) is never reached by a test.
- `check_socket` failure branches (server.rs:481-509): `ensure_runtime_root` failing, `rebind` failing, and the `BindState::Replaced` case. AC-11 says rebind failure makes subsystem `ipc` `unavailable`, status `degraded`, and retries at the next check; `DaemonCore::set_ipc_problem` and the matching branch in `DaemonCore::health` (state.rs:354-359) are never driven. The existing rebind tests only cover `Missing`.
- The accept error arm and `ACCEPT_BACKOFF` doubling (server.rs:453-463).
- The `Accepted::Rejected` arm of the accept loop (server.rs:437-451): log fields `peer_uid` and `peer_pid` and the two counters are only tested at `crates/ipc` level (there is no way to inject a uid or a `PeerCredSource` through `DaemonDeps`).

**Why it matters**: These are the branches that turn a degraded condition into either a quiet degraded daemon or a daemon that exits. A regression in any of them (for example `registry_failed` no longer calling `fail`, or the ipc problem never clearing after a successful rebind) would pass the whole suite. I did exercise two of them by hand and both behave per spec: with a regular file at the socket path the daemon logged `ipc.endpoint_occupied` ("cannot bind the socket again") and recovered after the file was removed (`socketRebinds` 1, `ipc` `ok`); with `data/registry` at mode 000 the daemon logged "cannot open the registry", stopped with the full stop order and exited 1 in 20 ms. Those checks are not repeatable evidence, though.
**Suggested fix**: Add in process tests in `tests/server/lifecycle.rs`: a short `prune_interval` that shows a second "registry history pruned" line; a registry made unusable after start (or a `DaemonConfig` hook that injects the prune error) to prove `fatal()` resolves with 1 and the stop order runs; a regular file placed at the socket path with a short `socket_check_interval` to assert `ipc` `unavailable` + `degraded`, then recovery when the file is removed; and a unit test of `DaemonCore::health` with `set_ipc_problem`. For the peer rejection log and counters, let `DaemonDeps` (or `DaemonConfig`) take the expected uid or a `PeerCredSource`, as AC-2 already does for the listener.

### Minor

#### 🟡 A stalled stderr pipe silences the file log, `apps/daemon/src/log_sink/mod.rs:403`
**Problem**: `Writer::write` writes stderr first (`write_all` at line 404, blocking) and the rotating file second (line 407), on one thread. If stderr is a pipe nobody reads, the thread blocks in the first call, so nothing reaches the file after the pipe buffer fills. Verified: daemon started with `stderr=PIPE` and never read, then 120 `stackly daemon status` calls: `stacklyd.log` grew to 65 307 bytes (the pipe buffer) and stayed there while the daemon kept answering; on SIGTERM the final lines ("stacklyd stopped") never reached the file, and the stop took the full 1 s flush timeout.
**Why it matters**: AC-12 and the spec test only require that requests are not held, and that holds. But the file log is the persistent diagnostic channel, and it goes dark in exactly the situation where someone starts to look at it. Feature 15 (`stackly daemon start`) and the app will launch the daemon with some stderr arrangement; a `Pipe` that is not drained is a common mistake.
**Suggested fix**: Write the file sink before stderr in `Writer::write`, so a blocked stderr cannot starve the file; or give stderr a non-blocking write (nonblocking fd, or its own small queue and thread). Add a test: stderr gate closed, file sink installed, lines still reach the file.

#### 🟡 The stop flush can take three times the spec bound, and the forced stop still waits for the registry close, `apps/daemon/src/connection.rs:86`
**Problem**: `Connections::close_all` gives each of three phases its own window: wait for subscriptions to queue `daemon.shutting_down` (up to `flush`), wait for connections to send `Out::Close` and end (up to `flush`), then close all and wait again (`REJECT_WRITE_TIMEOUT`). Worst case is about 3 s after the 5 s drain, while the spec says the flush takes at most 1 s (step 5) and the critical test scenario expects exit within 7 s. Separately, on a second signal `DaemonHandle::shutdown` skips the drain and flush but still awaits `spawn_blocking(drop(registry))` (server.rs:354-358); if the registry thread is slow to checkpoint, the "jump to step 6" can wait indefinitely, and a third signal is not handled.
**Why it matters**: Only a subscriber that stops reading while events are being published reaches the long path today (nothing publishes yet except `daemon.shutting_down`), so this is latent. It will matter once feature 7 and 10 publish events.
**Suggested fix**: Compute one `deadline = now + flush` at the top of `close_all` and use it for all three waits. In the forced path, bound the registry close (for example `timeout(SHUTDOWN_FLUSH, ...)`) and let `runtime.shutdown_timeout` abandon it.

#### 🟡 A request can be admitted after the stop was observed by the drain, `apps/daemon/src/connection.rs:664`
**Problem**: `on_frame` checks `core.is_stopping()` (line 664) and only later calls `core.drain().enter()` (line 691). `stop_gracefully` does `mark_stopping()` then `drain().idle()`. On the multi thread runtime the stop can run between the two lines: `idle()` sees zero running requests and returns, then the request is counted and runs outside the drain.
**Why it matters**: The window is nanoseconds and the request still completes unless the process exits first, but it breaks the guarantee that every admitted request is drained (spec *Berhenti* step 4).
**Suggested fix**: Take the `DrainGuard` first, then check `is_stopping()`; if stopping, drop the guard and answer `daemon.shutting_down`. Either the stop sees the counter or the request sees the stop.

#### 🟡 A handler panic never reaches the log file with its message or location, `apps/daemon/src/connection.rs:879`
**Problem**: `guarded` turns a panic into `internal.unexpected` and logs `a handler failed` with `panicked = true`, which satisfies the spec line. The panic text and location, the only thing that identifies the bug, are printed by the default panic hook straight to stderr (unstructured, and not through the log writer, so not in `stacklyd.log`). The spec also says daemon code never writes logs directly.
**Why it matters**: Diagnosing a handler bug from the file log is impossible, and with the stalled-stderr case above the text is lost altogether.
**Suggested fix**: Install a panic hook in `startup` that emits `tracing::error!` with the location and the payload as `&str` (payloads are code strings, not request params), then call the previous hook only when no subscriber is set.

### Strengths

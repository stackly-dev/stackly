# /coordinate

Sesi ini adalah **lead**. Setiap pekerjaan dari alur berjalan di **sub sesi** aplikasi (linked session) dengan worktree dan branch sendiri; lead tetap di checkout utama (`main`), memilih SCOPE, membagi item, menjaga gerbang centang, merge branch yang hijau, dan menulis log. Lead tidak menulis kode produksi: file yang lead edit hanya file scope (SCOPE, file scope lain yang item prasyaratnya ditarik, dan `docs/scope/index.md`), log koordinasi, `CHANGELOG.md`, dan hasil `/document` serta `/sync`.

Butuh tool `mcp__ccd_session__start_session` (Claude desktop app). Bila tidak ada, berhenti dan katakan skill ini hanya jalan di aplikasi.

## Pemakaian

```text
/coordinate <scope> [tanya | tanya berat] [ketentuan tambahan]
```

- `<scope>`: `07`, `Scope 07`, `Scope 07 · Stack enam service`, judulnya saja, atau path file scope. `F41` atau `fitur 41` membatasi kerja ke satu fitur. Kosong: lead mengusulkan scope berikutnya dan menunggu konfirmasi.
- `tanya` atau `tanya berat`: memilih Mode keputusan (bagian "Mode keputusan"). Tanpa kata itu modenya `auto`.
- Ketentuan tambahan: teks bebas sesudahnya, yang menimpa bawaan di bawah untuk run ini saja (misalnya model lain untuk satu peran). Lead menyalinnya apa adanya ke baris pertama log Keputusan dan ke file aturan umum brief.

Bawaan setiap run, tanpa perlu disebut user:

- Sub sesi paralel untuk setiap item yang ownership-nya tidak beririsan, dengan model per peran dari tabel langkah 3.
- Rencana wave ditampilkan lalu langsung dijalankan.
- Debugger dimulai begitu gerbang merah karena test atau langkah verify.
- Keputusan mengikuti Mode keputusan, bawaannya `auto`: opsi rekomendasi diambil dan dicatat.
- Langkah yang hanya bisa dilakukan user masuk file manual, dan kotaknya tetap dicentang (bagian "Langkah manual").
- Fitur ditandai `done` saat kotak terakhirnya dicentang.

Run selesai bila setiap kotak SCOPE tercentang, atau tercatat di log "Blocker terbuka" dengan apa yang membukanya.

## Alur lead

### 1. Tentukan SCOPE

- Prasyarat: lead berada di checkout utama pada `main` (`git rev-parse --abbrev-ref HEAD` = `main`, `git rev-parse --show-toplevel` bukan di bawah `.claude/worktrees/`) dan folder skill ini sudah ter-commit di `main` (`git ls-files .claude/skills/coordinate | grep -q .`), karena worktree sub sesi hanya memuat commit `main`. Bila belum ter-commit, minta user commit dulu dan sementara itu andalkan butir "Checkout utama" di file aturan umum brief; bila bukan di `main`, berhenti dan minta user menjalankan `/coordinate` dari checkout utama.
- Model lead: `mcp__ccd_session_mgmt__get_session` dengan `"self"` harus menampilkan `model: claude-fable-5-2`, karena `start_session` diam-diam mengabaikan `model` di atas lead, sehingga sub sesi Fable di tabel langkah 3 akan turun kelas. Bila bukan Fable, minta user mengganti model sesi ini lewat pemilih model aplikasi (`set_session_model` menolak sesi sendiri), dan jangan mulai sub sesi sebelum itu. Effort lead di bawah `high` bukan alasan berhenti: effort lead hanya membatasi giliran pertama sesi baru, jadi pakai giliran `standby` di langkah 3.
- Pisahkan argumen menjadi tiga bagian (bagian "Pemakaian"): scope, kata mode, dan ketentuan tambahan. Catat mode dan ketentuan tambahan di header dan baris pertama Keputusan log.
- Scope berupa nomor, judul, atau keduanya (`07`, `Scope 07`, `Stack enam service`, `Scope 07 · Stack enam service`, `ui`): cocokkan nomor dengan awalan nama file dan judul dengan daftar di Konteks saat ini, tanpa membedakan huruf besar. Nomor dan judul yang menunjuk file berbeda, atau judul yang cocok dengan lebih dari satu file: berhenti dan sebut kandidatnya.
- Scope berupa path file: pakai file itu. Bila tidak ada, berhenti dan katakan.
- Scope berupa fitur (`F41`, `fitur 41`, atau nama fitur): cari file scope yang memuat heading `### <nomor>. <nama>`. SCOPE adalah file itu; kerja dibatasi ke fitur itu plus item fitur lain yang memblokirnya, yang ditampilkan di rencana dengan penyebabnya dan ikut masuk antrian.
- Scope kosong: baca "Urutan file" dan "Catatan urutan" di `docs/scope/index.md`, usulkan file paling atas di "Urutan file" yang masih punya kotak terbuka (hitungan di Konteks saat ini; `ui-macos.md` ikut sebagai jalur paralel), sebut aturan Catatan urutan yang relevan, lalu tunggu konfirmasi user. Analisis SIAP baru dilakukan di langkah 2.
- Buat `docs/scope/coordination/<nama-SCOPE>.brief-umum.md` dari `templates/brief-umum.md` dan `<nama-SCOPE>.manual.md` dari `templates/manual.md` bila belum ada, dan commit keduanya bersama log sebelum sub sesi pertama dimulai.
- Baca bagian Keputusan semua log di `docs/scope/coordination/` dan terapkan yang berlaku lintas scope (penomoran spec, pilihan cross check); catat ulang di log SCOPE ini dengan rujukan log asalnya.
- Bila `docs/scope/coordination/<nama-SCOPE>.log.md` ada, baca dulu, lalu cocokkan tiap baris tabel sub sesinya: (a) masih tampil di `list_sessions {"linked": true}` atau `ListAgents` → jangan mulai ulang; kirim `SendMessage` berisi alamat lead baru dan minta laporan ke sana; (b) sesi hilang tetapi branch-nya punya commit di depan `main` (`git log --oneline main..<branch>`) → perlakukan sebagai laporan `done` yang belum diperiksa lewat gerbang langkah 6, atau bila belum selesai mulai sub sesi pengganti dengan `source_branch: <branch lama>` dan brief yang menyebut commit terakhirnya; worktree kotor (`git -C <worktree> status --short`) → biarkan apa adanya, catat di "Blocker terbuka", dan item itu menunggu sampai user memilih commit `wip(...)` atau buang; (c) tidak keduanya → item kembali ke antrian. Catat hasilnya di log; bila heading atau kolom log lama berbeda dari `templates/log.md`, sesuaikan dulu.

### 2. Analisis dan rencana wave

Baca SCOPE beserta file scope lain yang dirujuk prasyarat kotaknya atau baris `_Catatan_`-nya (mis. `ui-macos.md` dari `01-foundation.md` dan sebaliknya), `docs/scope/index.md` ("Catatan urutan" dan "Legend"), `AGENTS.md` (root, plus `apps/macos/AGENTS.md` dan `clients/swift/AGENTS.md` bila Swift disentuh), dan dari tiap spec di baris **Pointer** hanya baris `**Status**`, daftar ID AC di `## Requirements`, `## Build plan` beserta paragraf "Sesi paralel", dan `## Follow-up`; untuk `verify.md` cukup judul bagian `## Milestone <n>` dan jumlah langkah terbuka. `rationale.md` tidak perlu. `grep -n '^<<<<<<<' docs/specs/<NNNN>/*.md` harus kosong untuk tiap spec yang dibaca; bila ada, fitur itu TERBLOKIR `spec rusak` sampai user memilih versi yang benar lewat item `architect (update)`.

Rekonsiliasi dulu dengan keadaan nyata, selalu, bukan hanya bila log ada:

- Sesi dan branch lain: jalankan `ListAgents`, `list_sessions` tanpa filter, dan `git branch --no-merged main`; petakan tiap sesi peer dan branch ke fitur dan milestone lewat judul, nama branch, subject `git log --oneline main..<branch>`, dan path `git diff --stat main...<branch>` dibandingkan `code in`. Item yang cocok ditandai **DIKERJAKAN DI LUAR KOORDINASI**, bukan SIAP. Bawaannya tunggu: lead tidak menyentuh sesi atau branch itu, dan saat branch-nya selesai lead memeriksanya lewat langkah 6. Ambil alih (lead mengirim brief lewat `SendMessage` dan memperlakukan laporannya seperti sub sesi) atau abaikan hanya atas kata user. Branch tanpa sesi hidup dicatat di log "Blocker terbuka" dengan tawaran merge atau hapus. Sesi lain yang menyentuh `docs/scope/` dilaporkan ke user sebelum lead mengedit scope. Batas 4 sesi menghitung peer yang masih `busy`.
- Kode yang sudah masuk `main`: untuk tiap kotak `[ ]`, cek path `code in`, artefak yang disebut teks kotak (modul, trait, file test), dan `git log --oneline -15 -- <path dari Build plan>`. Kotak yang artefaknya sudah lengkap di `main` bukan item developer: ia langsung masuk checker verify langkah 6 dan dicatat di log Keputusan dengan hash commit-nya; kotak yang sebagian sudah ada menjadi item developer yang brief-nya menyebut langkah Build plan yang sudah masuk di "Prasyarat yang sudah selesai".

Bangun dependency graph dari empat sumber: (1) teks kotak SCOPE termasuk segmen `build steps N to M`; (2) paragraf pembuka `## Build plan` dan paragraf "Sesi paralel" spec fitur itu; (3) `## Follow-up` spec lain yang menyebut `Fitur <n>`, beserta kotak Follow-up yang belum `[x]` di sana; (4) Catatan urutan `index.md`, serta baris **Done when** untuk kotak tanpa frasa apa pun. Frasa prasyarat: `needs`, `after`, `butuh`, `uses`, `merged first`, `setelah`; frasa paralel: `can run in parallel`, `can run as ... session(s)`, `bisa paralel`. Resolusi: `spec NNNN` → fitur lewat Pointer; `milestone k spec NNNN` atau nama artefak (`daemon server`, `secret::delivery`) → langkah Build plan spec itu, lalu kotak SCOPE yang segmen `build steps`-nya memuat langkah itu (nomor milestone scope dan spec bisa berbeda, contoh F11); `needs feature N` tanpa milestone → `Build it` fitur N `[x]` (bukan status `done`), kecuali Build plan menyebut langkah yang lebih sempit; `A or B` → salah satu cukup; label `wave` diabaikan. Prasyarat setingkat langkah dicatat `setelah langkah <n> fitur <m> masuk main`, supaya item mulai begitu langkah itu di-merge, bukan seluruh milestone-nya. Kotak penutup tanpa frasa mengikuti Legend: `Verify it` dan `Test it` SIAP setelah `Build it` `[x]` dan boleh satu wave (ownership berbeda), `Review it` setelah keduanya `[x]`, `Document it` setelah `Review it`. Baris Follow-up `[ ]` berbunyi "update spec NNNN" yang menjadi prasyarat milestone menjadi item `architect (update)` dengan spec target itu sebagai ownership; baris `/sync ...` dikumpulkan untuk langkah 8 dan 9; baris `/scope ...` dikerjakan lead sendiri setelah persetujuan user. Kotak `Build it` tanpa Pointer dan tanpa kotak `(spec)` (contoh F14 saat scope ini ditulis) diperlakukan seperti kotak `(spec)` bila Done when-nya menyebut nilai yang tidak bersumber dari spec mana pun atau menjangkau lebih dari satu crate: mulai architect, dan setelah merge lead menempel Pointer dan milestone dari blok usulan di bawah kotak `Build it` yang ada tanpa menambah `Design it`.

Tandai tiap kotak terbuka **SIAP** atau **TERBLOKIR** beserta penyebabnya: prasyarat yang belum masuk `main` (kotak `[x]`, atau branch developer-nya sudah di-merge dan pemeriksaan `main` langkah 6 hijau walau checker verify-nya masih berjalan), keputusan yang belum ada di spec, atau hardware dan akun yang tidak tersedia. Prasyarat SIAP di file scope lain yang ownership-nya bebas masuk antrian yang sama sebagai item (brief menyebut file scope-nya; lead mencentangnya di file scope itu dan mencatatnya di log dengan kolom Scope). Dengan argumen nomor fitur, prasyarat lintas fitur dan lintas scope boleh ikut, item lain tidak.

Satu item adalah satu kotak, atau sebagian langkah `## Build plan` satu milestone bila paragraf "Sesi paralel" atau teks kotak menyebutnya dan file-nya tidak beririsan dengan bagian lain (`name` memakai `-s<langkah>`); langkah yang spec sebut dikerjakan lebih dulu di-merge dulu, lalu pecahannya dipotong dari `main`; spike yang spec catat sudah dilakukan tidak diulang. Lead boleh membentuk satu item gabungan `kontrak <major.minor>` per wave: satu developer memiliki `crates/protocol/`, `protocols/`, `schemas/`, `typeshare.toml`, dan hasil `cargo xtask codegen` (`clients/swift/Sources/StacklyClient/Generated/`, `providers/*/versions.json`), mengerjakan semua langkah Build plan yang hanya menyentuh protocol dari beberapa spec sekaligus dengan satu kenaikan minor; brief menyebut tiap langkah dan AC asalnya. Ownership ditulis sebagai path file atau folder dari `## Build plan` dan pointer `code in`, bukan crate; dua item boleh satu wave bila tidak ada file yang sama di ownership-nya, dengan pengecualian yang selalu boleh bersama dan diselesaikan lead saat merge: root `Cargo.toml`, `Cargo.lock`, satu baris `mod`/`pub use` di `lib.rs` crate yang sama, `docs/specs/<NNNN>/verify.md` (bagian milestone masing masing), baris `**Status**` spec, dan `evidence/`; `crates/protocol/`, `protocols/fixtures/`, dan hasil codegen tetap satu pemilik per wave. Untuk tiap kotak `(spec)` yang masuk wave, nomor spec = nomor fitur empat digit (`0015-<slug>`, konvensi spec 0001 sampai 0013); bila nomor itu sudah terpakai, nomor bebas berikutnya setelah mengecek `docs/specs/`, `git branch --no-merged main`, dan tabel sub sesi semua log; catat nomornya di log sebelum sub sesi dimulai. Kotak `(spec)` yang bersarang di bawah `Build it` adalah update spec Pointer yang ada (mode Update architect), bukan spec baru.

Rencana adalah antrian terurut yang disetujui sekali, bukan himpunan. Urutan: (1) item pada rantai sisa terpanjang menuju kotak terakhir SCOPE; (2) item yang merge-nya membuka paling banyak item lain, termasuk di file scope lain, dan untuk file satu pemilik urutkan pemiliknya menurut jumlah dependen; (3) kotak penutup fitur yang `Build it`-nya `[x]`; (4) architect tanpa dependen build sebagai pengisi slot. Item yang ownership-nya tumpang tindih dengan item yang sedang berjalan menunggu. Tampilkan tabel: item, peran, file scope, rantai sisa, yang dibuka, ownership, nama sub sesi, model dan effort dari tabel langkah 3, serta item TERBLOKIR yang akan terbuka oleh merge wave ini dalam urutan mulainya. Lead menampilkan tabel itu lalu langsung ke langkah 3 tanpa menunggu; antrian yang berubah (blocker baru, item tambahan) ditampilkan lagi dengan cara yang sama. Item TERBLOKIR karena keputusan dibuka menurut "Mode keputusan" (lewat item architect, atau satu `AskUserQuestion` untuk semua pertanyaan ronde itu); item TERBLOKIR karena hardware, akun, atau izin user mengikuti "Langkah manual". Bila tidak ada item SIAP sama sekali sesudah itu, jangan mulai sub sesi: tulis tiap blocker satu baris `<fitur> · <kotak> ← <file>:<prasyarat>` | `keputusan: <pertanyaan, OQ/AC terkait>` | `hardware/akun: <apa, pemiliknya>`, dan tawarkan prasyarat lintas scope dari lead ini.

### 3. Mulai sub sesi

Mulai sub sesi dari kepala antrian, maksimal 4 berjalan bersamaan (peer yang `busy` ikut dihitung); begitu satu selesai, ambil item antrian berikutnya yang ownership-nya bebas (termasuk yang baru terbuka oleh merge) tanpa menunggu wave berakhir dan tanpa persetujuan ulang. Untuk tiap item panggil `mcp__ccd_session__start_session` dengan `initiation: "user_asked"`, `context: "fresh"`, `use_worktree: true`, `wake_when_done: true`, `name` berbentuk `<peran>-f<fitur>-<item>` dengan peran disingkat `arc`, `dev`, `chk`, `tst`, `dbg` dan `<item>` = `m<k>` untuk milestone, `m<k>-s<langkah>` untuk pecahan, atau `spec`, `update`, `verify`, `test`, `review`, `fix` (contoh `dev-f10-m1-s3`, `chk-f6-review`, `arc-f67-spec`; maksimal 24 karakter; nama yang sudah dipakai wave lama diberi akhiran `-2`), `branch_name` yang sama, `title` yang diawali `name` itu (`<name> · <fitur dan item>`, di bawah 60 karakter) karena `ListAgents` menampilkan judul dan `[ref]`, bukan `name`, `prompt` berisi brief dari `templates/brief.md` yang sudah terisi penuh, dan `background` berisi tujuan wave. Sub sesi hanya menerima brief itu, bukan riwayat lead, jadi brief harus lengkap; aturan yang sama untuk semua item scope ini tinggal di `<nama-SCOPE>.brief-umum.md` dan brief menunjuknya. Jangan set `permission_mode`, supaya pesan antarsesi tidak tertahan menunggu persetujuan. `source_branch`: checker verify milestone dan debugger pada branch yang belum di-merge mendapat `source_branch: claude/<branch developer>`, sub sesi pengganti mendapat branch lama, yang lain dipotong dari `main`. `model` dan `effort` selalu di-set dari tabel di bawah, jangan dibiarkan mewarisi lead; catat keduanya di kolom Model log (`opus-5-5 · medium`).

`start_session` bisa ditolak pada giliran yang dipicu pesan sesi lain, jadi pada giliran user (giliran `/coordinate` itu sendiri) lead memulai sekaligus semua sesi yang antrian butuhkan: satu sesi per fitur yang punya item SIAP atau akan terbuka di wave ini, ditambah satu sesi cadangan `chk-f<n>-review` untuk tiap fitur `· GA` yang `Review it`-nya masih terbuka, karena review wajib sesi yang belum melihat implementasi. Sesi cadangan dan sesi yang itemnya belum SIAP mengakhiri giliran pertama dengan `STATUS: standby`. Sesudah itu item berikutnya berjalan di sesi yang dipakai ulang ("Pakai ulang sub sesi" di Hemat token); item yang tidak mendapat sesi menunggu sesi yang selesai atau giliran user berikutnya. Sesi architect tidak membangun, jadi boleh melebihi batas 4 sampai 6 sesi; build Rust penuh yang berjalan bersamaan mengikuti batas disk di file aturan umum brief.

Effort lead membatasi giliran pertama sesi baru. Bila effort lead di bawah effort peran di tabel, giliran pertama sesi itu hanya membaca brief, file aturan umum, dan role, lalu berakhir `STATUS: standby`; lead lalu memanggil `set_session_effort` dan mengirim "mulai".

Model per peran. Prinsipnya: keputusan, penilaian, dan pencarian root cause memakai Fable; membangun dan menulis test dari spec yang sudah diputuskan memakai Opus. Id-nya persis seperti di tabel. Ketentuan tambahan di argumen menimpa baris yang disebutnya.

| Peran | `name` | `model` | `effort` | Alasan |
| --- | --- | --- | --- | --- |
| architect, architect (update) | `arc-…` | `claude-fable-5-2` | `high` | keputusan load bearing dan trade-off spec |
| developer, termasuk `kontrak` dan fix hasil review | `dev-…` | `claude-opus-5-5` | `medium` | membangun dari spec dan Build plan yang sudah diputuskan |
| tester | `tst-…` | `claude-opus-5-5` | `high` | test dan evidence, termasuk kasus tepi dan error |
| checker verify, per milestone dan penuh | `chk-f<n>-m<k>`, `chk-f<n>-verify` | `claude-fable-5-2` | `high` | menilai AC, tafsiran developer, dan langkah manual |
| checker review | `chk-f<n>-review` | `claude-fable-5-2` | `high` | beda family dari penulis Opus; aturan reviewer di bawah |
| debugger | `dbg-…` | `claude-fable-5-2` | `medium` | root cause di async, proses anak, socket, dan race |

Sonnet dan Haiku tidak dipakai.

Sub sesi memanggil skill lewat tool `Skill` (`develop`, `check`, `test`, `debug`, `architect`) dengan argumen dari brief; bila tool itu tidak ada, mereka membaca `~/.claude/skills/<nama>/SKILL.md` dan mengikutinya. Reviewer harus beda family dari semua penulis di Range perubahan (kolom Model log dan trailer `Co-Authored-By` pada `git log --format=%b <range>`). Baris tabel (Fable) berlaku selama semua penulisnya Opus. Bila ada penulis Fable, misalnya sesi yang mewarisi model lead, pakai `claude-opus-5-5` `high` asalkan tidak ada penulis Opus. Bila kedua family ikut menulis, pakai Fable dan andalkan subagent review di dalam `/check review`. Brief menyebut "Model penulis kode" dan "Model reviewer". Alamat lead untuk `SendMessage` diambil dari baris pertama hasil `ListAgents` dan ditulis di file aturan umum brief; nama dan judul sub sesi terkait ditulis di brief karena `name` ditentukan lead sebelum mulai.

### 4. Komunikasi

Sub sesi boleh saling kirim pesan langsung lewat `SendMessage` (alamat persis seperti baris `ListAgents`: judul plus `[ref]`) untuk pertanyaan kontrak atau API, kegagalan test, dan temuan review, lalu mengirim ringkasan satu kalimat ke lead. Perubahan di luar ownership diminta lewat pesan ke pemilik file, bukan diedit sendiri. Penyimpangan dari spec dan keputusan yang belum tercatat diteruskan ke lead, yang menyelesaikannya menurut "Mode keputusan"; langkah yang butuh izin user mengikuti "Langkah manual". Panel skill asli dijawab sub sesi dari butir "Panel skill" di file aturan umum dan field "Jawaban panel khusus item ini" di brief, atau diteruskan ke lead dengan `STATUS: needs-decision`; lead tidak pernah menjawab panel di jendela sub sesi, dan keputusan yang berlaku untuk semua item (mis. pilihan cross check) dicatat sekali di log Keputusan dan di file aturan umum brief. Aplikasi menahan pesan antarsesi lead sesudah sekitar 20 pesan sejak user terakhir mengetik: brief meminta satu laporan akhir per item tanpa pesan sementara, lead menggabungkan tindak lanjut untuk satu sesi ke satu pesan, dan saat pesan mulai tertahan lead menutup giliran dengan ringkasan satu baris dan meminta user mengetik `lanjut`. Pesan ke sesi yang sedang bekerja masuk antrian sampai gilirannya berakhir; laporan yang tidak tiba dibaca lewat `mcp__ccd_session_mgmt__list_events`. Lead mengirim tindak lanjut ke sub sesi yang sama lewat `SendMessage`, bukan memulai sesi baru; tindak lanjut sesudah laporan `done` atau sesudah merge lain selalu dimulai dengan `git merge main` di worktree sesi itu.

### 5. Laporan

Saat sub sesi mengakhiri giliran, lead menerima catatan berisi awal recap-nya; karena itu baris pertama recap wajib `STATUS: ...`. Laporan lengkap sesuai `templates/report.md` dikirim sub sesi ke lead lewat `SendMessage`. Setiap branch atau worktree yang selesai wajib sudah ter-commit: laporan `done` hanya sah bila pekerjaannya ter-commit di branch sub sesi itu dan working tree-nya bersih; laporan `done` dengan perubahan yang belum di-commit dikembalikan dengan permintaan commit. Laporan tanpa STATUS, daftar file, branch, atau perintah plus hasil dikembalikan untuk dilengkapi. File di luar BOLEH yang muncul di laporan adalah pelanggaran: minta dikembalikan, lalu catat di log. Catatan sebuah sesi adalah laporannya, bukan bukti: lead memeriksa diff branch-nya sebelum mempercayainya.

### 6. Gerbang centang dan merge

Hanya lead yang mengedit file scope, satu kotak per edit, setelah membaca ulang file itu. Untuk tiap laporan `done`, lead memastikan worktree sub sesi bersih (`git -C .claude/worktrees/<name>-<hash> status --short`) dan `git diff --stat main...<branch>` hanya memuat file ownership (daftar crate yang disentuh diturunkan dari situ, seperti `package_of` di `.githooks/pre-commit`), lalu di checkout utama `git merge --no-ff --no-commit claude/<name>-<hash>` dan memeriksa gabungannya di `main` (satu `target/`, bersama branch yang sudah masuk, karena merge tidak menjalankan hook): `git diff --name-only --diff-filter=U` dan `git grep -n -E '^(<<<<<<< |=======$|>>>>>>> )' -- . || true` harus kosong sebelum commit apa pun, `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test -p <crate yang disentuh>`, `cargo xtask check-deps`, `cargo xtask codegen --check` bila `crates/protocol/` atau `schemas/` berubah, `swift test --package-path clients/swift` bila `clients/swift/` berubah. Hijau: `git commit`. Konflik: hanya pengecualian langkah 2 diselesaikan lead (`Cargo.lock` → `cargo build` lalu commit hasilnya; hasil codegen → jalankan codegen ulang; `verify.md` → ambil kedua centang; `**Status**` → `In Progress`); konflik lain → `git merge --abort`, minta pemilik lewat `SendMessage` untuk `git merge main` di worktree-nya, menyelesaikan, memverifikasi ulang, commit, dan melapor lagi (pemilik yang sudah tidak ada diganti developer baru dengan ownership file yang konflik). Merah karena `fmt`, clippy, atau file di luar ownership: laporan belum lengkap, kirim perintah dan output ke developer itu lewat `SendMessage`, maksimal satu ronde. Merah karena test atau langkah verify: `git merge --abort`, mulai debugger dengan brief yang memuat laporan gagal itu, beri tahu pemilik file (bila sesinya sudah tidak ada, mulai developer baru dengan ownership yang sama sebagai pemilik), dan jangan mulai sub sesi yang bergantung pada merge itu. Siklus merah: debugger mengirim usulan ke pemilik, pemilik menerapkannya di branch-nya dan melapor `done` lagi, lead mengulang pemeriksaan ini dari awal; kotak tetap terbuka sampai hijau. Lalu centang, dan commit tiap edit scope segera (langkah 7):

- `Design it (spec)` di tingkat fitur: ringkasan "Accept this spec?" sudah dijawab menurut "Mode keputusan", branch architect sudah di-merge, spec punya `## Requirements` dengan AC ber-ID, `## Decision`, `## Build plan`, dan `## Consequences`, status `Proposed`, dan laporannya memuat blok scope usulan. Lead lalu mengedit persis: 1) heading `### <n>. <nama> · in-progress` (hapus ` · needs a decision`, pertahankan tag tier); 2) baris `**Pointer:** spec [NNNN](../specs/NNNN-slug/index.md)` di bawah **Trace** (tanpa `code in`); 3) `- [x] Design it (spec): ...`; 4) `- [ ] Build it: /develop <fitur>` plus 2 sampai 5 milestone dari blok usulan, tiap milestone merujuk nomor langkah Build plan yang ada, lalu kotak penutup sesuai tier; 5) baris fitur itu di tabel At a glance `docs/scope/index.md` menjadi `in-progress` dan hitungan Status di "Urutan file" disesuaikan (contoh format: fitur 7 di `01-foundation.md`). Follow-up architect yang menjadi fitur baru diusulkan ke user untuk `/scope`. Kotak `(spec)` bersarang di bawah `Build it` dan item `architect (update)`: lead hanya mencentang kotak itu atau baris Follow-up-nya, tanpa Pointer dan Build it baru, lalu mengusulkan penyesuaian milestone bila Build plan berubah.
- Milestone: branch developer di-merge, lalu checker verify (dimulai dari branch developer lewat `source_branch` begitu laporan `done` tiba, tanpa menunggu merge) melaporkan `done` untuk bagian `## Milestone <n>` di `verify.md`; brief checker menyebut bagian itu, ID AC milestone itu saja, dan langkah yang sudah `[x]`. Laporan `done` developer tanpa bagian `verify.md` milestone itu dikembalikan. Milestone yang dipecah dicentang setelah semua pecahannya di-merge dan satu verify mencakup semuanya. Saat mencentang, gabungkan path dari field "Pointer code in" laporan ke baris `**Pointer:**` fitur (`· code in <path>`, tanpa duplikat, hanya path yang ada di `main`), dan ubah `**Status**` spec `Proposed` → `In Progress` bila developer belum melakukannya.
- `Build it` dan `Verify it`: ditutup bersama oleh satu checker yang menjalankan `/check verify` penuh setelah milestone terakhir di-merge (langkah yang sudah `[x]` tidak diulang, hanya dicek masih relevan setelah merge terakhir); `verify.md` yang dicentangnya di-merge. Langkah yang tersisa `NOT_RUN` atau `BLOCKED` mengikuti "Langkah manual": kotak dicentang bila sisanya hanya langkah manual yang sudah tercatat di file manual, dan tiap `BLOCKED` punya `reason` dan `owner` (aturan spec 0002).
- `Test it`: laporan tester `done`, branch-nya di-merge, `cargo xtask evidence check` lulus di `main`, evidence berlabel benar. `Verify it` dan `Test it` boleh berjalan bersamaan.
- `Review it` (fitur `· GA`): review dari sub sesi checker BARU yang belum melihat implementasinya (brief memuat Range perubahan dan Model penulis kode), file di `docs/reviews/` ada. Temuan Blocker atau Major: lead memulai developer `dev-f<fitur>-fix` dengan ownership file temuan, merge lewat pemeriksaan di atas, checker verify yang sama mengulang langkah `verify.md` yang menyentuh file itu lewat `SendMessage`, lalu reviewer yang sama mengonfirmasi lewat diff baru; `Review it` dicentang setelah tidak ada Blocker atau Major terbuka. Minor dicatat di log.
- `Document it`: lead menjalankan skill `document` lewat tool `Skill` dengan argumen `changelog` dan rentang `<hash main sebelum merge pertama fitur>..<hash merge terakhirnya>` dari log sebagai pengganti `BASE..HEAD` (di `main` rentang bawaan kosong; `pr` tidak dipakai karena tidak ada PR), lalu membaca ulang SCOPE karena skill itu mencentang kotaknya sendiri; `CHANGELOG.md` di-commit lead `docs(changelog): <fitur>`.
- Kotak terakhir fitur dicentang: tandai fitur `done` (Legend menyebutnya keputusan user; user memberikannya lewat bawaan skill ini) dan catat di log Keputusan beserta langkah manual fitur itu yang masih `NOT_RUN`. Edit-nya: `done` di heading, At a glance, hitungan "Urutan file", dan `**Status**` spec `In Progress` → `Accepted` (bukan `In Progress` → catat di log, jangan timpa).

### 7. Log

Setelah setiap laporan, perbarui `docs/scope/coordination/<nama-SCOPE>.log.md` sesuai `templates/log.md` (`<nama-SCOPE>` adalah nama file scope tanpa `.md`, misalnya `01-foundation`). Buat foldernya bila belum ada. Salin field "Langkah Build plan selesai" dan "Pointer code in" laporan ke kolom Item, supaya developer milestone berikutnya menerimanya di "Prasyarat yang sudah selesai". Commit edit scope dan log segera setelah tiap centang dan tiap pembaruan log (`docs(scope): tick <fitur> <kotak>`; graph diperbarui hanya untuk file commit itu, lihat "Graph hanya untuk file yang diubah" di Hemat token), sebelum merge berikutnya dan sebelum memulai sub sesi baru, karena worktree baru hanya melihat `main` yang sudah di-commit dan `git merge` menolak checkout yang kotor pada file yang sama.

### 8. Akhir wave

Tutup wave dengan ringkasan, dalam urutan ini: keputusan delegasi bertanda `berat` (opsi yang diambil, runner-up, cara membatalkan), keputusan delegasi lain, langkah manual baru di file manual beserta kotak yang dicentang dengan langkah itu `NOT_RUN`, lalu selesai (kotak yang dicentang dan branch yang di-merge), terbuka, blocker, kotak di file scope lain yang terbuka karena merge wave ini, dan wave berikutnya. Jalankan `sync` seperti langkah 9 butir 2 dengan rentang wave ini (`<hash awal wave>..HEAD`) supaya `AGENTS.md` yang dibaca sub sesi wave berikutnya sudah mencerminkan kode yang di-merge, commit hasilnya, lalu pastikan `git status --short docs/ AGENTS.md` kosong (edit scope dan log sudah di-commit per langkah 7). Bila masih ada item terbuka, catat `git rev-parse main` sebagai hash awal wave berikutnya di log dan lanjut dari langkah 2; bila semua item SCOPE (atau fitur yang diminta) sudah `[x]`, lanjut ke langkah 9.

### 9. Penutupan: merge semua, `/sync`, commit, push, bersihkan

Saat semua pekerjaan selesai (satu rangkaian spec SCOPE, atau fitur yang diminta), lead di checkout utama menjalankan butir di bawah. User sudah menyetujui push `main` dan pembersihan worktree serta branch lewat skill ini (2026-10-20), jadi lead tidak bertanya lagi; aplikasi tetap bisa meminta approval per arsip sesi.

1. Cocokkan tabel sub sesi di log dengan `git branch --no-merged main`. Merge hanya branch yang laporan terakhirnya `done` dan lulus gerbang langkah 6 (termasuk pemeriksaan di `main` sesudah merge); branch `failed`, `blocked`, dan debugger dicatat `tidak di-merge` di log beserta alasannya. Selesai bila `git branch --no-merged main` hanya menampilkan branch yang tercatat `tidak di-merge`.
2. Jalankan skill `sync` lewat tool `Skill`. Di `main` tanpa perubahan uncommitted skill itu berhenti "nothing to sync", jadi saat mengikutinya lead mengisi inputnya sendiri: `MODE=branch`, `MERGE_BASE=<hash awal dari log>`, `DIFF_COMMAND=git diff --name-status <hash awal>..HEAD`, `CHANGED_FILES` dari perintah itu, scope yang direkonsiliasi `<SCOPE>`, plus baris Follow-up `/sync ...` dari spec yang dibaca langkah 2 untuk diterapkan lalu dicentang. Sesudahnya baca `git diff docs/scope/ docs/specs/`: centang atau status yang tidak didukung gerbang langkah 6 (mis. `Test it` hanya karena ada file test) dikembalikan per hunk dan dicatat `ditolak dari /sync` di log.
3. Commit hasil `/sync` bersama log terakhir di `main` (perbarui graph dulu, hanya untuk file commit itu), lalu tulis ringkasan akhir di log: semua branch yang di-merge dengan hash merge-nya, kotak yang dicentang, dan blocker yang tersisa.
4. Push `main`. `git fetch origin`, lalu pastikan `git status --short` kosong dan `git rev-list --count main..origin/main` = `0`. Bila remote lebih maju, berhenti dan laporkan ke user; jangan rebase, merge, atau force. Lalu `git push origin main` (tanpa `--force`, tanpa branch atau tag lain), dan pastikan `git rev-parse main` = `git rev-parse origin/main`. Push yang gagal (auth, jaringan, hook remote) menghentikan langkah ini sebelum pembersihan; laporkan error-nya ke user.
5. Bersihkan worktree dan branch yang dipakai koordinasi ini, yaitu setiap branch di tabel sub sesi semua wave log SCOPE ini, beserta worktree-nya di `.claude/worktrees/`. Branch dan sesi di luar log tidak disentuh. Sebelum menghapus apa pun, pastikan semua isinya sudah di `main`. Tiap branch harus lulus ketiga cek ini:
   - sesinya tidak sedang bekerja (`list_sessions {"linked": true}`);
   - `git -C <worktree> status --short` kosong, termasuk file untracked;
   - `git merge-base --is-ancestor <branch> origin/main` berhasil, artinya semua commit branch itu sudah ada di `main` dan sudah ter-push.

   Bila lulus: panggil `mcp__ccd_session_mgmt__archive_session` untuk sesinya dengan `reason: "<branch> sudah di origin/main"`, yang juga menghapus worktree-nya. Bila sesinya sudah tidak ada atau worktree masih tersisa sesudah arsip, jalankan `git worktree remove <path>` tanpa `--force`. Lalu `git branch -d <branch>`, bukan `-D`. Terakhir `git worktree prune`. Sub sesi tidak pernah push, jadi tidak ada branch remote yang perlu dihapus.

   Bila satu cek gagal, atau arsip ditolak karena sesi di-pin atau sedang terbuka: jangan hapus apa pun dari branch itu. Catat `disimpan: <alasan>` di log dan sebutkan ke user. Branch yang tercatat `tidak di-merge` (`failed`, `blocked`, debugger) tidak pernah dihapus otomatis; tunjukkan `git log --oneline main..<branch>`-nya dan biarkan user memutuskan. Jangan pernah memakai `git branch -D`, `git worktree remove --force`, `clean_up_worktrees` dengan `include_uncommitted`, atau `discard_kept_worktree`.

   Selesai bila `git worktree list` dan `git branch --list 'claude/*'` tidak lagi memuat branch log ini, kecuali yang tercatat `disimpan` atau `tidak di-merge`.
6. Catat hasil push dan pembersihan di bagian Penutupan log, perbarui graph hanya untuk file log itu, commit `docs(scope): close <nama-SCOPE> coordination`, lalu push lagi dengan cek yang sama seperti butir 4.

## Mode keputusan

**Keputusan** adalah pilihan yang mengubah isi spec: jawaban atas gap architect, "Accept this spec?", dan perubahan teks AC, OQ, atau keputusan yang sudah tercatat. Tafsiran AC yang ambigu oleh developer, checker, atau tester bukan keputusan: sesi itu mengambil tafsiran yang paling sesuai teks AC dan `rationale.md`, menulisnya di laporan, dan checker yang menilainya.

Keputusan **berat** adalah yang mahal dibalik sesudah dibangun: format data di disk atau migrasi, break kontrak (kenaikan major protokol), model keamanan, trust, atau secret, lisensi dan hal hukum, perilaku yang menyentuh data user yang sudah ada, dan perubahan teks AC atau keputusan pada spec `Accepted`. Architect yang menandainya; lead boleh menaikkan tanda itu, tidak menurunkannya.

| Mode | Kata di argumen | Keputusan biasa | Keputusan berat |
| --- | --- | --- | --- |
| `auto` (bawaan) | tidak ada | opsi rekomendasi | opsi rekomendasi, bertanda `berat` |
| `tanya berat` | `tanya berat` | opsi rekomendasi | user |
| `tanya` | `tanya` | user | user |

Mode hanya mengatur keputusan. Rencana wave, debugger, langkah manual, dan tanda `done` berjalan sama di ketiga mode.

**Opsi rekomendasi.** Architect memilih opsi yang direkomendasikannya sendiri, menulis alasannya dan runner-up di `rationale.md`, dan melaporkannya di field "Keputusan diambil". Bila dua opsi setara, ia mengambil yang paling murah dibalik dan menandainya `berat`. Lead membalas `accept` pada ringkasan spec sesudah memeriksa tiga hal: temuan cross check sudah diterapkan, setiap ID di baris **Trace** fitur tercakup AC, dan tidak ada keputusan yang bertentangan dengan spec `Accepted` lain (tanya graph). Ringkasan yang gagal salah satunya dikembalikan ke architect dengan daftar perbaikan. Setiap keputusan masuk tabel "Keputusan delegasi" log: opsi yang diambil, runner-up, tanda `berat`, dan cara membatalkannya.

**User.** Lead mengumpulkan pertanyaan semua architect ronde itu ke satu `AskUserQuestion` (opsi rekomendasi pertama, runner-up kedua, masing masing dengan akibatnya dalam satu kalimat), dan item yang tidak bergantung pada jawabannya tetap berjalan. Jawaban dicatat di log Keputusan dengan `user`.

**Nilai yang hanya user tahu** (alamat email, akun, handle, nama badan hukum, harga) bukan keputusan di mode apa pun: nilainya masuk file manual di bawah "Nilai dari user", AC yang bergantung padanya `BLOCKED` dengan `owner: user`, dan sisanya dibangun.

**Membatalkan.** User menyebut baris "Keputusan delegasi"; lead memulai item `architect (update)` pada spec itu dengan opsi yang user pilih, lalu item developer untuk langkah Build plan yang berubah.

## Langkah manual

Langkah **manual** adalah langkah yang butuh mata, tangan, akun, perangkat, atau izin user: sesi GUI nyata, `cargo xtask ui-test`, login Keychain dan Application Support asli, sleep, logout, reboot, jaringan mati, unduhan, akun macOS kedua, signing dan notarization, pengaturan repo GitHub, upload atau publish, dan kotak yang memuat "after your approval" atau "run by hand on this Mac". Tidak ada sesi yang menjalankannya. Langkah yang gagal, flaky, atau hanya mahal diotomasi tetap merah dan masuk siklus debugger langkah 6.

- Sub sesi menulis langkah itu di `verify.md` bagian `### UI / manual`, atau sebagai evidence `NOT_RUN` atau `BLOCKED` dengan `reason` dan `owner: user`, dan menyalin teksnya ke field "Langkah manual" laporan.
- Lead menyalinnya ke `docs/scope/coordination/<nama-SCOPE>.manual.md` sesuai `templates/manual.md`: prasyarat, perintah persis, hasil yang diharapkan, dan AC yang dibuktikan.
- Kotak dicentang bila setiap langkah yang bisa diotomasi lulus dan sisanya tercatat di file manual. Baris centang di log memuat `(manual NOT_RUN: <nomor langkah>, owner user)`.
- User mengirim `PASS` atau `FAIL` per nomor. Lead meneruskannya ke checker fitur itu, yang mencentang `verify.md`. `FAIL` membuka kembali kotaknya: lead menghapus centang, mencatatnya di log, dan memulai debugger.

## Batasan

- `prd.md` tidak pernah diubah. ID AC dan OQ tetap stabil; teks AC, OQ, dan keputusan spec berubah hanya lewat item architect, diputuskan menurut "Mode keputusan".
- Yang selalu menunggu user, di mode apa pun: konfirmasi scope saat argumen kosong, mengganti model lead, membuang apa pun (worktree kotor, branch yang tidak di-merge), mengambil alih sesi di luar koordinasi, `/scope` untuk fitur baru, dan remote yang lebih maju saat push.
- Lead tidak menulis kode produksi dan tidak membuat branch kerja. Lead hanya push `main` ke `origin`, hanya di langkah 9, dan tidak pernah dengan `--force`. Sub sesi commit hanya di branch-nya sendiri, tidak push, tidak membuat PR.
- Hanya lead yang mengedit file scope (SCOPE, file scope lain yang item prasyaratnya ditarik, `docs/scope/index.md`) dan log koordinasi, dan hanya lead yang merge ke `main`; konflik kode diselesaikan pemilik branch di worktree-nya, bukan lead.
- Fixture pass bukan bukti native; hardware, binary, atau signing yang hilang dicatat `BLOCKED`, bukan dilewati.

## Hemat token

- **Graph hanya untuk file yang diubah.** Setiap update graph (langkah 7 dan 9) hanya memproses file di commit yang sedang disiapkan, yaitu `git diff --cached --name-only` (saat `git merge --no-ff --no-commit` atau sesudah `git add`). File lain yang terdeteksi berubah tidak ikut. Kode cukup `graphify update .`: ekstraksinya AST tanpa LLM dan hanya memproses file kode yang berubah, jadi tidak memakai token. Bila daftar itu memuat dokumen atau gambar, ikuti alur `/graphify . --update`, tetapi sesudah `detect_incremental`, isi `files` di `graphify-out/.graphify_detect.json` dan `graphify-out/.graphify_uncached.txt` hanya dengan dokumen dan gambar dari daftar itu (path absolut), lalu lanjutkan alurnya seperti biasa. Saat menyimpan manifest, panggil `save_manifest` hanya dengan file dari daftar itu: `_stamped_manifest_files(<daftar per tipe>, <ekstraksi baru>, Path("."))`, `kind="semantic"`, tanpa `scan_corpus`. Jangan memakai `incremental['files']`, karena helper itu selalu menandai file kode sebagai selesai, sehingga korpus penuh akan menandai kode dan dokumen lain yang belum diproses. Dengan daftar terbatas, baris file lain tetap seperti semula dan masuk antrian `--update` berikutnya. Jangan jalankan `save_manifest` dari jalur full build. Ekstraksi semantik penuh atas seluruh antrian hanya dijalankan bila user memintanya.
- **Graph dulu, file kemudian.** `graphify-out/` hanya ada di checkout utama dan lead yang memperbaruinya (setelah tiap merge, langkah 7, hanya untuk file merge itu). Sebelum membaca file untuk menjawab "di mana X dibangun", "apa yang memanggil Y", "spec mana yang memutuskan Z", atau "milestone mana yang menyentuh crate ini", lead dan sub sesi bertanya ke graph: `graphify query "<pertanyaan>" --budget 1500` lalu `graphify explain "<node>"`, dijalankan dari checkout utama atau dengan `--graph <checkout utama>/graphify-out/graph.json` dari worktree. File dibuka hanya pada lokasi yang graph tunjuk (`src=`, `loc=`). Di langkah 2 lead memakai graph untuk peta ownership dan dependensi lintas spec, dan membuka spec hanya pada bagian yang disebut langkah itu. Hasil query yang relevan ditempel lead di field "Pengetahuan dari graph" brief, supaya sub sesi tidak mengulanginya.
- **Pakai ulang sub sesi, bersihkan konteksnya dulu.** Untuk item berikutnya dari fitur yang sama (milestone berikutnya, verify milestone berikutnya, `architect (update)` lanjutan, fix hasil review), lead memakai ulang sub sesi yang sudah `done` dan di-merge, bukan memulai yang baru: 1) pastikan sesi idle dan laporannya sudah lewat gerbang; 2) panggil `mcp__ccd_session_mgmt__clear_session` dengan id sesi itu, supaya konteks `/develop` atau `/check` sebelumnya tidak terbawa; 3) bila baris tabel model langkah 3 untuk item baru berbeda dari item lama (mis. verify milestone → verify penuh), panggil `set_session_model` dan `set_session_effort` lebih dulu; 4) perbarui judul lewat `set_session_title` ke `<name> · <item baru>` dan kirim brief baru yang lengkap lewat `SendMessage`, diawali perintah `git merge main` di worktree-nya; 5) catat di log sebagai baris baru dengan status `dipakai ulang`. Worktree dan branch tetap sama, jadi pemeriksaan langkah 6 memakai `git diff --stat main...<branch>` yang hanya memuat perubahan baru. Tidak untuk `Review it` (wajib sesi baru) dan tidak untuk sesi yang sedang dibuka di layar atau di-pin (clear ditolak aplikasi; mulai sesi baru).
- **Brief ringkas, bukan salinan.** Brief menunjuk bagian spec dan `verify.md` yang dibutuhkan item itu, bukan menyalin isinya; `AGENTS.md` sudah dimuat otomatis di tiap sesi, jadi tidak diulang; laporan sub sesi memuat nomor langkah dan path, bukan isi file.

## File skill

- `roles/architect.md`, `roles/developer.md`, `roles/checker.md`, `roles/tester.md`, `roles/debugger.md`: tujuan, command, ownership, jalur pesan, definisi selesai, dan verifikasi tiap peran.
- `templates/brief.md`, `templates/report.md`, `templates/log.md`: format brief, laporan, dan log.
- `templates/brief-umum.md`: aturan yang sama untuk semua brief satu scope (mode keputusan, model per peran, larangan, disk, panel skill); lead mengisinya sekali di langkah 1.
- `templates/manual.md`: format file langkah manual untuk user.

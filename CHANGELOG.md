# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `stacklyd`, the per user daemon, now serves the Stackly IPC protocol 1.2 over a private Unix socket. Messages are JSON behind a 4 byte length, at most 1 MiB, and every client starts with a handshake that names its protocol version and contract digest (see spec 0006).
- Only one daemon runs per user. It holds a lock in `<data>/stacklyd.lock` before it touches the log, socket, or registry; a second `stacklyd` for the same root exits 3 and names the daemon that owns the lock (see spec 0006).
- `stackly daemon status` shows the running daemon: status, pid, uid, version, protocol, server instance, start time, the four roots, and the socket path. `--json` prints `info`, `health`, and a `client` block with the contract drift flag. Any health exits 0; no daemon exits 6, an untrusted socket 4, another protocol major 5, a timeout 8, and a rejected `STACKLY_ROOT` 2 (see spec 0006).
- Every error, from the daemon or the client, is one envelope from a single catalog: a stable `code`, a `category`, `retryable`, safe `details`, and optional `items`. The catalog is written to `protocols/error-codes.json` (see spec 0006).
- Event subscriptions with cursors: `events.subscribe` with `since` replays missed events in order and then goes on live. A cursor from an earlier daemon run, or one older than the last 4096 events, starts with an explicit `events.gap` so the client takes a fresh snapshot (see spec 0006).
- Recovery mode: when the registry needs recovery (for example a schema newer than the app), the daemon keeps serving with health `degraded` and the recovery report in `get_health`, never prunes, and answers any method not allowed there with `registry.recovery_mode`. A registry another process holds is tried again after 1, 2, and 4 seconds first (see specs 0005 and 0006).
- The daemon log: JSON lines to stderr and to `<logs>/daemon/stacklyd.log`, rotated at 20 MiB with 5 files kept, never blocking the daemon, and counting any dropped lines in health. Each request line carries the request ID, method, client kind, `interactive`, duration, and outcome, never params or replies. `STACKLY_LOG` sets the filter (see spec 0006).
- `stacklyd --print-roots` prints the resolved data, logs, cache, and runtime roots plus the socket path, then exits without creating anything (see spec 0006).
- The `stackly-ipc` crate: the socket transport shared by the daemon and the CLI, with the endpoint checks below and a client that matches replies by request ID (see spec 0006).
- Contract tooling: `cargo xtask codegen` writes the Swift types, `OpenEnums.swift`, `ContractInfo.swift`, the JSON Schemas, the error catalog, and the contract digest, and records each protocol version in `protocols/contract-versions.json`. It refuses a contract change that keeps the same version (see spec 0006).
- Shared contract fixtures in `protocols/fixtures/`, read by both the Rust and the Swift tests, and `StacklyJSON` in the Swift client for millisecond timestamps (see spec 0006).
- Fuzzing for the IPC codecs: `cargo xtask fuzz list`, `seed`, `build`, and `run` with a pinned nightly toolchain and cargo-fuzz version, and the targets `ipc_frame_decode` and `ipc_request_decode` (see spec 0006).
- The provider engine: it reads a provider package in `providers/<name>/` (a `stackly/v1alpha1` manifest, a settings schema, config templates, and `versions.json`), validates it strictly, and builds the init, run, and reload plans as plain data for the process supervisor. Reading a package never runs a process, writes a file, or reads a secret, and every problem comes back as an issue with its file, field path or line and column, and a stable code (see spec 0009).
- Provider settings are a typed model from a small JSON Schema dialect, with the six VAL-012 classes (managed, advanced, secret, immutable after init, reloadable, restart required), patterns that always match the whole value, and checked defaults, so forms can be drawn from the schema alone (see spec 0009).
- Config templates use a small renderer of their own (`{{ }}`, `#if`, `#each`) that escapes every value for `yaml`, `json`, or `natsConf`, parses `yaml` and `json` output again, and stops at 1 MiB (see spec 0009).
- Three example packages: `official/nats`, `official/traefik` with a list of routes, and `testing/fake` for tests only (see spec 0009).
- `cargo xtask provider check [<dir>...]` checks provider packages and prints `ok <id> <revision> <manifest_sha256>` for each valid one, or one line per problem (see spec 0009).
- `cargo xtask codegen` also writes each provider's `versions.json` from `runtimes/inventory.toml` and the editor JSON Schemas in `schemas/provider/`, and `--check` fails when they drift (see spec 0009).
- `stackly-fake-server`, a dummy server for tests that can delay readiness, crash with a chosen exit code, spam logs, ignore SIGTERM, and reload its config on SIGHUP, plus `stackly_testkit::fake_server::binary()`, which builds it once per test run (see spec 0009).
- Four fuzz targets for provider manifests, templates, interpolation, and settings schemas, seeded from the example packages (see spec 0009).
- Error codes `manifest.invalid` and `provider.*` (invalid settings, unsupported capability, endpoint not loopback, unrepresentable value, plan invalid, render failed), with each package or settings problem as an `issue` item, and a provider `ResourceRef` written as `<namespace>/<name>@<revision>#<manifest_sha256>` (see spec 0009).
- The operation engine: every change Stackly makes runs as one operation that is recorded first and answers with its ID at once, then runs in the daemon in the background through the seven states `queued`, `running`, `cancel_requested`, `succeeded`, `failed`, `cancelled`, and `needs_recovery`. A client that disconnects never cancels its operation (see spec 0007).
- Idempotency keys: a request that starts an operation needs an `idempotencyKey`. The same key with the same request replays the first operation, so the GUI and the CLI sending the same command make one change, and the same key with another request is refused with `operation.idempotency_key_reused`. Secret values never enter the request fingerprint (see spec 0007).
- Locks per resource and a bounded queue: operations on the same resource run in order, the rest run side by side, at most 8 run and 64 wait, and a full queue answers `operation.queue_full`. Locks live in memory; the registry never serves as a lock while a step waits (see spec 0007).
- Six operation methods in the daemon: `operation.get`, `operation.list` (newest first, a cursor, `activeOnly`, a resource filter, pages that always fit a frame), `operation.cancel`, `operation.resume`, `operation.abandon`, and `operation.get_stats`, plus the events `operation.state_changed` and `operation.progress` in revision order. Protocol 1.3 adds them to the contract with fixtures for Rust and Swift (see spec 0007).
- Cancel says what happened: cancelled before it started, stopped and undone, still running because it passed a step that cannot be undone, or already final (see spec 0007).
- Recovery after a crash or a stop: an operation that can resume runs again from its last step without repeating a step that is not safe to repeat; one that cannot is undone automatically before its point of no return, or waits in `needs_recovery` for `operation.resume` or `operation.abandon`. `daemon.get_health` reports the `operations` subsystem as `degraded` with the number of operations that need recovery (see spec 0007).
- The operation journal in the registry: migration 2 adds the steps, created items, and lock keys of each operation, with a frozen `registry-v2.sql` fixture (see specs 0005 and 0007).
- A failed operation keeps its items and the business rule it broke. `operation.get`, `operation.list`, the operation events, and the `recovery.error` of an operation in `needs_recovery` carry up to 100 items (each a reason kind with at most 8 short fields) and a rule such as `BR-002`, also after the daemon restarts. Field values are redacted before they are stored, the whole list stays under 64 KiB, and the number of items left out goes in the `omitted` detail. The wire contract does not change; the existing `items` and `rule` fields now carry these values (see spec 0007).
- Migration 4 adds the stored items and rule to the operation journal, with a frozen `registry-v4.sql` fixture. Operations written by earlier builds read as having no items and no rule (see specs 0005 and 0007).
- The process supervisor in the daemon: `instance.create` (a temporary create for the fake provider until feature 20), `instance.start`, `instance.stop`, `instance.get`, and `instance.list`, plus the events `instance.state_changed` and `instance.health_changed` ordered by `statusSeq`. Protocol 1.8 adds them with fixtures for Rust and Swift. Process, readiness, health, and desired state are reported apart, so a server that runs but is not ready yet never looks stopped (see spec 0010).
- Starting an instance is one transaction: the process is spawned suspended, its identity is recorded, and only then does it run. Readiness comes from `tcp`, `http`, or `exec` probes with a deadline per provider, and starting an instance that already runs never spawns a second process on the same data, because start holds an exclusive lock on the instance folder (see spec 0010).
- Restart policy: a process that exits on its own while it should run is started again after 1, 2, 4, 8, and 16 seconds with jitter. The sixth crash in 5 minutes stops the retries with `crash_loop`, a long healthy run resets the count, and a port another program took stops it with `endpoint_in_use` without using the budget (see spec 0010).
- After a daemon restart, the daemon adopts a running instance only when its compound identity matches (PID, start time, executable, boot session, and the instance lock). A process it cannot prove is marked `unknown` and never signalled, and after a reboot instances come back `stopped` (see spec 0010).
- Instance output goes to spool files in the runtime folder and keeps being written while the daemon is down. The daemon reads them line by line, redacts every known secret before anything is kept, frees the bytes it read so the spool stays small, and keeps the last lines for `lastFailure.excerpt` (see spec 0010).
- The `ProcessSupervision` platform port with its macOS adapter and a fake for tests (see spec 0010).
- `OperationEngine::replay` looks up an idempotency key before a method starts an operation. It only reads: a repeated request gets its first reply back without running the method's precheck, writing to the registry, or sending an event, and it follows the same daemon phase rules as starting an operation (see spec 0007).

### Changed

- `stackly` now reads `STACKLY_ROOT` once at startup, with the same rules as the daemon (see spec 0006).
- Open enums in the contract read a value from a newer daemon as `unrecognized` instead of failing, in Rust and in Swift (see spec 0006).

### Security

- The daemon checks the peer's uid right after accept and refuses a peer of another user, or one whose credentials cannot be read, with `ipc.peer_rejected` before it reads any request (see spec 0006).
- Clients check the socket and its folder (type, owner, and mode, without following symlinks) and the daemon's uid before they send a byte, so a fake endpoint never receives a credential or a change (see spec 0006).
- The daemon opens no TCP or UDP socket, and `cargo xtask check-deps` rejects any TCP or UDP socket in the daemon, CLI, and IPC code (see spec 0006).
- A provider manifest cannot run a shell or code of its own: its steps, probes, and template formats are closed sets, unknown fields (including security fields) are rejected, every argument is one argv element exactly as written, the child environment comes only from the plan, executables come only from the declared runtime, and every path stays inside the instance folders the manifest declares (see spec 0009).
- A provider package cannot exhaust memory or loosen its own checks: a YAML manifest or rendered YAML config whose aliases would expand it far beyond its size is refused before it is built, and a settings or data marker pattern must compile on its own, so it always matches the whole value (see spec 0009).
- A secret reaches a provider process only through stdin, a one time file in the instance's `secrets` folder, a whole env value of the start or init command, or a sensitive config file, never through argv, and plans show it only as `<secret:field>` (see spec 0009).
- Cleanup after a failed or cancelled operation removes only what that operation created under the Stackly roots: its own scratch folder and the folders of the instances or environments it made, never through a symlink, never across a device, and never a tree whose owner it cannot prove (see spec 0007).
- A normal stop never uses `SIGKILL` or kills by name: it follows the provider's stop strategy, and only a helper process group that outlives its timeout is killed. `cargo xtask check-deps` allows the `SIGKILL` name only in the macOS adapter's kill module and rejects any process spawning API in the core and the daemon (see spec 0010).
- A secret never reaches a provider through argv: the start is refused before it spawns anything, and the secret files a start rendered are removed again when the start fails or is cancelled before the process runs (see specs 0010 and 0011).
- Operation journals, the request fingerprint, events, and the daemon log never hold a secret value; a byte scan of the registry files and the log after an operation with a secret in its params finds none (see spec 0007).
